## 1. テスト戦略の原則

### 1.1 何のためにテストするか
1. **回帰防止**: 変更で既存機能を壊さないこと（Phase 1 で「シンプル化」した割に肥大化しないこと）
2. **設計判断の保護**: spec.md / architecture.md の判断を実装が逸脱したら検知すること
3. **手戻り削減**: 実装中の早期検出で「Phase 1 仕様再検討」相当の手戻りを防ぐこと

### 1.2 何をテストしないか
1. **WebView2 / Tauri / OS API 自体**: 上流の責任、信頼する
2. **voicevox_core / Irodori モデルの合成品質**: 上流の責任、入出力の存在のみ検証
3. **LLM プロバイダの応答品質**: 同上
4. **キャラ画像の見た目品質**: 手動目視のみ

### 1.3 三段構成
| レベル | 対象 | 自動化 | 実行頻度 |
|---|---|---|---|
| ユニット | 純関数・パーサー・データ変換 | ◎ | 変更のたびに開発機で（CI は無い。§2.3） |
| 統合 | Tauri コマンド・DB マイグレーション・サイドカー HTTP | ◎ | 同上。リリース前は Workflow `release-audit` でも走らせる |
| 手動 | UI・実発話・実 GPU・配布 | △ | リリース前 |

## 2. テスト技術スタック

### 2.1 Rust 側
- **ユニット**: `cargo test`（標準 `#[test]`）
- **非同期テスト**: `#[tokio::test]`
- **HTTP の相手**: モック用のクレートは使わない。テストの中で `std::net::TcpListener` を 127.0.0.1 の空きポートに立て、決めた応答を返す（`tts/sidecar.rs` のテストなど）。サイドカーの代役・無関係なサービスの代役・接続は受けるが答えない相手を、同じ方法で作る
- **SQLite テスト**: `Db::open(":memory:")` で都度新規 DB。ファイルとして開く必要があるものは `tempfile` の一時ディレクトリに作る
- **アサーション**: 標準の `assert!` / `assert_eq!`（追加のアサーション用クレートは使っていない。dev-dependency は `tempfile` だけ）
- **実機依存のテスト**: 実環境の Irodori ランタイムを使うものは `#[ignore]` を付け、環境変数（`UGG_IRODORI_REAL_ROOT`）で対象を渡したときだけ手動で走らせる（`tts/irodori_download.rs` の `irodori_update_on_a_real_runtime`）
### 2.2 TypeScript 側 ★v0.5.3 で実際に導入
- **ユニット**: [Vitest](https://vitest.dev/)（Vite ネイティブ、軽量）。`npm test` = `vitest run`、設定は `vitest.config.ts`
- **DOM 操作**: **happy-dom**（当初は jsdom 想定だったが、起動が速く Vitest の推奨でもあるため差し替えた）
- **DOM の作り方**: ダミーを手書きせず **`index.html` の body をそのまま読み込む**（`src/__tests__/dom.ts`）。フロントは静的配置された要素を `getElementById` で掴む設計なので、手書き DOM だと **id がずれてもテストだけ通る**。出荷する HTML を使えばそのずれも落ちる
- **Tauri IPC モック**: `vi.mock("@tauri-apps/api/core")` で `invoke` を差し替え、コマンド名ごとに応答を返す
- **経緯**: 本節は Phase 3 から書かれていたが、**v0.5.2 まで実体が無かった**。v0.5.3 の 14 件のうち 3 件がフロント側のつなぎ目だったため、ここで最小限だけ用意した

### 2.3 CI（置いていない）
- **CI は無い**（`.github/` は無い。v0.4.1 で見送り。CLAUDE.md のロードマップ参照）。自動テストは開発機で走らせる: `cargo test` / `cargo check`（src-tauri/ 内）・`npx tsc --noEmit`・`npm test`
- リリース前は Workflow `release-audit`（`.claude/workflows/release-audit.js`）が `cargo test` / `cargo check` / `npx tsc --noEmit` をまとめて走らせる。**`npm test` は含まれないので別に走らせる**（§6・§7）

### 3.2b 操作列テスト（★v0.5.3、spec §6.0 項目 9）

v0.5.3 で確定した第三者レビューの 14 件は、**単機能テストでは 1 件も捕まらなかった**。
単独の機能ではなく「更新経路」「保存後の再保存」「連続通知」「非同期の中断」という
**つなぎ目**に集中していたためで、そこを固定するには操作を順に流すテストが要る。
4 本を常設側に置く（v0.5 の「再発を止める土台」＝契約テスト 2 本と同じ位置づけ）。v0.5.4 で 5 本目を足した。

| # | 操作列 | 場所 | 何を固定するか |
|---|---|---|---|
| 1 | 旧版からの更新 | `commands/assets.rs::install_tests::install_then_update_then_failed_update_leaves_a_usable_ghost` | 新規導入 → 更新成功 → **更新失敗** → 再更新。失敗しても直前まで使えていた版が残り、そのあと更新し直せる |
| 2 | 保存してからの再保存 | `src/__tests__/resave-does-not-revert.test.ts` | ゴースト切替を保存 → `default_shell` の追従 → **もう一度保存**。フォームが古い id を送り返して追従を取り消さない |
| 3 | 連続通知 | `src/__tests__/consecutive-notices.test.ts` | 同じ tick で 2 件の通知 / 通知の描画中に応答が割り込む / 応答の描画中に通知が来る / Ambient は守らない |
| 4 | 非同期処理途中の停止 | `src/__tests__/stop-during-async.test.ts` | 合成 → **デコード待ちの最中に停止** → デコード完了。停止後に再生も口パクも始まらない |
| 5 | 更新が届いていないランタイムを開く（★v0.5.4） | `src/__tests__/irodori-update-visible.test.ts` | 古いが動いているランタイムを**「未導入」に落とさず**、実モデルの設定も消さない / 最新なら更新の導線を出さない / 未導入は導入へ誘導する / 更新後に導線が消える / 確認で断ったら入れ直しを始めない |

書き方の要点:
- **「表示された」ではなく「最後まで表示された」を観測する。** 打ち切られた発話も
  記録してしまうと、消えたことが観測できずテストが変異を素通りする（実際に一度そうなった）
- 各テストは対応する修正を**壊して落ちること**まで確認する（変異テスト）

### 3.3 テストデータ
- **外部のフィクスチャファイルは置いていない**（`tests/` フォルダも `include_str!` / `include_bytes!` も無い）。辞書・マニフェストなどの入力は、各テストの中にインラインの文字列で書く（`ghost/dict.rs` / `ghost/manifest.rs` / `ghost/dnd.rs` など）
- DB: `:memory:` で都度生成するか、`tempfile` の一時ディレクトリに作る（§2.1）
- ファイルが要るテスト（アセット展開・ログ・台帳・導入記録など）は `tempfile` の一時ディレクトリに書き出す
- 設定: 各テストでデフォルト Settings から差分指定

## 4. 統合テスト戦略

### 4.1 Tauri コマンドレベル E2E（Rust）

各コマンド（architecture.md §4）に対し、最低限以下を検証:

| コマンド群 | 主要テスト |
|---|---|
| boot | `get_boot_payload` が必須フィールドを満たす、画像 data URL が valid |
| settings | `set_settings` で clamp 適用、`apply_settings` が後処理を呼ぶ |
| dialogue | `send_user_message` が low/advanced で適切な経路を通る（LLM 部分はモック） |
| interaction | `poke` / `nade` の events 探索順、サブ無しゴーストでの分岐 |
| profile | `add_profile` で origin=manual、容量上限到達時の挙動 |
| tts | `synthesize_voice` が slot 振り分け（合成本体は voicevox_core Stub） |
| pomodoro | `start/stop`・状態機械の遷移・節目 emit |
| assets | `dnd_install` が zip/フォルダを正しく検出、衝突時の戻り値 |
| data | `export_data` の JSON 構造、`clear_history` の影響範囲 |

### 4.2 サイドカー HTTP クライアントのテスト（Z3）

モック用のクレートは使わず、テストの中で 127.0.0.1 の空きポートにダミーサーバを立てて応答を決める（§2.1）。
主な実例は `tts/sidecar.rs` のテストで、次を確かめている:

- `/health` の**応答の形**で自分のサイドカーを見分ける（GPU 不在の 503 でも自分のもの。無関係なサービスは撃たない）
- 孤児掃除の判定（死んだポートは拒否で捨てる / 接続は受けるが答えない相手は記録を残す / 自分のものは `/shutdown` で止め、止められなければ記録を残す）
- 台帳（`sidecars.json`）の読み書きと排他、`ready.json` は起動した子の pid と一致するものだけを受け入れる
- stderr の読み取りが、読めない行や読み取りの失敗で黙って止まらない（★v0.5.5）

500 応答の本文から発話テキストを伏せる処理は `tts/irodori.rs` の `sanitize_sidecar_error` のテストで確かめる。
実モデル・GPU を使う合成と、漢字→ひらがな前処理（`commands/tts.rs` の `preprocess_for_irodori`）の実際の変換は自動テストの対象外（手動テスト §5）。
### 4.3 辞書 v3 バリデータの統合テスト

- ✓ 正しい v3 辞書がパース成功
- ✓ schema_version != 3 で起動時警告
- ✓ when 条件（all_of/any_of/not/not_in_recent/probability）が個別に評価される
- ✓ sub: null が main 単独として処理
- ✓ 必須 system_messages キーの不足を warn する（致命ではない）
- ✓ 未知の events キーは warn して読み飛ばし

### 4.4 DB マイグレーション

- ✓ 空 DB に対し v1 への初期マイグレーションが通る
- ✓ 既存 v1 DB を起動して破壊しない
- ✓ マイグレーション中にエラーが起きてもアプリは起動失敗で安全停止（壊さない）

### 4.5 GPU/サイドカー実機テスト（Z3、手動）

- 自動テストは無い（§2.1・§4.2。`gpu-required` という feature もラベルも無い）。下の対象は §5 の手動チェック（E-1b〜d・E-7・E-8 など）で確かめる
- 対象: 実 Python サイドカー起動、実 GPU 検出、Irodori モデルロード、合成精度の確認（出力 wav が再生可能か）
- 例外として、実環境の Irodori ランタイムの更新経路だけは `#[ignore]` のテスト `irodori_update_on_a_real_runtime`（`UGG_IRODORI_REAL_ROOT` で対象を渡す）で走らせられる。**実環境を書き換える**ので、ユーザーの端末で行う（CLAUDE.md の dev 実機検証の規律）

## 5. 手動テストチェックリスト（リリース前必須）

spec.md の §4 機能仕様の構造に従う。各項目に **○/×/該当なし** を記入してリリース判定に使う。

### 5.1 A. キャラクター・ウインドウ

- [ ] **A-1 サブ任意化**: shell.json に sub 定義なしのゴーストで、画面に main のみ表示・掛け合い辞書は無視・撫で/つつき sub 操作不可
- [ ] **A-2 pose プリロード**: 全 pose を起動時に取得、切替時にチラつきなし
- [ ] **A-15 タイプライター速度可変**: 設定で「速い/普通/遅い/一気に」が反映される、変更後の発話で効く
- [ ] **A-3 3 つ目の吹き出し**: advanced モードで複数回会話しパターン3/4 が出るまで待つ（出にくい場合は system prompt が短いので数十回程度）。パターン3（main→sub→main）・パターン4（sub→main→sub）とも、3 番目の発話が `#balloon-extra`（既存の main/sub とは別の吹き出し）に独立表示される。配置は 3 ターン目の話者キャラ（パターン3=main、パターン4=sub）の横（既存 main/sub と同じキャラ左横・顔の高さ）で、かつ main/sub の吹き出しと重ならず外側（上方向）にずれている。3 ターン目の間もキャラをドラッグすると extra 吹き出しが追従する。全ターンの表示+読み上げが終わると main/sub/extra が同時に消える（3 つ目だけ残らない）
- [ ] **A-4 口パク（spec §4.1.4／v0.5.1 で初めて動くようになった）**: TTS 有効で発話させる → **声の大小に追従して**口が開閉する（一定間隔の点滅ではない）。無音の間は閉じている。TTS 無効では動かない。**発話を途中で止めても口が開いたまま固まらない**（`stop()` は `onended` を確実には発火しないため要確認）。設定「音声」の**声のテスト（プレビュー）では動かない**（キャラが喋っているわけではない）。開口フレーム（`<pose>_talk.<ext>`）を持たないシェルに切り替えると口パクは起きないが、**発話そのものは normal のまま正常に行われる**（絵が欠けたり止まったりしない）
- [ ] **A-5 表示スケール**: 0.5〜2.0 でキャラサイズが変わる、**吹き出しのフォント・borderは変わらない（視認性維持）**
- [ ] **A-6 ステージとキャラ位置**: ステージは作業領域下端の全幅帯（ウインドウ自体は動かせない）。キャラを X ドラッグ→終了→再起動で位置復元。保存なし・モニタ消滅時は既定配置（main 右端・sub その左）
- [ ] **A-9 伺か風レイアウト**: 既定配置でメインが右端・サブがその左隣・下端揃え（足元がタスクバー上端）、吹き出しは各キャラの左横（顔の高さ）に出て、しっぽがキャラ側を向く
- [ ] **A-10 キャラ個別移動**: main / sub をそれぞれドラッグで X 方向にのみ移動できる（Y は固定）。ステージ端で clamp。吹き出し表示中はキャラに追従し、画面左端付近では吹き出しが右横に反転する。透明部・吹き出しのドラッグでは何も動かない
- [ ] **A-11 入力導線**: キャラを 1 クリックで、そのキャラが入力促し（辞書 input_prompt、単独発話・TTS あり）を返し、入力欄がそのキャラのバルーン上側に出る。促し吹き出しは入力欄を閉じるまで残る。sub クリックでは sub が反応し sub 側に入力欄。再クリック / Esc で両方閉じる。キャラをドラッグすると入力欄も追従
- [ ] **A-12 表示モニタ選択（spec §4.1.6／M13）**: 設定「基本」→「表示モニタ」に接続中のモニタが順番・解像度・主/現在つきで並ぶ。選ぶと**その場でステージが移動**する（次の 1 秒監視を待たない）。再起動しても選んだモニタに出る。モニタ 1 台の環境では select が無効で「モニタが 1 台のため選択できません」と出る
- [ ] **A-13 DPI が異なるモニタ間の切替（spec §4.1.6 の名指し要件／M13）**: 拡大率の違う 2 台（例 150% と 100%）の間で切替 → **移動先の拡大率でステージ高さが再計算**され、キャラの足元がタスクバー上端に揃う。切替直後に一瞬ずれても 1 秒以内に収束すること（`apply_dock` は `set_position` → `set_size` の順）。切替後に ① クリック透過（キャラの外側でデスクトップを操作できる）② キャラ X 位置が新しい幅へ clamp される ③ 吹き出しがキャラに追従する、の 3 点が崩れないこと
- [ ] **A-14 選択モニタの取り外しと復帰（M13）**: 選択中のモニタをケーブル抜き／無効化 → **主モニタへ退避**し、設定には「選択中のモニタが見つかりません（主モニタに表示中）」の注記が出る（**「自動」に戻ったように見えないこと**）。つなぎ直すと自動で選択モニタへ戻る。解像度やモニタの並びを変えた場合は「別構成」と判断して主モニタに置く（仕様どおり。選び直せる）
  - **既知の制限（v0.4.0）**: 2 台→1 台になった場合だけ、注記より「モニタが 1 台のため選択できません」が優先表示され、select も「自動」に見える。選択自体は保持されている
- [ ] **A-7 セーフモードがない**: 設定パネルにセーフモード項目なし、トレイメニューにも項目なし
- [ ] **A-8 トレイ**: 左クリックで表示/非表示、右クリックメニューに「セーフモード」項目なし

## 6. CI 構成（置いていない）

CI（GitHub Actions など）は**置いていない**（v0.4.1 で見送り）。Phase 3 で書いた雛形（`ci.yml` / `release.yml`）は
導入されなかったので、2026-09-17 の docs 整理で本節から外した（原本は git 履歴）。代わりに次で担保する:

- **開発中**: 変更のたびに開発機で `cargo test` / `cargo check`（src-tauri/ 内）・`npx tsc --noEmit`・`npm test`
- **リリース前**: Workflow `release-audit` がビルド検査（`cargo test` / `cargo check` / `tsc`）・契約とバージョンと bundle 設定の突合・差分レビューを並列で行う。`npm test` は別に走らせる。インストール版の起動確認は `.claude/skills/releasing-ugg` の手順で行う（§7）
- **自動テストで扱わないもの**: GPU を使う合成（Z3）・実 Python サイドカーの起動・voicevox_core 実資産の DL・LLM プロバイダへの実接続。これらは手動テスト（§5）で担保する
