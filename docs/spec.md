## 1. プロダクトコンセプト

### 1.1 ugg とは
「伺か」コンセプトを Tauri v2 で再構築したデスクトップマスコット。デスクトップに常駐する2体（または1体）のキャラクターが、自発的に話したりユーザーと対話したりする。

### 1.2 コアアイデンティティ
- **マスコットの存在感**: 起動挨拶・独り言・放置反応・つつき/撫で反応で「そこにいる」感を出す。
- **掛け合い対話**: メイン/サブ2体の会話表現が基本。
- **無料でも動く**: API キー無しでも辞書ベースの会話で楽しめる。
- **プライバシー優先**: 発話テキストは外部送信しない（クラウド LLM 経路を除く明示的同意済みの範囲のみ）。

### 1.3 ターゲット
- **OS**: Windows 10/11 x64 のみ
- **ハードウェア**: 通常のCPUのみで全機能動作（一部 GPU 拡張機能あり、§4.5.1 参照）

## 2. 採用済み技術選定（再調査しない）

| 領域 | 選定 | 理由 |
|---|---|---|
| プラットフォーム | Tauri v2 + Vanilla TypeScript + Rust | v0.0.3 実証済 |
| データストア | SQLite + keyring + ファイル資産 | 同上 |
| TTS（既定） | voicevox_core 埋め込み（libloading + プリビルドC API） | 無サーバ・CPU合成 |
| TTS（オプション） | Irodori-TTS サイドカー同梱（GPU必須） | キャプションVoiceDesignの上位品質 |
| クリック透過 | アルファマスク方式（8px グリッド + ポーリング） | 透明部分の誤クリック防止 |
| 対話モード | 二モード制（low=辞書 / advanced=LLM） | API キー無しでも動かす |
| 配布 | NSIS インストーラ（currentUser） | v0.0.3 実証済 |

## 3. 横断方針（全機能に適用）

### 3.1 ゴースト発話原則
**システム的なメッセージはできる限りキャラクター（ゴースト）に喋らせる**。トースト・ダイアログは補助・フォールバック扱い。

対象例:
- コスト警告（80%到達・上限超過）
- モード自動降格の通知
- 更新通知
- 自動DL完了・失敗
- 軽微なエラー

**ウインドウが見えていない間（隠している・最小化している）は出さない**（§4.6.1 と同じ「見えない間は届いていない」。v0.5.6）。
1 回だけ出す告知（コストの 80% 警告・上限到達・集計不能・アプリ更新）は、**届いたときにだけ済みにする**ので、見えていない
間に来たものは次の機会にもう一度出る。以前ここにあった「重大なものはトーストで二段表示」は実装されないまま v0.5.6 で
取り下げた（2026-09-19 ユーザー裁定。2 段目も同じウインドウの帯で、見逃しが起きる状況では 1 段目と一緒に消えるため）。

辞書 `system_messages` に対応キーを定義し、各台詞バリエーションを作者が書ける構造。発話できない状況（ゴースト未ロード・起動直後・致命的エラー）は従来のトースト/ダイアログにフォールバック。

### 3.2 「無サーバ」要件
**ユーザーが ugg を使うために、別アプリ・別サーバを手動起動する必要はない**。
- voicevox_core: アプリに埋め込み
- Irodori-TTS: サイドカーとして同梱（ユーザーから見れば「ugg の一部」）
- LLM API: 例外（クラウド/ローカルとも、ユーザーが API キー or LLM サーバを別途用意）。これはユーザーの選択で動かす対象なので「無サーバ」の対象外と整理。

### 3.3 プライバシー
- 発話テキスト・合成音声は外部送信しない。
- LLM プロバイダへの送信のみクラウドへ出る（ユーザー同意済み・既定ローカル/オフライン優先）。
- 時事ネタの検索キーワードは検索サービスへ送信（既定オフ・オンボーディング同意必須）。
- カレンダー: ユーザーが明示設定した URL への ICS 取得リクエストのみ（既定オフ。§4.6.4）。
- 天気: ユーザーが明示設定した地域の座標・地名クエリを気象 API へ送信（既定オフ・**設定行為をもって同意とみなす**・座標は市区町村粒度に丸める。§4.7.2）。
- データのエクスポート・削除をユーザーが自由にできる。

## 4. 機能仕様

### 4.1 キャラクター・ウインドウ

#### 4.1.1 キャラ構成（2体だがサブは任意）★
- メインキャラとサブキャラの 2 体構成を基本とする。
- 配置は伺か風: 下端揃えでタスクバーの上に立つ。**既定配置はメインが画面右端・サブがその左隣**（デフォルトシェルは main 256×384 / sub 96×144 でメイン大・サブ小）。
- **キャラはそれぞれ独立してドラッグで X 軸方向にのみ移動できる**（§4.3.4）。Y は作業領域下端（タスクバー上端）で固定。移動範囲はステージ内（＝ステージを置いているモニタの作業領域内）。**キャラをドラッグで別モニタへ移すことはできない**（ステージごと移す = 表示モニタの選択は §4.1.6）。
- **シェル/ゴーストはサブを省略可能**。サブ無しゴーストでは:
  - 画面にメインのみ表示
  - 掛け合いパターンはパターン1（main単独）相当に縮退
  - 撫で/つつきは main のみ
  - 設定 UI の「サブの声」等は無効化または非表示
- データスキーマ（shell.json）と辞書スキーマは「サブが存在しないゴースト」を表現可能にする（Phase 2）。

#### 4.1.2 キャラ画像表示（全 pose プリロード）
- 全 pose の `<img>` を data URL でプリロードし、`visible` クラス切替で表現。
- 切替時のチラつきはほぼゼロを目標。

#### 4.1.3 吹き出し描画 ★
- **吹き出しはキャラクターの左横に表示**(伺か風)。上端をキャラの顔の高さ（キャラ上端 + 高さの 12%）に合わせ、しっぽはキャラ側を向く。main/sub 両表示で重なる場合は main を上・sub を下へ退避。
- キャラが画面左端付近で左横に収まらない場合は**右横に反転表示**（しっぽも反転）。
- **タイプライター描画**（1文字ずつ表示）。
- **描画速度はユーザー設定で可変**（速い / 普通 / 遅い / 一気に表示）。
- main → sub の順に逐次表示、重ならない。
- **掛け合いパターン3/4 では 3 つ目の吹き出しを独立表示**（v0.0.3 の「同じ吹き出しに追記」方式は廃止）。
- 新発話で interrupt（古い音声・描画を打ち切る）。
  - **ただし通知は割り込まない（★v0.5.3）。** 通知は「一度出したら配達済みの記録が残り、
    二度と出ない」ので、消されると**記録だけが残って永久に届かない**。
    実際に起きていたのは、同じ周期で 2 件のカレンダー通知が配達されると後の 1 件が
    前を消すこと、および 80% コスト警告の直後にチャット応答が返ると応答が警告を消すこと。
    - 通知は**キューに入れ、描画中なら空くのを待って 1 件ずつ**出す。
    - 通知の描画中に他の発話が来たら**割り込みは許すが、通知はキューの先頭へ戻す**。
      ユーザーの入力への応答を待たせないため。戻した分は空き次第あらためて出す。
    - 対象は**通知だけ**（`notify()` 経由の system_message と、配達の Notice =
      リマインダー・カレンダー）。状況発話・独り言・定例会話（Ambient）は含めない。
      消えても記録が残らず、また出るので守る必要が無く、含めると操作を待たせるだけになる。
    - **入力促し・メニュー前口上は「ステージを使用中」として扱わない。** これらは
      いつでも出し直せる UI で、一度きりの通知とは性質が違う。ここを待ちにすると、
      入力欄を開いたまま離席したときに通知が滞留する。
- 表示継続時間はセリフ総文字数に比例。
- 全ターンの描画+発話完了後に一括消去。

#### 4.1.4 口パク（振幅駆動のみ）★
- TTS 有効時のみ動作。再生振幅（AnalyserNode RMS）でリアルタイム駆動。
- **TTS 無効時の口パクは無し**（v0.0.3 のタイマー近似を廃止）。
- pose 画像の隣に `<name>_talk.png` があれば開口フレームとして使用。無いシェルは口パクなし。
  - **`shell.json` には書かせない**（Rust 側が pose 画像の隣を自動で探す）。`poses` に混ぜると advanced の LLM に渡る pose 語彙に `normal_talk` 等が入ってしまうため、boot payload では `talk_poses` として分けて送る。
  - 駆動は TTS の本発話のみ。設定画面の音声プレビューでは動かさない（キャラが喋っているわけではないため）。

#### 4.1.5 表示スケール ★
- 設定 UI で 0.5〜2.0 の範囲で可変。
- スケールはキャラ画像のみに適用（ウインドウはステージ方式 §4.1.6 で全幅固定のため連動しない）。拡縮の基準点はキャラの足元左（bottom left）。ステージ高さは上限 2.0 でもデフォルトシェルのキャラの頭が切れないよう確保する（§4.1.6）。
- **要件: 吹き出しのテキスト・フォントサイズはスケールの影響を受けず、視認性を維持する**（v0.0.3 で課題化された問題）。
- 実装方針（Phase 2 で設計）: キャラ画像と吹き出しのレイヤーを分けて scale を別管理、または逆補正。

#### 4.1.6 ステージ（ウインドウ）とキャラ位置の永続化
- ウインドウは**モニタ作業領域の全幅 × 高さ 1024 の透明ステージ**として**作業領域下端に固定**する（＝キャラの足元が常にタスクバー上端に乗る）。高さはデフォルトシェルのキャラを表示スケール上限（§4.1.5、2.0）で拡大しても頭が切れず、その上のバルーン・入力欄まで収まる値。作業領域高さが足りなければその高さでキャップする。**ユーザーがウインドウをドラッグで動かす手段は無い**（表示モニタの切り替えのみ設定から可能。次項）。
- **表示モニタの選択（v0.4）★**: ユーザーは**設定パネルで、ステージを表示するモニタを選べる**。
  - **明示的に選択されたモニタが常に優先**される。選択が無い場合にかぎり、前回終了時の位置から推定する（`window_pos` キー。従来の挙動）。**1 秒間隔の監視は明示選択を上書きしない**。
  - 選択したモニタが見つからない場合は**主モニタへフォールバックする**が、**選択自体は保持する**。
  - **戻る保証の範囲**: OS が返すモニタ識別子は接続順で入れ替わりうるため、「同じ物理モニタに必ず戻る」ことは保証しない。**表示構成が選択時と同じであれば選んだモニタに戻る**。構成が変わっていた場合は主モニタに置き、ユーザーは選び直せる（誤ったモニタに固定されない）。
  - 選択は `monitor_pref` キーに永続化する（識別子の形式は Phase 2 設計。`window_pos`（前回位置）とは別の値）。
  - **DPI が異なるモニタへ移しても正しく表示される**（ステージ高さをそのモニタのスケールで再計算する）。
- モニタ構成・解像度・タスクバー高さ・DPI の変更は 1 秒間隔の監視で検知し、自動で再ドックする。
- **キャラごとの X 位置**（ステージ内 CSS px、視覚ボックス左端）を `char_pos` キーに永続化する。保存はドラッグ終了時（mouseup）に即時。起動時に復元し、ステージ幅に収まるよう clamp。保存が無いキャラは既定配置（§4.1.1）。**モニタを移して幅が変わった場合も新しいステージ幅に clamp する**（モニタごとに別々の X 位置は記憶しない。将来課題 §6.6）。

#### 4.1.7 タスクトレイ ★
- アイコン常駐、左クリックでウインドウ表示/非表示。
- 右クリックでメニュー（**セーフモード項目は除く**）:
  - 表示/非表示
  - モード切替（low / advanced）
  - 静音モード
  - 設定を開く
  - 終了
- メニューのチェック状態は設定変更時に同期。

#### 4.1.8 セーフモード（廃止）★
- v0.0.3 のセーフモード（不透明・枠ありで起動する保険機能）は廃止。
- ウインドウ生成は単一ラベル・単純構造に。

### 4.2 対話

#### 4.2.1 二モード制
- **low モード**: 辞書のみ。API キー不要・無料・オフライン。
- **advanced モード**: LLM 経由で動的生成。
- ユーザーは設定で手動切替可。
- 自動降格条件: API エラー連続 / コスト上限超過 → 一時 low に降格 → 一定時間後に復帰試行。
- **モード境界の再定義（2026-07-12、日常支援 §4.6 の採用に伴う）★**:
  - low = **決定論的・ローカル・即時・低コスト**（辞書会話、定型コマンド、リマインダー、ToDo、ポモドーロ、状況検知と定型通知、カレンダー表示 等）
  - advanced = **解釈・生成・要約・提案**（自由会話、曖昧な指示の解釈、タスク分解・優先順位提案、状況に応じた発話生成、長期記憶の参照 等）
  - **不変条件: LLM が利用不可（未設定・降格・障害）でも、生活支援機能（リマインダー・ToDo・タイマー・カレンダー表示）は常にローカルで動作する。** advanced はこれらの上に「解釈と提案」を上乗せする層であり、基盤機能の前提にしない。

#### 4.2.2 LLM プロバイダ（OpenAI 互換のみ）★
- **OpenAI 互換 API のみサポート**。
- 設定: モデル名 / `base_url`（任意） / API キー（keyring）。
- これにより以下が同じ仕組みで接続可:
  - OpenAI 公式
  - Grok（OpenAI 互換）
  - LM Studio / Ollama（ローカル LLM、OpenAI 互換エンドポイント）
  - その他 OpenAI 互換サーバ
- **Anthropic SDK 専用ルートは廃止**。

#### 4.2.2b キャラクターの人格記述（persona）★

- `ghosts/<id>/ghost.json` にゴースト作者が記述し、**advanced 経路の system prompt に載せる**。
  - `characters.main.persona` / `characters.sub.persona`: 各キャラの人格・口調・一人称。
  - `prompt.max_chars_per_line`: 1 発話あたりの目安文字数。**指示として載せるだけで強制はしない**。
  - `prompt.style_notes`: 掛け合い全体のトーン指示。
- **いずれも省略可**。省略時は役割だけの既定文（「メインキャラ。」等）にフォールバックする。
  第三者ゴーストが書いていなくても壊れない。
- 適用先は **advanced の 3 経路すべて**: チャット応答 / 独り言生成（§4.4.4）/ 定例会話の言い換え（§4.7.1）。
- **プロンプトには「設定文そのものを台詞で説明しない」旨の指示を併記する。**
  これが無いと LLM が人格記述を復唱する（「あたし、好奇心旺盛だから！」）。
- **ここに書かれたものを読むだけで、ugg が人格記述を生成することはない。**
  第三者ゴーストの辞書等から persona を機械生成して LLM に演じさせる導線は
  **§6.4 のレッドライン**で禁止している。
- 背景: v0.4.1 まで `GhostManifest` がこれらのフィールドを宣言しておらず、
  **serde が黙って捨てていた**。実測（2026-09-02、ローカル LLM・8 往復 ×2）では、
  persona 不在だと一人称の一致が main/sub とも 0/8 で、**2 人が区別のつかない同調役に潰れ、
  §4.2.4 の掛け合いが成立していなかった**。v0.5 §6.0 の項目 1 で配線。

#### 4.2.3 辞書スキーマ v3 ★
- v0.0.3 の schema v2 を整理して v3 を新規策定（**v2 からの自動マイグレーションは設けない**、作者に書き直しを求める）。
- 整理方針:
  - セクションを統合・最小化（recall_talk / update_talk 等の使い分けを見直し）
  - events キーの乱立を抑制（推奨命名・部位粒度を C-2 に合わせて簡素化）
  - 横断方針 §3.1 に対応する system 系 events を整理・追加
- スキーマ詳細は Phase 2 で策定。

#### 4.2.4 掛け合いパターン ★
- パターン1: main → sub
- パターン2: sub → main
- パターン3: main → sub → main（**3つ目の吹き出し**で表示）
- パターン4: sub → main → sub（**3つ目の吹き出し**で表示）
- **新パターン: 問いかけパターン**（極低確率発生、ユーザー応答を期待）
  - 例: 「最近どんなことに興味あるの？」「コーヒー派？紅茶派？」
  - ユーザー応答時の処理（user_profile への自動反映、follow-up 発話）は Phase 2 で設計。
  - 応答が来なかった場合のタイムアウト挙動も Phase 2 で設計。
  - **実装（v0.5.1）**: **advanced の掛け合いパターン 5** として実装。構造はパターン1
    （main → sub）と同じで、**内容がユーザーへの問いかけで終わる**点だけが違う。
    ターン数は増やさない。発生確率 5%（残り 95% は従来の重み 50/25/15/10 を保つ）。
    **サブ無しゴーストでも出せる**（main が尋ねるだけなので 2/3/4 の制約が当たらない）。
    質問は 1 つに限る（尋問にしない）。応答は次のターンで LLM が会話として自然に受けるため、
    専用の応答経路は作らない。
    - **そのために直近の会話を注入する（★v0.5.3）。** v0.5.2 まで履歴注入は常に空を返しており、
      「次のターンで自然に受ける」は**成立していなかった**（キャラが尋ねてユーザーが
      「それがいい」と答えても、その「それ」が LLM に渡らない）。v0.5.1 のリリースノートの
      説明も、この前提で書いた誤りだった。
      - **直近 8 往復を上限**に注入する（ユーザー裁定 2026-09-06）。
      - **合計文字数の上限も設け、超えたら古い方から落とす。** 往復数だけで抑えると
        長文 1 往復でプロンプトが膨らみ、コストが跳ねる。
      - **ユーザー発言の直前のキャラ発話は往復の一部として残す。** 問いかけがそこにあるので、
        上限で切り落とすと目的そのものが失われる。
      - キャラの連続発話（掛け合いの 2〜3 行）は**まとめて 1 応答**とし、誰の発言かを
        名前で残す（名前を落とすと 2 人の区別が消え、persona 配線 §4.2.2b が無駄になる）。
      - **チャット経路のみ。** 独り言の補充には渡さない（§4.4.4「独り言は応答ではない」を維持）。
      - **注入するのは advanced の会話行だけ（★v0.5.3、リリース前監査で是正）。**
        チャットログには独り言・リマインダー通知・カレンダー通知・状況発話も入る。
        これらまで送ると **§3.3 / §4.6.4 が定めた送信物の範囲を超える**
        （カレンダーで外部へ出るのは ICS 取得リクエストのみと明記してある）。
        加えて、常駐しているだけでユーザー発言が 1 件も無い窓では往復数の上限が働かず、
        文字数上限いっぱいまで独り言が入ってしまう。
        **往復が 1 つも無いなら何も注入しない。**
        問いかけパターンは advanced の掛け合いパターン 5 なのでこの絞り込みでも残る。
    - 背景: architecture が「辞書の events キー + `probability`」と書いており spec と
      矛盾していた（実装が変わるレベルの食い違い）。**spec を正本として** architecture 側を訂正した。
- サブ無しゴーストではパターン2/3/4 は使えない（自動的にパターン1へ縮退）。
- advanced のみ可変、辞書系は常にパターン1。
- 番号が小さいほど高確率（重み付け）。

#### 4.2.5 長期記憶（user_profile）★
- ユーザーの情報を保存。LLM 呼び出しの system prompt に注入。
- 設定パネルで閲覧・追加・削除。
- オンボーディングで nickname / 興味 / 話し方 / 時事ネタ ON/OFF を聞き取り → 自動投入。
- **新機能: 会話からの自動抽出**（advanced のみ）
  - LLM 呼び出し時に「記憶すべきサマリ」を副産物として抽出
  - user_profile に自動保存
  - 抽出ロジック・トリガー条件は Phase 2 で設計
- **容量管理**: 件数/文字数の上限・古いものの自動破棄/要約を Phase 2 で設計。

#### 4.2.6 会話の自動要約（記憶に統合）★
- v0.0.3 の `context_summaries` テーブルは廃止。
- 過去会話の要約は §4.2.5 の user_profile 自動抽出に統合する。
- 辞書 `recall` のトリガーも user_profile から派生。**トリガー語（`source_keywords`）はユーザーが入力した語からのみ作る（v0.5.1）**: アプリが組み立てた定型文（「ユーザーの呼び名は…」「話し方の希望: …」「興味のあること: …」）ごと渡すと、「ユーザー」「希望」「興味」といった汎用語が想起のトリガーになり、**低負荷モードの通常応答を無関係な入力まで奪う**。
  - **自動抽出（advanced）にも同じ規則を適用する（★v0.5.3）。** 記憶の本文は LLM が書いた要約文なので、そこから語を採ると LLM の言葉づかいがトリガーになる。v0.5.1 で塞いだのはオンボーディングの定型文だけで、自動抽出経路には同じ穴が残っていた。**ユーザー入力から拾った語のうち、記憶本文にも現れるものだけ**を採る。言い換えられて一致しなければトリガーを作らない（**誤爆より不発を選ぶ**。誤爆は毎回 low の応答を奪うが、不発は静かなだけ）。

#### 4.2.7 コスト管理 ★
- LLM 呼び出しのコストを `api_usage` テーブルに記録。
- 月額上限 `monthly_limit_usd` を設定。
- **80% 到達時に警告**:
  - トースト + **ゴースト発話**（横断方針 §3.1）
  - 辞書 `system_messages` に対応キーを追加（例: `cost_warning_80`）
- **上限超過時に自動降格**:
  - low モードへ降格
  - **ゴースト発話**で通知（黙って降格しない）
- 次月リセットで復帰。
  - 判定は **LLM 呼び出しの前**に行う単一のゲートとし、chat / 独り言補充 /
    定例会話の言い換えの 3 経路すべてが通る。降格タイマー（API エラー由来）で
    解除してはならない。
  - 告知済みかどうかは **当月タグを `app_settings` に永続化**して判定する
    （プロセス内フラグでは再起動で消え、月が替わっても戻らない）。
  - **集計できないときは止める（★v0.5.3、fail-closed）。** 上限が有限なら、
    当月コストを集計できない間は LLM を呼ばない。v0.5.2 まではここを通していた
    （「集計できないときに課金を止めるのは過剰」）が、v0.5.2 で**破損 DB でも
    起動を続ける**ようにしたことで集計失敗が現実の経路になり、**上限を設定して
    いるのに無制限に課金される**組み合わせが生まれた。上限が有限であることは
    ユーザーが「ここまで」と言っているということなので、守れないなら使わない。
    - **黙って low に落ちない。** 「上限に達した」とは別の告知として、
      集計できないから止めている旨をゴーストが伝える（辞書 `cost_unknown`）。
    - 告知は**プロセスごとに 1 回**。この場合の告知済みフラグは永続化しない
      （記録先の `app_settings` 自体が同時に失敗しうるため。月次の予算ではなく
      「いま壊れているか」の話なので、セッション単位で足りる）。
    - 上限 0（無制限）のときは止めない。守るべき上限が無いのに機能を落とすのは
      ただの機能低下になるため。
- ローカル LLM 利用時は記録のみ（料金は 0）。
- **当月の利用状況を設定画面（AI・拡張）に表示する**: 利用額 / 上限 / 比率。
  `get_cost_status` コマンドで取得する。
  - **料金表に無いモデルはコスト 0 で記録され、上限が発動しない。**
    ローカル LLM なら 0 が正しいので、`llm_base_url` がローカルを指していない
    場合のみ「料金を計算できないため上限は機能しない」と警告する。

#### 4.2.8 API キー管理
- keyring に保存（`service = "ugg"`, `user = provider 名` 等）。
- 設定パネルで登録（伏せ字表示）、「保存済み」状態を表示。
- 1 プロバイダ 1 キー。

### 4.3 ユーザー操作

#### 4.3.1 クリック種別の判別と入力導線 ★
- 最後のクリックから 250ms 待って確定:
  - 1 回 → **入力導線**（下記）
  - 2-3 回 → つつき反応
  - 4 回以上 → 連打反応
- mousedown 後の移動 4px 超でドラッグ扱い（クリック判別を抜けてキャラ移動 §4.3.4 へ）。
- **入力導線**: クリックされたキャラが「なにか用かな？」のような**入力促しの反応**（辞書 `input_prompt`、そのキャラ単独の短い発話。TTS 対象・chat_log 記録あり）を返し、**チャット入力欄をそのキャラのバルーンの上側に表示**する。
  - 促しの吹き出しは通常の表示時間で消さず、**入力欄が閉じるまで保持**する。
  - 入力欄が開いている状態での 1 クリック・Esc は入力欄と促し吹き出しを閉じる。送信時・新しい発話でも促しは置き換わる。
  - キャラ以外（吹き出し・透明部分）のクリックは main の導線として扱う。**ただしパネル・バッジ・入力欄などの UI 要素上のクリックは導線・つつきの対象外**（その UI の操作を優先する）。辞書に `input_prompt` が無いゴーストでは促し無しで入力欄だけ開く。
  - 入力欄の配置はバルーンと同じ幾何に従う（キャラ左横基準、画面左端付近では右横へ反転、キャラのドラッグに追従）。

#### 4.3.2 つつき部位判定（縦のみ）★
- 縦 3 区分: head / chest / body（**横判定は廃止**）。
- shell.json で `poke_regions.head_max` / `chest_max` を指定（横の `left_max` / `right_min` は廃止）。
- 辞書 events 探索順: `poke_<t>_<v>` → `poke_<t>`。

#### 4.3.3 撫で（ホバー往復判定）
- ボタン無しでキャラ上を往復するホバージェスチャを検知。
- 判定指標の合わせ技: 方向反転回数 ≥2 / 累積移動量 / 局所性 / 最低継続時間 / cooldown。
- 部位判定は §4.3.2 と同じ（縦のみ）。
- **パネル (設定・読み上げ・チャットログ・確認・オンボーディング) 表示中は無効**。
  パネル操作でカーソルが背後のキャラ上を往復して誤発話するため。

#### 4.3.4 ドラッグでキャラ移動（キャラ単位・X 軸のみ）★
- mousedown したキャラ（部位判定と同じヒットテスト）だけを動かす。**main / sub は独立して移動**。
- 移動は **X 軸方向のみ**。Y はステージ下端（タスクバー上端）に固定（伺かと同仕様）。
- mousedown 後 4px 超でドラッグ開始。移動範囲はステージ（モニタ作業領域）内に clamp。
- ドラッグ終了（mouseup）で位置を即時保存（§4.1.6）。
- 吹き出し表示中はキャラに追従する。
- キャラ以外（吹き出し・透明部）のドラッグでは何も動かさない。`data-tauri-drag-region` は使わない。

#### 4.3.5 右クリック → バルーンメニュー ★
- 独立したコンテキストメニュー UI は廃止し、**メニューはメインキャラのバルーン内に表示**する（伺か風）。
- **メインを右クリック**: メインが前口上（辞書 `menu_prompt.main`、例「なにか用かな？」。TTS 対象・chat_log 記録）を発話し、**続けて同じバルーン内に**メニュー項目を表示する。
- **サブを右クリック**: サブが誘導セリフ（辞書 `menu_prompt.sub`、例「用事ならメインに頼んでくれ」）を自分の吹き出しで発話した後、メイン右クリックと同じ挙動に遷移する（サブの吹き出しは表示したまま）。
- 項目（実装準拠）: モード切替（low ⇔ advanced）/ 静音モード切替 / 予定・ToDo（§4.6.1 / §4.6.2、専用パネルを開く）/ ポモドーロタイマー（§4.4.5、専用パネルを開く）/ テキスト読み上げ / 設定を開く / ウインドウを隠す / 終了（トレイの「終了」と同じ経路。§4.4.2）。ゴースト/シェル切替は設定パネルから行う。
- 閉じる: 項目実行・Esc・メニュー外クリック。新しい発話（自発発話等）でも置き換わる。メニュー表示中の左クリックは「閉じる」専用（入力導線 §4.3.1 やつつきには流さない）。
- キャラ以外の右クリックは何もしない（WebView 既定メニューの抑止のみ）。
- 辞書に `menu_prompt` が無いゴーストでは、セリフ無しでメニューのみ表示（サブ右クリックは直接メインのメニューへ）。

### 4.4 存在感系イベント

#### 4.4.1 起動挨拶
- 初回 = `events.first_boot`（オンボーディング兼）。
- 2 回目以降 = `events.boot`（時間帯条件 / 日付条件で分岐）。
- 静音モードでも起動挨拶は鳴らす。

#### 4.4.2 終了挨拶
- **トレイと右クリックメニューの「終了」は同じ経路**（v0.5.6。以前はメニューの「終了」があいさつも終了前の確認も無く
  即座に終わっていた）。
- **見えていれば**、今日の未完了 ToDo の確認（§4.6.2、`events.todo_quit`）か `events.quit` を再生してから exit。
- **隠している・最小化しているときは、すぐ exit**（見えない間は届いていない扱い。§4.6.1 と同じ）。隠していても音は
  鳴っていたが、そのあいさつは無くなってよい（2026-09-24 ユーザー裁定）。
- 待ち時間は台詞の文字数からの推定（最長 8.5 秒。合成の完了は待たないので、Irodori では台詞が切れうる）。待っている間に
  **もう一度「終了」を押すと、すぐ exit**。
- 強制終了（Alt+F4 でウインドウを閉じる場合を含む）では当然鳴らない。

#### 4.4.3 放置反応
- 60 秒間隔チェック、最終操作から 30 分で 1 回 idle 発火。
- 静音中・busy 中は持ち越し。
- ユーザー操作でリセット。

#### 4.4.4 ランダムトーク（独り言）★
- 一定間隔でキャラが独り言を発話。
- **既定間隔: 10 分**（v0.0.3 の既定 0=無効から変更）。
- 0 設定で無効化可能。
- advanced モードでは LLM 生成 + キャッシュ補充。
  - 発話のたびに LLM を呼ばず、**まとめて複数ストックし、キャッシュが尽きたら補充**する（LLM 呼び出し頻度を独り言の発話頻度より低く保つ）。ストックは**再起動をまたいで保持**する（起動のたびに補充が走らないこと）。
  - 補充時、時事ネタ（§4.4.6）が有効なら**その材料を一緒に渡して織り込む**（有効でなければ独り言のみ。追加の LLM 呼び出しはしない）。
  - **ストックした文にも生成時刻を持たせ、発話時に鮮度を判定する**（時事ネタを含む文の失効は §4.4.6）。
  - コスト管理は advanced 会話と同じ扱い（月額上限・自動降格に従う）。降格中・LLM 障害時は low と同じ辞書経路にフォールバックする（本節の low 側の挙動と同じ）。
  - **履歴クリア（§4.5.5）の対象**に含める。
- low モードでは辞書 `monologue` から選択。
- 静音条件下では発火しない。

#### 4.4.5 ポモドーロ ★
- 集中(work) → 休憩(break) をラウンド数だけ繰り返す。
- 既定 25 分 / 5 分 / 4 回（設定変更可）。
- 集中中は静音扱い（ランダムトーク・放置反応を止める）。一時停止中も静音扱いを維持。
- 辞書 events: `focus_start` / `focus_end` / `break_end` / `pomodoro_done`。
- **focus_end / pomodoro_done では「ねぎらいの台詞」を充実**させる（辞書側で台詞バリエーション拡充）。
- バッジ表示（画面上部中央、`.solid`）。進行状況（フェーズ・残り時間・ラウンド）を常時表示。一時停止中はその旨を示す。
- **専用 GUI パネル（`.solid`、アプリ内オーバーレイ。独立ウインドウは作らない）から操作する**:
  - **開始**: idle 時にタイマー開始。
  - **停止（一時停止 / 再開）**: 進行中のカウントダウンを一時停止し、再度押すと同じ残り時間から再開する（**新設**。従来の「レジューム無し」から変更）。
  - **中断**: タイマーを破棄して idle に戻す（従来の stop 相当）。
  - **閉じる**: パネルを閉じる。タイマーが動作中なら継続し、バッジで表示する。
  - **時間設定**: 集中/休憩/ラウンド数をパネルで編集。値は既定設定（`pomodoro_work_min` / `pomodoro_break_min` / `pomodoro_rounds`）と共有し保存される（設定パネルと同一の値）。進行中は編集不可（次の開始時に反映）。
- **右クリックメニューは「ポモドーロタイマー」1 項目**でこのパネルを開く（従来の「開始」「停止」直接項目は廃止）。トレイからの制御は現状維持。

#### 4.4.6 時事ネタ雑談
- RSS（既定 Google ニュース検索）から興味分野の見出しを取得。
- **advanced モードの独り言生成のついで**に織り込む（追加 LLM コストなし。§4.4.4 のキャッシュ補充に相乗りする）。
- **賞味期限は 1 週間**。時事ネタは鮮度が価値なので、次の 2 点で担保する:
  - **織り込み時**: 取得から 7 日を超えた見出しは材料に使わない。
  - **発話時**: 独り言のストックは補充から時間が空いて発話されうるため（§4.4.4）、**発話の時点で見出しが取得から 7 日を超えていたらその文を使わず、辞書の独り言に差し替える**。古いネタを口に出さないことを優先する。
- 暗い見出し（事故・災害等）をフィルタ。
- low モードでは時事ネタ無し。
- 取得間隔は 30 分以上にクランプ。
- 興味分野は `interest_topics` テーブル（user_profile との統合は Phase 2 検討）。
- **既定オフ**・オンボーディングで明示同意必須。

#### 4.4.7 更新通知
- `update_feed_url` の JSON を起動時に取得。
- 現バージョンより新しければ辞書 `system_messages.update_available` で**一度だけ**ゴーストが通知。
- 既定オフ（フィード URL 未設定なら無効）。
- **★v0.5.7 Irodori のランタイムの更新**: Irodori を導入済みで、更新の対象があれば、辞書
  `irodori_update_available` で知らせる（設定パネルを開かなくても分かるように）。起動 30 秒後と 24 時間ごとに確かめ、
  更新の錠が握られている間は確かめない。**更新の対象の組ごとに 1 回**、届いたときだけ済みにする（§6.0 項目 7）。

#### 4.4.8 静音モード
- `quiet_mode` 設定 ON で自発的な発話を停止。
- ユーザー操作への応答は通常通り。
- 起動挨拶・終了挨拶は静音下でも鳴る。
- トレイ・右クリックメニューから切替。

#### 4.4.9 フルスクリーンアプリ自動静音 ★
- `auto_quiet_fullscreen` 設定 ON で、フォアグラウンドウインドウがモニタ全面なら自動静音扱い。
- ゲーム・プレゼン・動画視聴中は黙る。
- Win32 API で検知、デスクトップシェル（Progman/WorkerW）は除外。
- **既定 OFF**（v0.0.3 の既定 ON から変更、ユーザーが明示的に ON）。

### 4.5 音声・補助

#### 4.5.1 TTS ★
- **2 エンジン体制**:
  - **voicevox_core**（既定、必須）: 公式プリビルド C API を libloading で実行時ロード。CPU合成・無サーバ。
  - **Irodori-TTS**（オプション、上級）: サイドカー同梱、GPU必須、不安定許容。
- **共通動作**:
  - 「ユーザーが別途サーバー/アプリを起動する必要はない」を両方とも満たす。
  - 失敗時は声なしで会話継続（アプリは落ちない）。
  - 全発話経路（応答・独り言・つつき・撫で・挨拶・時事ネタ・リマインダー）に乗る。
- **voicevox_core 詳細**:
  - 資産（dll / onnxruntime / Open JTalk 辞書 / .vvm）は **初回 DL** で取得
  - 規約同意必須、GitHub PAT で API レート制限緩和（任意）
  - クレジット表示「VOICEVOX:話者名」を画面下端中央に常時表示（VVM 規約準拠）
  - 事前 init（boot 時・設定変更時）で初回発話のラグを解消
- **Irodori-TTS 詳細**:
  - Python + PyTorch + CUDA + モデルをサイドカー同梱方式で配布
  - **初回 DL 方式**（軽量インストーラ → 設定で有効化時に 5〜10GB DL）
  - GPU 検出失敗時は voicevox_core にフォールバック + ユーザーに通知
  - **★v0.5.7 使えない理由を言い分ける**（§6.0 項目 7）: 更新中（`irodori_updating`）／モデルが揃っていない
    （`irodori_model_missing`。設定の「更新する」で直る）／GPU が見えない（`irodori_no_gpu`）／VRAM が足りない
    （`irodori_vram`。ほかに GPU を使うアプリを止めれば戻る）／そのほか（`irodori_unavailable`）。以前は理由によらず
    「GPU 環境が整っていない」と言っていた
  - **参照音声クローン方式**（声質の一貫性を確保）
    - 参照音声がある場合: 保存済み参照音声でクローン合成
    - 参照音声が無い場合: キャプション（VoiceDesign）から参照音声を生成 → 保存 → 以降はクローン合成へ切替
    - 参照音声の供給源は**自前生成のみ**（外部音声の取り込みは行わない＝著作権リスク回避）
    - 参照音声の再生成（キャプション変更で作り直し）・削除 UX は Phase 2 で設計
  - **合成のステップ数**（★v0.5.7、設定 `tts_irodori_steps`）: 8（速さ優先）/ 16（標準・既定）/ 40（品質優先）から選ぶ。
    多いほど品質が上がり時間がかかる。**v4.1 のモデルのときだけ効き**、v3 で喋っている間（更新前・失敗して戻った後・
    保留中）は v0.5.6 の sway 8 のまま。参照音声の生成には効かない（40 固定）。変えたら次の発話から効く（§6.0 項目 4）
  - **漢字→ひらがな前処理**: Irodori-TTS は漢字の発話精度が不安定なため、合成前にテキストをひらがなに変換する前処理を入れる
    - 変換手段の候補: voicevox_core が同梱する Open JTalk 辞書の流用 / 形態素解析ベース（Phase 2 で選定）
    - 変換漏れ・誤読は許容（完全な読み付与は目指さない）
    - voicevox_core エンジン側ではこの前処理は不要（内部で読み解析を行うため）
  - **絵文字アノテーションの保護**: Irodori-TTS V3 は入力テキスト中の特定絵文字（45 種、upstream `EMOJI_ANNOTATIONS.md` 準拠）で感情・スタイル・効果音を制御できる。前処理はこれらの絵文字を除去せず、位置を保ったまま合成テキストに残す
    - 対応絵文字は upstream の一覧をホワイトリストとして保持（対応外の絵文字は従来通り前処理で落ちる）
    - 同一絵文字の連続（強調）も保持する
    - voicevox_core エンジン側では絵文字は解釈されないため保護しない（従来通り読み飛ばし）
  - **詳細実装は Phase 2 で**: Python ランタイム配布方式 / モデル配布 / サイドカープロセス管理 / GPU 検出 / 参照音声管理（生成・保存・再生成・削除） / **漢字→ひらがな前処理の実装方式** / 設定UI
- 設定:
  - エンジン選択（VOICEVOX / Irodori-TTS）
  - 話者選択（メイン / サブ）
  - 話速・音量
  - Irodori-TTS のキャプション入力（参照音声の初回生成・再生成に使用）
  - Irodori-TTS の参照音声管理（生成・再生成・削除）
  - 規約同意・GitHub PAT（voicevox_core 用）
- 共通の再生制御:
  - 逐次キュー（main → sub が重ならない）
  - 新発話で interrupt
    - **中断は非同期処理を跨いで効かせる（★v0.5.3）。** 合成・デコードなど待ちを
      含む処理の**あとに毎回**世代を確認し、失効していたら音も口パクも始めない。
      v0.5.2 までは合成後にしか確認しておらず、**デコード中に停止すると
      「停止したあとに喋り出す」**（その時点では再生元がまだ無いので、停止処理の
      対象にもならない）。台本読み上げ側は同じ位置で確認していたので、
      チャット発話側だけが抜けていた。
  - WebView2 自動再生ポリシー対策（`--autoplay-policy=no-user-gesture-required`）★v0.5.1 実装
    - **`additionalBrowserArgs` は wry の既定引数を「追加」ではなく「置換」する。**
      既定は `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection` に
      `--autoplay-policy=no-user-gesture-required`（autoplay 既定 true のため）を足したもの。
      **自動再生ポリシー自体は既定で既に効いていた**ので、ここに自前の値を書くときは
      既定の `--disable-features=...` も必ず併記する（併記を怠ると、得るものが無いまま
      ミニメニュー・SmartScreen の抑止だけを失う）。
    - 併せて `ensureAudioCtx` で `AudioContext.state === "suspended"` なら `resume()` を
      試みる（**待たない**。待つと発話が遅れるうえ、失敗時に無音なのは変わらない）。
      これが無いと `start()` は例外も投げず Promise も解決するため、
      **正常に喋ったように見えて音だけ出ない**。

#### 4.5.5 データエクスポート / 履歴クリア
- **エクスポートの対象（v0.5.1）**: 再生成できるキャッシュ 3 つ（`calendar_cache` / `topics_cache` / `monologue_cache`）を除く**全テーブル**。v0.4.1 まで 12 テーブル中 3 つしか出しておらず、**リマインダー・ToDo・設定が持ち出せなかった**。schema は `ugg-export-v2`。 **★v0.5.3: 部分救出**。テーブルの読み取りに失敗しても**そこで打ち切らず、読めた分を書き出す**。失敗したテーブルは名前と理由を `failed_tables` に並べ、該当テーブルの値は `null` にする（`include_profile=false` による `user_profile: null` とは意味が違うので、区別は `failed_tables` で行う）。**破損を検知したらまず export で控えるよう案内している以上、必要な場面でだけ失敗する実装は通らない。** schema は `ugg-export-v3`。 **★v0.5.7: 読めなかったものを画面に出す**。戻り値を保存先と読めなかったテーブルの組にし、1 つでもあれば画面に「読み出せなかったもの」を取説と同じ呼び方で並べ、「このファイルには入っていません。元のデータは消さないでください」と添えて、成功と同じ見た目にしない（以前はファイルにしか載らず、画面は「保存しました」だけだった）。
- **DB の整合性検査（v0.5.1）**: 起動時に `PRAGMA quick_check` を 1 回行う。
  - **破損していても DB は作り直さない。** 作り直すとリマインダー・ToDo・記憶・設定が一緒に消えるため。起動も止めない（起動できないよりデータを取り出せるほうがよい）。
    - **起動を止めないとは「マイグレーションが失敗しても続行する」ということ**（★v0.5.2）。破損 DB では `db_schema_version` の書き込み自体が失敗するため、ここを致命扱いにすると整合性検査を非致命に作っても意味がない（v0.5.1 は実際に setup フックが panic して起動しなかった）。**健全な DB でのマイグレーション失敗は従来どおり致命**とし、破損が検知されている場合だけ続行する。
    - **同じ理由で、整合性検査は `journal_mode` / `foreign_keys` の設定より前に行う**（★v0.5.3）。v0.5.2 まで `journal_mode=WAL` が検査より前にあり致命扱いだったため、**ヘッダやスキーマページが壊れていると検知にも保全にも起動継続にも到達しなかった**。あわせて `journal_mode` の変更は DB ファイル自体を書き換えるので、**退避を取る前に原本へ書いていた**ことにもなる。pragma の失敗は健全な DB でのみ致命とする。
  - 破損時は ① 原本のタイムスタンプ付きコピー（**`-wal` / `-shm` サイドカーも同じ規則で運ぶ**。これが無いと、本体へまだチェックポイントされていない書き込みが退避から丸ごと抜ける。実機では `-wal` が本体より大きいことがある）② `VACUUM INTO` による救出コピー（読み出せた分のみ。開いている接続を通すので WAL の内容も入る。失敗しても続行）を作り、設定 →「システム」→「データ管理」に検知内容と退避先を表示する。どう復旧するかはユーザーが決める。
  - **保全は破損 1 件につき 1 回だけ。** 既に退避があればそれを指し、作り直さない。毎起動コピーすると、破損した DB を抱えたまま使い続けるユーザー（＝この機能が対象にしている人）のディスクを起動のたびに食い潰す。先に作られた世代のほうが原本に近いので、古いものを残す。
  - **救出コピーの作成に失敗したら残骸を残さない**（★v0.5.2）。`VACUUM INTO` は失敗しても 0 バイトのファイルを残すことがあり、放置すると次回起動で「救出済み」と誤認して二度と再試行しない（「1 回だけ」のガードが失敗を成功として固定してしまう）。
  - **既存の退避・救出コピーを名前だけで採用しない**（★v0.5.3）。救出コピーは「読める DB であること」が存在意義なので、**空でないことと `quick_check` が通ることまで確認**する。原本の退避コピーは壊れた DB のバイト列コピーなので中身の健全性は要求せず、空でないことだけを見る。v0.5.2 までは名前だけで採用しており、**v0.5.1 が残した 0 バイトの `salvaged-*.db` を「救出済み」と誤認して二度と再試行しなかった**（更新経路でのみ踏む）。
  - 正常時は何も表示せず、コピーも作らない。
- **エクスポート**: 会話ログ・記憶（任意）・コスト履歴を JSON でダウンロードフォルダに書き出し。
- **履歴クリア**: 会話ログ・独り言キャッシュを削除。記憶を含めるかはオプション。
- 設定パネルから手動実行。

#### 4.5.6 ゴースト・シェル切替 ★
- **ゴースト切替時のシェル追従（v0.5.1）**: ゴーストを切り替えたとき、そのゴーストの `ghost.json` が `default_shell` を宣言していればシェルもそこへ追従する。
  - **同じ操作でユーザーがシェルも明示的に変えた場合は、ユーザーの選択を優先する**（設定画面はゴーストとシェルを同時に保存するため）。
  - 宣言が無い / 実体のシェルが存在しない場合は追従しない（切替先が無いと起動できなくなるため）。
  - 背景: v0.4.1 まで `default_shell` は出荷されているのに読まれておらず、DnD で入れたゴーストが自前シェルを連れてこなかった。
  - **追従した結果を設定フォームへ戻す（★v0.5.3）。** 保存後にフォームへ書き戻す処理がゴースト・シェルの select だけを対象外にしており、パネルを開いたまま再保存すると**追従が黙って取り消されていた**（フォームが古い id を送り返すため）。「保存済みの値をフォームへ戻す」対象からゴースト・シェルを外さない。
- 設定パネルで複数のゴースト・シェルから選択切替。
- **ホットリロード（ファイル編集の即時反映）は廃止**。作者は再起動して確認する。
- **検討: ドラッグ&ドロップ展開**
  - ゴースト/シェルの zip ファイルやフォルダをアプリにドロップ
  - 自動的に `ghosts/<id>/` or `shells/<id>/` に展開
  - 「再起動して使えるようにする」を明示提示
  - 実装可否・対応形式は Phase 2 で決定（zip 中身検証・上書き確認 UX 含む）
- **導入は非破壊で行う（★v0.5.3）**
  - **別ディレクトリで展開・検証を終えてから差し替える。** 上書き承認後に既存を先に削除してから展開すると、禁止拡張子・zip 破損・容量不足などで失敗したときに**使えていた旧版まで失われる**。悪意ある入力を必要としない、通常の更新操作の問題だった。
  - 旧版は削除ではなく**待避してから**入れ替え、入れ替えに失敗したら戻す。**戻せなかった場合は待避先を消さず、場所をログに残す**（自動で消すと、まさに守ろうとしたデータを失う）。
  - 作業ディレクトリと待避先は `ghosts/` `shells/` の**外**に置く（有効な manifest を持つディレクトリが資産一覧に現れないようにするため）。
  - **確認に使う manifest と、展開に使う manifest は同じ規則で選ぶ**（最も浅いもの。同じ深さならエントリ順で先のもの）。v0.5.2 までは確認が「最初に一致」・展開が「最も浅い」で、複数 manifest を含む zip で**確認ダイアログに出した id と実際の中身が食い違いえた**。差し替え前に展開結果の id を再確認する。

#### 4.5.8 テキスト読み上げツール（詳細: docs/text-reader-spec.md、台本形式: docs/script-reader-spec.md）

- 読み上げ中は自発発話を抑制（`set_reading_active` コマンド → 静音判定に追加）。
  リマインダーの静音特例は従来通り。停止ボタン / パネルクローズで即停止。
- 追加コマンド: `reader_load_text(path) -> Vec<ReadingChunk>` / `set_reading_active(active)`。
  `synthesize_voice` に `caption: Option<String>` を追加（Irodori 実モデル経路のみ使用。**★v3 本体では音声に反映されない**。v0.5.7 で乗り換える v4.1-Small では反映される — §6.0 の spike で確認）。
- **台本形式対応**: `.md` 台本（`speakers` / `lines` ブロック必須 + `defaults` 任意）も
  受理する。話者 ID を ugg の slot（main / sub）へマッピングし、行ごとに話者を切り替える。
  行ごとの `speed`（再生側 playbackRate に合成）、`caption`（声質・演技指示。Irodori 実モデル
  時のみ有効、無効環境ではパネルに注記を表示して読み上げ。**★v3 本体の checkpoint は caption を条件付けに使わないため、
  現行は実モデルでも音声に反映されない**。v0.5.7 で乗り換える v4.1-Small では反映される — §6.0）、`pause_after`（行間の間）を制御。
  不正な台本はロード時に全行検証して fail-fast（部分再生しない）。詳細は docs/script-reader-spec.md 参照。

#### 4.6.1 統合リマインダー ★

  **アプリ内トースト**（§3.1 のフォールバック）。
  - **OS 通知（Windows トースト）は現状の実装範囲外**。フォールバックはアプリ内の帯であり、

    保留は 10 秒ごとに再試行され、2 件以上溜まったら「『X』ほか N-1 件」に集約して 1 発話にする
    （起動時の取りこぼし回収と同じ扱い）。
  - 可視性は**到達判定**であってガバナンスではないため、`can_deliver` には段を足さない。
- advanced 上乗せ: 曖昧表現の解釈（「夕方になったら薬局」）、会話中の予定からの登録提案、通知文の生成、未完了の再通知判断。
- 登録導線はチャット入力欄の自然文（現行踏襲）。一覧・完了・削除・スヌーズの管理 UI は `.solid` パネル方式（ポモドーロパネル §4.4.5 と同型）を想定、配置は Phase 2。
- データスキーマ（既存 `reminders` テーブルの拡張 or 新テーブル）・コマンド契約は Phase 2。

#### 4.6.2 ToDo・日課管理 ★
- **期限が厳密でない作業**を管理する（厳密な時刻を持つものはリマインダー §4.6.1 の領分）。
- low:
  - 追加・完了・削除
  - 分類は **今日 / 今週 / いつか** の 3 区分のみ
  - **繰り返しタスク（日課）**: 完了しても翌日（翌週）に復活する
  - 優先度は **高 / 普通 の 2 段階のみ**
  - 未完了件数の表示（表示位置・形式は Phase 2）
  - 起動時の確認（発話ガバナンス §4.6.3 に従う）・終了前の確認（「終了」の操作への応答なので**ゲートは通さない**。
    静音中も出す — §4.4.8 の終了挨拶と同じ。見えていないときは出さずに終了する。§4.4.2）
- **キャラクター関与が本体**（一覧 UI は従属）:
  - 朝: 件数の告知（「今日は 3 件あるよ」）
  - 長時間未完了: **責めない**催促（サブ主体、頻度はガバナンス管理）
  - 完了時: 労いの反応
  - 複数日滞留: 再整理の提案
  - 対応する辞書 events キーを新設（命名・種類は Phase 2）
- advanced 上乗せ: 会話からの ToDo 抽出提案、タスク分割、優先順位・「今から何をすべきか」の提案、実行可能な量への絞り込み。
- **非採用（過剰 PM 化の防止）**: サブタスク階層・プロジェクト・タグ・工数管理。

#### 4.6.3 状況対応型自発発話と発話ガバナンス ★
- 現行の時間間隔ベースの自発発話（§4.4.3 放置反応・§4.4.4 独り言）に、**ユーザーの状況に反応する発話カテゴリ**を追加する（既存の置換ではない）。
- low の判定材料（**すべてローカルで完結**。ウインドウ内容・キー入力・スクリーン内容は見ない）:
  - 現在時刻 / PC 連続利用時間 / アイドル時間（既存基盤）
  - フルスクリーンアプリの有無（既存 §4.4.9）
  - バッテリー残量 / 音量・ミュート状態
  - ポモドーロ状態（既存）/ リマインダー・ToDo の状態（§4.6.1 / §4.6.2）
- 発話カテゴリの例: 休憩促し（連続利用）・深夜利用の声かけ・バッテリー低下・未完了フォロー。**提案 #10「PC 利用時間・休憩支援」は独立機能とせず本カテゴリに統合**。医療的判断・診断はしない。
- **発話ガバナンス（本機能の前提条件であり、後付けにしない）**:
  - **カテゴリごとのオン / オフ**（新カテゴリの既定は控えめ = 原則 OFF。既定値の確定は Phase 2）
  - **全体の最低発話間隔**
  - **夜間静音（時間帯指定）**
  - 既存の抑制系と統合: フルスクリーン自動静音（§4.4.9）・静音モード（§4.4.8）・ポモドーロ集中・読み上げ中
  - **フィードバック**: 「いまのは邪魔」をワンアクションで伝えられ、該当カテゴリの頻度が自動で下がる
- advanced 上乗せ: 直前の会話・最近の作業傾向の考慮、発話必要性の判断、同内容の繰り返し回避、キャラ別の言い回し生成。**ただし発話可否の最終ゲートは常に low 側のガバナンスが握る**（LLM 判断でガバナンスを越えて喋らせない）。

#### 4.6.4 カレンダー参照（読み取り専用）★
- **ICS（ファイル / URL）の読み込みのみ**。書き込み・双方向同期・OAuth 認証は非採用（将来課題 §6.6）。
- low:
  - ICS 取得とローカルキャッシュ（オフライン時はキャッシュを表示）
  - 今日・明日の予定表示
  - **開始 N 分前のゴースト通知**（既定 15 分、変更可）と終日予定の通知

  告知し（`calendar_fetch_failed`）、成功したら戻す（次にまた失敗し始めたらまた告知する）。届いたときだけ済みにする
  （隠している間の失敗は、見えたときに出る。§3.1・v0.5.6 項目 6）。消した・書き直した取得元の失敗は告知しない。

- advanced 上乗せ: 「今日の予定は？」「次の予定まで何分？」への応答。空き時間の抽出・ToDo の予定割当提案は将来（§6.2 以降）。
- Tier A「朝・夜の定例会話」（§4.7.1）の主要材料になる前提で設計する。

### 4.7 定例会話と天気・生活情報（v0.3 スコープ・**実装済み** 2026-07-24）★

2026-07-18 のスコープ選定（ユーザー裁定）で Tier A（§6.2）から採用した第 2 弾。**「1 日の始まりと終わりに、キャラクターがその日の情報をまとめて話しかけてくる」同居感の完成形**。Tier S（§4.6）のデータ（予定・ToDo・未完了）と本節の天気を材料にする。実装設計（API 選定・DB・モジュール・マイルストーン）は **Phase 2 設計書（regular-talk-design.md として新設予定）**を正とする。§4.6 の横断原則（AI 非依存 / キャラクターが配達する / 邪魔をしない = 発話ガバナンス §4.6.3 準拠）は本節にもそのまま適用する。

#### 4.7.1 朝・夜の定例会話 ★
- **朝と夜の 1 日 2 枠**、それぞれ独立に有効/無効・時刻・有効曜日をユーザー設定できる（既定: **両方オフ**のオプトイン。有効化時の既定時刻は朝 8:00 / 夜 21:00、曜日は毎日）。
- **発火規則**: 「設定時刻きっかり」ではなく、**設定時刻を過ぎて最初にユーザーが PC を使っているとき**に 1 回配達する（朝 8:00 に PC が点いていない日常を許容する）。「使っている」の基準は **OS 全体の入力アイドル**（§4.6.3 の連続利用検知と同系統）が閾値未満であることとし、**連続利用中でも設定時刻経過後の最初の判定で発火する**（アイドル→アクティブの遷移待ちではない。閾値は Phase 2）。ただし**設定時刻から一定時間で当日分は失効**する（既定 6 時間・確定値は Phase 2 設計書。終日 PC を触らず夜に開いた日に朝の定例が夜間へずれ込んで配達される「夜の『おはよう』」と、朝・夜の連続配達を避ける）。1 枠 1 日 1 回。日付が変わったら未配達分は消化（翌朝に昨日の朝の分を言わない）。
- **中身（low = 定型フォーマット。材料の集約はローカルで完結）**:
  - 朝: あいさつ + 今日の予定（カレンダー §4.6.4）+ 今日の ToDo・日課の件数（§4.6.2）+ 未完了リマインダー（§4.6.1、**直近の数件に絞る** — 全件読み上げをしない。絞り方は Phase 2）+ 今日の天気（§4.7.2、有効時のみ）
  - 夜: ねぎらい + 今日の完了実績（ToDo 完了数）+ 未完了の持ち越し + 明日の予定 + 明日の天気（有効時のみ）
  - 材料が空の項目は黙って省く（空リストの読み上げをしない）。全部空でも短いあいさつは成立させる。
- **§4.6.2「朝の件数告知」との統合**: 定例会話（朝）が有効な間は、朝の ToDo 件数告知を定例会話に**吸収**し単独では発火させない（二重告知の禁止）。吸収時の 1 日 1 回管理は定例会話側で行い、**定例会話が当日配達されなかった日は件数告知も出ない**（許容する）。定例会話（朝）が無効なら従来どおり。
- **ガバナンス**: **朝・夜それぞれ独立の発話カテゴリ**として追加する（どちらも Ambient。段 3 のカテゴリ OFF が各枠のトグルに対応する）。ハード静音・夜間静音に従い、抑制中は**同日内で再試行**する。**夜間静音が優先**のため、枠の設定時刻を夜間静音帯内に置くとその枠は配達されない — 設定 UI はこの重なりを検知して警告する。🔕 フィードバックは各枠を対象とし、**3 回で当該枠のトグルを OFF にする**（1 日 1〜2 回の定例のため、Situation* の間隔バックオフ（§4.6.3）は適用しない）。
- advanced 上乗せ: 同じ材料を会話形式の言い回しに整形する（**材料の選定と発話可否は常に low が確定**し、LLM は言い回しのみ。§4.6.3 の原則）。
- 辞書 events キーを新設（朝/夜の導入・締め。命名は Phase 2）。サブ主体の原則（§4.6 冒頭）に従う。

#### 4.7.2 天気・生活情報 ★

「生活情報」は将来の傘だが、**本 v の実体は天気のみ**（それ以外を本節に足す場合は spec 改訂を伴う）。

- **キー不要・無料の公開気象 API** から予報を取得する（サービス選定は Phase 2。API キーをユーザーに要求しない）。**選定 API の利用規約に従い出典表示を行う**（§4.5.1 の VOICEVOX クレジットと同型の義務）。規約・可用性の条件を満たす API が確保できない場合は、本機能を無効のまま出荷してよい（任意の API キー方式へのフォールバックは将来判断）。
- **地域は手動設定・既定オフ**（§3.3 準拠・**設定行為をもって同意とみなす**）。地名検索から緯度経度を設定できる UI を持つ。外部へ送るのは気象 API への座標・地名クエリのみで、**送信する座標は市区町村粒度（目安: 小数 1 桁 ≒ 約 11km）に丸める**。
- low:
  - 予報の取得とローカルキャッシュ（定期 + 定例会話の直前。オフライン時はキャッシュを使い、**取得から一定時間を超えた古いキャッシュは使わず天気項目を省く** — 閾値は Phase 2、既定 6 時間目安）
  - 定例会話（§4.7.1）への材料提供: 今日/明日の天気・気温・降水確率
  - **降雨の一言**: 当日に降雨が見込まれる朝に一言知らせる状況発話カテゴリ（§4.6.3 に追加、既定オフ）。カレンダーに外出予定（当日の時刻付き予定）がある日は言い回しを強める。**朝の定例会話が有効な間は定例会話（天気項目）に吸収**し単独では発火させない（§4.6.2 の吸収と同型・二重告知の禁止）
- **本 v の非採用**（将来課題 §6.6）: 気象警報・注意報の取得、気温差アラート、週間予報の読み上げ、複数地点。
- advanced 上乗せ: 「今日の天気は？」への応答（キャッシュを会話材料に注入）。

## 5. 配布

- **形式**: NSIS インストーラ（`currentUser` モード、日本語ロケール）。
- **初回起動時 DL** が必要なもの:
  - voicevox_core 資産（c_api / onnxruntime / dict / models 合計数百MB）
  - Irodori-TTS（オプション、Python+PyTorch+CUDA+モデル 数GB）
- **インストーラサイズ目標**: 5〜10 MB（資産は全部初回DL）
- **インストール先**:
  - 実行ファイル: `%LOCALAPPDATA%\ugg\`
  - データ: `%APPDATA%\ugg\`（DB、TTS 資産、ログ）
    - ログは `ugg.log`（追記、2MB で `ugg.log.1` へ 1 世代退避）。パニックと、これまで `eprintln!` で stderr にしか出していなかった診断を残す。**リリース版はコンソールが無く、以前は 1 行も残らなかった。**
    - **診断ログに会話本文を残さない（★v0.5.3）。** ユーザーの入力・LLM の応答本文をログやエラー文言に載せない。**ログは履歴クリアの対象外**なので、載せると消す手段が無いまま溜まり続ける。診断に必要な情報（何が起きたか・どこで失敗したか・長さ）は本文なしで残す。
      - **対象は LLM を叩く経路すべて**（チャットの応答・独り言バッチ・HTTP エラーボディ）。
        v0.5.3 の最初の実装はチャットの応答だけを直しており、**同じ形の独り言バッチが
        漏れていた**（リリース前監査で検出）。1 箇所直して済ませない。
      - HTTP エラーボディは診断に要る（課金切れ等はここにしか出ない）ので、
        消すのではなく**長さで頭打ちにする**。プロンプトを反射するサーバがあるため、
        丸ごと載せると会話本文が落ちうる。
  - keyring: OS 標準（Windows Credential Manager）
- **更新**: 自動更新は無し、`system_messages.update_available` 経由のゴースト案内のみ（手動 DL & 再インストール）。

着手前の spike でユーザーが聴き比べ、**MF は高い音が劣化する**と判断して v4.1-Small（RF）へ改めた

直した。前回の記録は `docs/release-notes/v0.5.6.md`。

### spike と検証で分かったこと（2026-09-25〜26、実物で確認）

計測は ugg の Python 環境を scratchpad へ複製して行った。更新前（transformers 4.57.6 / 上流 `8224daf`）と
更新後（transformers 5.17.0 / huggingface_hub 1.33.0 / 上流 `89f9d8fb`）で、`RuntimeKey` / `SamplingRequest` の値は
ugg の `sidecar.py` と同じにした。**コーデックだけは ugg の `model\` にある `weights.pth` をパスで渡した**（ugg 本体は
revision が `main` の間は repo ID を渡し、共有 HF キャッシュの写しを読む。どちらも `47376ee2` の同じ重み）。比べるときだけ
seed を固定した。参照音声はユーザーのメインの参照音声（VoiceDesign 生成の 1 文、4.32 秒）の写し。取得物は計測後に
削除した（2026-09-14 裁定 C）。

**1. 依存を上げても v3 の音は変わらない — 途中の状態でも。**
v3（seed 固定の 3 文）と v2-VoiceDesign（3 キャプション）の出力は、次の 3 つの状態のどれでも更新前と**ビット同一**だった。
- 更新後（transformers 5 / hub 1.33 / 上流 `89f9d8fb`）
- **P**: transformers 5 / hub 1.33 / 上流 `8224daf`（全戻しで固定 URL の 3 本だけが通信なしで戻り、名前付きの依存が
  戻せなかった形）
- **R**: 全戻しの後に、更新で新しく入った配布（hf-xet・pydub・typer・shellingham・annotated-doc）が残った形
  （いまの全戻しは新しく入った配布を消さない）
依存の解決は transformers 5.17.0・huggingface_hub 1.33.0・tokenizers 0.23.2 に、新しく hf-xet・typer・shellingham・
annotated-doc が入る（torch と `numpy<2` は固定のまま解決した）。上流の `pyproject.toml` は `8224daf` と `89f9d8fb` で同一で、
どちらも `transformers>=5.12.1,<6`・`huggingface-hub>=0.34.0` を宣言している（ugg はいまも `transformers<5` を入れて
上流の宣言に逆らっている）。

**2. MF は高い音が落ちる。原因は精度ではない。**
ユーザーの聴感で、品質は **v4.1-Small の 40 ステップが有意に最良 > v4.1 の 16 ステップ > v4.1 の 8 ステップ
≒ v3（sway 8）> MF**。帯域のエネルギーでも、MF は 8 kHz 以上が 3 文とも v3 より 4〜13 dB 低く、
**bf16 と fp32 で差が無かった**（蒸留そのものの性格）。ただし v4.1-Small も帯域の数字では MF と同程度に
高域が少なく、数字の順位は聴感の順位と一致しなかった。**判定はユーザーの耳で行い、数字は補助に留める。**

**3. 速さ。v4.1-Small は同じステップ数なら v3 より遅い。**
参照音声の事前変換あり・短 / 中 / 長の 3 文の中央値（RTX 5080・LM Studio の llama-server 常駐）:

| 構成 | 生成時間 |
|---|---|
| v3・sway 8・fp32（v0.5.6 の構成） | 181 / 277 / 299 ms |
| v4.1-Small・sway 8・fp32 | 288 / 347 / 384 ms |
| v4.1-Small・linear 16・fp32 | 455 / 528 / 540 ms（別の回で 454 / 551 / 612） |
| **v4.1-Small・linear 16・bf16・透かしあり（v0.5.7 の既定の見込み）** | **469 / 521 / 549 ms** |
| v4.1-Small・linear 40・fp32（上流の既定） | 819 / 999 / 1100 ms |
| （参考）MF・4 ステップ・bf16 | 185 / 208 / 211 ms |

ステップ数と品質・速度は比例すると見なす（2026-09-26 ユーザー指示。中間の値の聴き比べは行わない）。
モデルの読み込みは fp32 19.2 秒・bf16 12.0 秒。

**この表は同じ文を繰り返して測った値で、初めての長さの文にかかる準備を含まない**（2026-09-27、E-11 の実機検証で判明）。
上流 `89f9d8fb` は注意機構の cuDNN を最優先に固定しており、cuDNN は入力の形が変わるたびに実行計画を組み立てるので、
長さが毎回違う ugg の台詞では 1 文ごとに約 700 ms 上乗せされていた（v4.1・16 ステップで 1115〜1290 ms）。
`sidecar.py` で cuDNN を外すと初回も 444〜491 ms で、表の値に収まる（定常の速さは変わらない）。
また、**ローカル LLM（LM Studio 等）が同じ GPU で生成している間は、どちらでも 1 文に数秒〜十数秒かかることがある**
（2 つのプロセスの GPU の取り合い。v3 でも同じ状況で 3〜5 秒）。v0.5.7 では直さず、取説に既知の事項として書く。

**4. VRAM。bf16 なら v3 より少ない。**
1 プロセスに 1 つだけ読み込み、透かし込みで 16 ステップの合成と 40 ステップの参照音声の生成を通したときの、
torch の確保量のピーク: **fp32 4.74 GB / bf16 3.31 GB**（v3・fp32 は 3.73 GB）。GPU 全体の使用量の増分は
fp32 5.93 GB / bf16 5.46 GB（CUDA の文脈とキャッシュの予約を含む。予約は足りなくなると手放してやり直す）。
LM Studio のモデルを読み込んだ状態の空きは約 4.2 GB（2026-09-23 の記録）で、**fp32 では入らない恐れがある**。
帯域のエネルギーは bf16 と fp32 で差 1 dB 以内。**ユーザーの聴感で bf16 は許容。ただし参照音声の生成では bf16 に
機械音声の特徴・クセが出る（許容範囲内）**（2026-09-26）。

**5. v4.1-Small は参照音声の生成も担える。**
no_ref + caption で、キャプションごとに違う声が出て（seed を固定した同じキャプションの 2 回はビット同一）、
作った声でそのまま合成できた。ユーザーの聴感で、参照音声からの生成は v2-VoiceDesign・MF・v4.1 のどれでも
機能し、モデル差は無い。

**6. 透かしは pydub を足せば効く。ただし重みを黙って取得する。**
pydub を入れると `silentcipher` が import でき、上流のランタイムが合成結果に透かしを入れる。silentcipher 自身の
読み取りで、ペイロード `IRDTS`（73, 82, 68, 84, 83）を信頼度 0.94 で検出した（透かしの無い音では信頼度 0.45 の
でたらめな値）。追加の時間は 1 文あたり十数〜数十 ms。長さとサンプルレートは変わらない（内部で 44.1 kHz に落として
埋め込むが、出力は 48 kHz のまま）。**透かしの重み（`sony/silentcipher`、約 68 MB）は、最初の合成のときに上流が
`snapshot_download` で黙って取る**（取得先は共有 HF キャッシュ。revision は指定されず `main`）。**状態 P でも、
pydub があるだけで同じことが起きた**（上の 1.）。v0.5.6 の §6.0 が警告していた「合成時の無言の DL」と同じ形。

**7. huggingface_hub 1.33 では、取得の進捗の形が変わる。**
hf-xet 経由の取得では、進捗の行が「取得済みの量と速度」だけになり（`model.safetensors: downloading bytes: ███ | 956MB, 24.6MB/s`）、
全体量と割合が出ない。行は `\r` の上書き。パイプ越しでも v0.5.6 の差し替え（`is_tqdm_disabled`）は効いて行は出た。
v4.1-Small の 3.06 GB は、この環境で 125 秒かかった。

**8. 参照音声が短い 1 本だと、v4 は v3 より少し似にくい。**
上流の評価（JVS 100 話者、RF 40 ステップ）で、1 本（平均 4.8 秒）の話者類似度は v3 0.678 / v4 0.661、
約 30 秒で v4 0.752、120 秒で 0.775（伸びの大半は 30 秒まで）。読みの正確さは長さで変わらない。評価は
「同じ話者の短い発話を 1 本ずつ変換して連結」した参照で、1 本の長い録音は評価されていない。
**少ないステップでは逆転する**: RF 4 ステップでは 1 本 0.359 → 120 秒 0.340（ステップ数を減らすと似方が崩れる）。
ugg の参照音声は VoiceDesign の 1 文（約 4 秒）で「1 本」の領域にあり、ユーザーの聴感でもモデル差は無かった。
§4.5.1 で外部音声の取り込みは禁じているので、長くするには生成するしかなく、その効果は分からない。
**参照音声を長くする件は記録して次以降へ回す**（2026-09-26 ユーザー裁定）。

**9. caption は v4.1-Small では効き、v3 では効いていない。**
seed を固定し caption なし・ありを比べると、v4.1-Small では音が変わり（同じ条件の 2 回はビット同一）、
v3 では**渡しても音が 1 ビットも変わらない**（v0.5.4 の反証が指摘した「caption は一度も効いていない」を実測で確認）。
絵文字 45 種は v4.1-Small のトークナイザでどれも未知語にならない（v4.1-Small の `EMOJI_ANNOTATIONS.md` は v3 と同じ
45 種・同じ意味）。**ただしユーザーの聴感では、caption も絵文字もどのモデルでも効きが弱い**（効かせるには工夫が要りそう）。

**10. 参照音声の事前変換は、新しい上流でもそのまま使える。**
v0.5.6 項目 1 が使う非公開のメソッド `_load_reference_latent(req=…, batch_size=1, messages=[])` は `89f9d8fb` でも
同じ形で、v4.1-Small・MF・v3 のどれでも変換結果を作って合成できた（v0.5.6 の §6.0 が「上流の固定版を上げたときに
確かめる」とした点）。上流は `ref_wavs`（複数本を 1 本ずつ変換して連結）にも対応し、その場合も 1 つの変換結果になる。

**11. v0.5.6 の §6.0 の誤りの訂正。**
「MF は実行時に渡したステップ数を無視して 4 ステップで回る」は誤り。上流は `num_steps` を渡されれば
その数で回し（ugg の 8 を渡すと 8 NFE・257 ms）、無視するのは CFG とサンプラーの設定だけ（明示の 4 と既定は
ビット同一）。MF を採らないので実装には影響しないが、記録として訂正する。

### 反証レビュー（別 Opus、2026-09-26）が崩したもの

**1. 「揃っているか」の判定を `assets_ready` に入れると、更新前の利用者の設定が消える。**
案では「トークナイザが取れたかを判定に含める」としていた。`assets_ready` は `get_irodori_status` の `present` になり、
フロントは `present` が偽だと実モデルの設定（`tts_irodori_use_real_model`）を倒して保存し、**更新ボタンも隠す**
（`settings.ts`）。アプリを入れて更新をまだしていない人は v4.1 のトークナイザを持っていないので、ビルドの値で判定すると
「未導入」になり、設定が消えたうえに更新もできなくなる。v0.5.4 で一度踏みかけた罠（architecture の
`irodori_assets_ready` の注記）。→ **項目 2 で、欠けは「更新が要る」（`outdated`）の側に倒し、`present` の意味は変えない。**

**2. 生成を合成のランタイムで済ませるには、サイドカーの変更が要る。**
`_load_synth` と `_load_voice_design` は別々に `InferenceRuntime.from_key` を呼ぶ（上流の `from_key` はキャッシュしない）。
記録の値を揃えるだけでは v4.1 を 2 つ読み込む。また、欄を消したときに v2 を読みに行く理由は「決定表が基準値と読むから」
ではなく、**読み先の決定がビルドの名前しか回さないので引数が渡らず、`sidecar.py` の既定値が使われる**から（結論は同じ）。

**3. 全戻ししても新しく入った配布は残り、戻った v3 で透かしが有効になる。**
全戻しは控えにあった配布しか戻さない（新しく入ったものは「残します」とログに書くだけ）。pydub が残ると上の 6. の
無言の取得が起きる（状態 R・P で確認）。→ 項目 5 で、透かしの重みを更新の**最初**に取る。

**4. ゲートの VRAM 不足のしきい値が v3 のまま**（`GATE_VRAM_SUSPECT_MB = 4096`、根拠は v3 のピーク 3.5 GB）で、
v0.5.6 項目 3b が約束した「v3 が transformers 5 で動くと分かれば、保留を許すかを再判断する」が案から消えていた
（上の 1. で動くと分かった）。→ 項目 6 で保留を許す（2026-09-26 ユーザー裁定）。

**5. ゲートは参照音声の生成を試さないのに、成功後に v2-VoiceDesign を消す案だった。** 参照音声を持たない人は、
試されていない生成しか手段が無くなり、失敗しても戻る先が無い。→ 項目 6・10 で、ゲートで生成も試し、両方通ったときだけ消す。

**6. 「ランタイムをダウンロード」でも、控え・全戻し・ゲートなしで major 移行が起きる。** 導入済みでも GPU があれば
押せ、全段を `--upgrade` で入れ直して最後に今の値を記録する（固定 URL の 3 本は `--force-reinstall` なし）。
→ 項目 1 で、導入済みの環境では更新の経路へ振り向ける。

**7. 絵文字の受け入れ条件「あり・なしで音が変わる」は、効いていなくても必ず通る**（本文に文字を足せば、何であれ音は
変わる。spike でも 45 種すべてが「変わる」だった）。v0.5.6 の caption の条件と同じ型。→ 受け入れ条件を「未知語に
ならない」に絞る。

**8. ほか**: 契約の改訂の漏れ（サイドカーの HTTP 応答は理由によらず 500、`TtsError` は 4 種、`export_data` はパスしか
返さない）／transformers を範囲で指定すると利用者の環境が spike で確かめた組み合わせにならない／`sidecar.py` の既定値を
v3 に据え置く決まり（v0.5.6 3a）と、既定値が `MODEL_PINS` と一致することを求める契約テストの衝突／コーデックは
`main` の間は共有キャッシュから読まれ、新規の人は最初の合成で約 0.43 GB を黙って取る／空き容量の確認の取りこぼし／
確認ダイアログが旧モデルを消すことを伝えていない／案の「記録からいまの要求に無い名前を消す」は今回は対象が無い
（開発方針 2）／§6.0 の差し替えで宙に浮く参照 4 か所（spec §4.5.8・§6.6 の表、script-reader-spec、architecture）。
すべて下の項目に入れた。

**2. 合成モデルを v4.1-Small（bf16）へ差し替える**

  写しから読む（v0.5.5 の `_codec_location`）。`main` のままだと共有キャッシュから読まれ、新規の人は最初の合成で
  約 0.43 GB を黙って取る。置き場所の名前に revision が入るので取り直しになる（手元の `main` の写しが同じ版なら移して
  使ってよいかは実装で決める）

- 読み先と取得先は v0.5.6 項目 3a の決定表のまま（取得はいまのビルド、読みは記録。更新が成功したときだけ記録が
  ビルドに追いつく）
- 参照音声の事前変換の結果はファイル名にモデルと精度が入るので、乗り換え後の最初の合成で作り直される（v0.5.6 項目 1）

- 確かめ方: 更新後の最初の合成で `ugg.log` にモデル・精度・所要時間が出る
- 改訂: architecture §2.4 と §8.1（`model\` の下の置き場所・`tokenizer\`）、§8.3（モデルの一覧）
- → **2026-09-26 に実装した**（`d4c75e9`）。精度とサンプラーは `sidecar.py` が**読み込むモデルで決める**
  （`V4_MODELS`。v4.1 は bf16・16 ステップ linear、v3 と v2-VoiceDesign は v0.5.6 の fp32・sway 8 のまま —
  更新前・失敗して戻った後・保留中に v3 で喋るとき、ユーザーの聴いていない組み合わせにしない）。
  取得は `model.safetensors` と `tokenizer/*` を `snapshot_download` で取る。欠けの判定は、記録がいまのビルドの
  モデルを指しているときだけファイル（`MODEL_FILES`）を見る（古いモデルの記録は欠けで責めない）。
  コーデックは手元の `main` の写しを移さず取り直す（約 0.43 GB。単純さを優先）。**変異テストで、既存の契約テスト
  （`sidecar.py` の既定値と `MODEL_PINS` の一致）が「名前がファイルのどこかにある」しか見ておらず素通りすることが
  分かり、代入の行を見る形に強めた**

**3. 参照音声の生成を v4.1-Small にまとめる**（2026-09-26 ユーザー裁定）

- v2-VoiceDesign（2 GB）の取得と、生成のための別モデルの読み込みをやめる
- **`model_voice_design` の欄は消さず、中身を `model_synth` と同じ値にする。** 欄を消すと、読み先の決定がビルドの名前しか
  回さないので引数が渡らず、`sidecar.py` の既定値（旧 v2）が使われる（上の反証 2.）。同じ値なら取得は 1 回で済む
  （etag の照合で 2 回目は取らない）
- **サイドカーは、`model_voice_design` と `model_synth` が同じ repo@revision なら、生成に合成のランタイムを使い回す**
  （`_load_voice_design` が `_load_synth()` を返す）。今のままでは同じモデルを 2 つ読み込み VRAM を 2 倍使う
- 生成のステップ数とサンプラーは据え置き（linear 40。一度きりなので品質を優先する。項目 4 の設定の対象外）。
  精度は合成と同じ bf16（生成だけ fp32 にするとランタイムが 2 つになる）。bf16 の生成に機械音声のクセが出ることは
  上の 4.（許容範囲内の裁定）
- **既存の参照音声は作り直さない**（2026-09-26 ユーザー裁定）。声の質感が変わることは項目 8 で伝える
- 確かめ方: 乗り換え後に参照音声を作り直せる／合成と生成でモデルを 1 回しか読み込まない（`ugg.log`）
- → **2026-09-26 に実装した**（`56911c1`）。使い回すときは `ugg.log` に「参照音声の生成は合成と同じモデルで
  行います（読み込みは 1 回）」。揃っているべきファイルに、生成の側もトークナイザを含めた（caption の
  トークナイザも同じ `tokenizer/`）

**4. 合成のステップ数を設定で選べるようにする**（新しい設定 1 つ。2026-09-26 ユーザー裁定）

- 設定 `tts_irodori_steps`。選択肢は **8（速さ優先・sway）/ 16（標準・linear）/ 40（品質優先・linear）**、
  **既定は 16**。測った 3 点をそのまま選択肢にする（中間の値は置かない）
- **4 のような極端に少ない値は置かない**（上の 8. — RF 4 ステップでは話者類似度が崩れる）
- **v4.1 にだけ効く。v3 で喋っている間（更新前・失敗して戻った後・保留中）は v0.5.6 の値（sway 8）のまま**

**7. 更新があることと、使えない理由を事実どおりに伝える**（告知 3 件、2026-09-25 ユーザー裁定）

- **Irodori の更新があることを設定パネルの外でも知らせる。** いまは設定パネルを開いた人にしか見えず、乗り換えが
  届いたことに気付けない。**Irodori を導入済みの人だけ**、起動後に 1 回確かめて、**更新の対象の組ごとに 1 回**、
  届いたときだけ済みにする（v0.5.6 項目 6 の `once_reached`）。確かめる処理（`status()`）は python.exe を起動し
  記録に基準値を書き足すので、**更新の錠を握っている間は確かめない**
- **使えない理由を分ける。** いまは理由によらず辞書の `irodori_unavailable`（「GPU 環境が整っていないようだ」）を言う。
  少なくとも「モデルが無い（更新が要る）」「更新中」「GPU が無い」「VRAM が足りない」「起動に失敗」を分ける。
  そのために、**サイドカーの HTTP 応答で失敗の理由の種類を返し**（いまは理由によらず 500「Irodori 合成失敗」）、
  Rust 側の `TtsError` で区別する（いまは 4 種）
- **VRAM が足りないことを伝える。** サイドカーは既に GPU のメモリ不足を見分けている（`_is_out_of_memory`）が、
  使っているのは事前変換とゲートの経路だけ
- 改訂: `NoticeKind` と辞書キー（spec §4.4 / architecture の告知の表）、辞書（main.yaml）、architecture §8.5
  （応答の形）・§8.6（振り分け）
- → **2026-09-27 に実装した**（`52f9422`）。サイドカーは合成の失敗の応答に種類（`model_missing` / `oom` / `other`）を
  入れ、Rust は `TtsError::Synth` で受ける（古い形は今までどおり `Http`）。更新中は `TtsError::Updating`、GPU が
  見えないのはヘルスの 503（`status: no_gpu`）。更新の告知はアプリ本体の更新の確認と同じ見張りに乗せ、済みの記録は
  `irodori_update_notice_seen:<対象の組>`。**変異テストで、配線を本文のテキストで固定するテストが自分自身の文字列に
  当たって素通りすること（3 か所）と、1 回だけの告知の確認（v0.5.6 からある）が引数の中で先に済みにする形を
  捕まえられないことが分かり、直した**

### 受け入れ条件

- **実データで更新を通す**（v0.5.6 の §6.0 が「分割の弱点」として挙げた点。v0.5.7 がその最初の回）:
  (a) 更新前（v0.5.6 の環境）→ 成功（v4.1・bf16 で合成と生成ができ、旧モデルが消える）
  (b) 更新前 → 途中で失敗 → **transformers 5 → 4 まで全部戻り、v3 で喋れる**（新しく入った配布が残ることと、
  透かしの重みを黙って取らないことも見る）
  (c) VRAM 不足で保留 → VRAM を空けて更新 → ゲートだけで成功
  手段は v0.5.6 の E-10 と同じく、`installed.json` を控えて欄を書き換える／ユーザーの端末かエクスプローラーから起動する
- **caption が効くこと**（test-plan の S4 / S4' と script-reader-spec §5.2 の期待値を書き換える）:
  seed を固定し、同じ文・同じ参照音声で caption なしとありを合成して差が出る。対照として同じ seed・同じ caption の
  2 回がビット同一。seed を固定する手段は**試験の経路だけ**に置く（`--synth-once` に引数を足す等。HTTP の要求や
  ユーザー向けの設定には足さない）
- **絵文字 45 種**: トークナイザで未知語にならない。**音が変わるかは条件にしない**（何を足しても変わるので効き目の
  証拠にならない。上の反証 7.）。効きの強さも条件にしない（ユーザーの聴感で、どのモデルでも弱い。§6.5）
- **透かし**: 実機の出力から `IRDTS` を読み取れる。対照として、透かしを外した出力からは読み取れない
- **速さ**: 既定の 16 ステップ・bf16 で、インストール版の `ugg.log` の所要時間が上の表の ±20% に収まる
- **声**: ユーザーが既定の 16 ステップ・bf16 を自分の参照音声で聴いて許容（2026-09-26 に spike の音で許容済み。
  インストール版で改めて聴く）→ 2026-09-27 の A2 で、受け入れ条件の道具の出力（インストール版と同じランタイム・自分の
  参照音声）を聴いた（caption の差は誤差のレベル）。v0.5.7 はインストール版を開発機で使い始めた（09-28）
- **実モデルの ON/OFF**（v0.5.6 項目 4 が「v0.5.7 の実機検証の前提」とした mock と実モデルの往復）が、v4.1 でも次の
  発話から効く
- → **caption・絵文字・透かしを 1 回で確かめる試験の経路を用意した**（2026-09-27、`7e74f3e`）: `sidecar.py --acceptance
  <出力先> --voice-ref <参照 wav>`。seed はこの経路の中だけで固定する（HTTP の要求・設定・通常の合成・ゲートには無い）。
  結果は `acceptance.json` と聴き比べ用の wav。手順は test-plan E-11 の「受け入れ条件」

| 項目 | 要点 |
|---|---|
| 画面 OCR・画面理解 | PowerToys 等で代替可能。採用する場合は範囲選択・送信前プレビュー・クラウド送信明示・自動マスクを必須条件とする |

| スマートホーム連携 | 構想のみ |
| **伺かゴースト（SHIORI 辞書）の変換** | **非目標（2026-08-31 裁定）。** 実装しない。技術的に不可能だからではなく（里々は宣言的で構造がほぼ 1:1 に対応する）、**得られるものと失うものが釣り合わないため**。① ugg の events 約 40 キーのうち伺かから供給源があるのは約 20 で、それは汎用マスコットの側。`focus_*` / `pomodoro_done` / `todo_*` / `reminder_*` / `situation_*` / `calendar_upcoming` / `regular_*` / `weather_*` と `system_messages` / `input_match` / `fallback` / `recall` / `monologue` は**供給源が存在せず**、ugg の存在理由にあたる側が結局手書きになる。② 辞書の `Line` は 1 応答 = 最大 2 発話だが、伺かのトークは話者が 4〜12 回入れ替わる脚本で、**その往復のリズム自体がキャラの個性**。スキーマの表現力差なので実装では改善しない。③ ゴーストは作者が書いた文章そのもので、条件分岐を潰す変換は「作者が設計したいつ何を言うか」を壊す。**著作権法 50 条により私的複製（30 条）は著作者人格権に及ばず**、同一性保持権の論点は手元利用でも消えない。界隈の許諾も作者ごとに真逆で機械判定できない。**例外は「原作者本人が自分のゴーストを移す」場合のみ**（他人のゴーストを変換する道具としては作らない） |
| **他人のキャラの人格記述の自動生成** | **レッドライン（2026-08-31）。** 第三者ゴーストの辞書から `persona` / `style_notes` を機械生成して LLM に演じさせる導線は作らない。原作者が一度も書いていない台詞を、そのキャラの名前で、原作者の訂正手段なしに生成し続ける装置になるため。**§4.2 の persona 配線を行う場合も、この線を先に確定させてから着手する** |

| 項目 | 方針 |
