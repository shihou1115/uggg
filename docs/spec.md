## 1. プロダクトコンセプト

### 1.1 ugg とは
「伺か」コンセプトを Tauri v2 で再構築したデスクトップマスコット。デスクトップに常駐する2体（または1体）のキャラクターが、自発的に話したりユーザーと対話したりする。

### 1.2 コアアイデンティティ
- **マスコットの存在感**: 起動挨拶・独り言・放置反応・つつき/撫で反応で「そこにいる」感を出す。
- **掛け合い対話**: メイン/サブ2体の会話表現が基本。
- **無料でも動く**: API キー無しでも辞書ベースの会話で楽しめる。
- **プライバシー優先**: 発話テキストは外部送信しない（クラウド LLM 経路を除く明示的同意済みの範囲のみ）。

### 1.3 ターゲット
- **OS**: Windows 10/11 x64 のみ
- **ハードウェア**: 通常のCPUのみで全機能動作（一部 GPU 拡張機能あり、§4.5.1 参照）

## 2. 採用済み技術選定（再調査しない）

| 領域 | 選定 | 理由 |
|---|---|---|
| プラットフォーム | Tauri v2 + Vanilla TypeScript + Rust | v0.0.3 実証済 |
| データストア | SQLite + keyring + ファイル資産 | 同上 |
| TTS（既定） | voicevox_core 埋め込み（libloading + プリビルドC API） | 無サーバ・CPU合成 |
| TTS（オプション） | Irodori-TTS サイドカー同梱（GPU必須） | キャプションVoiceDesignの上位品質 |
| クリック透過 | アルファマスク方式（8px グリッド + ポーリング） | 透明部分の誤クリック防止 |
| 対話モード | 二モード制（low=辞書 / advanced=LLM） | API キー無しでも動かす |
| 配布 | NSIS インストーラ（currentUser） | v0.0.3 実証済 |

## 3. 横断方針（全機能に適用）

### 3.1 ゴースト発話原則
**システム的なメッセージはできる限りキャラクター（ゴースト）に喋らせる**。トースト・ダイアログは補助・フォールバック扱い。

対象例:
- コスト警告（80%到達・上限超過）
- モード自動降格の通知
- 更新通知
- 自動DL完了・失敗
- 軽微なエラー（重大なものはトーストで二段表示）

辞書 events に対応キーを定義し、各台詞バリエーションを作者が書ける構造。発話できない状況（ゴースト未ロード・起動直後・致命的エラー）は従来のトースト/ダイアログにフォールバック。

### 3.2 「無サーバ」要件
**ユーザーが ugg を使うために、別アプリ・別サーバを手動起動する必要はない**。
- voicevox_core: アプリに埋め込み
- Irodori-TTS: サイドカーとして同梱（ユーザーから見れば「ugg の一部」）
- LLM API: 例外（クラウド/ローカルとも、ユーザーが API キー or LLM サーバを別途用意）。これはユーザーの選択で動かす対象なので「無サーバ」の対象外と整理。

### 3.3 プライバシー
- 発話テキスト・合成音声は外部送信しない。
- LLM プロバイダへの送信のみクラウドへ出る（ユーザー同意済み・既定ローカル/オフライン優先）。
- 時事ネタの検索キーワードは検索サービスへ送信（既定オフ・オンボーディング同意必須）。
- カレンダー: ユーザーが明示設定した URL への ICS 取得リクエストのみ（既定オフ。§4.6.4）。
- 天気: ユーザーが明示設定した地域の座標・地名クエリを気象 API へ送信（既定オフ・**設定行為をもって同意とみなす**・座標は市区町村粒度に丸める。§4.7.2）。
- データのエクスポート・削除をユーザーが自由にできる。

## 4. 機能仕様

### 4.1 キャラクター・ウインドウ

#### 4.1.1 キャラ構成（2体だがサブは任意）★
- メインキャラとサブキャラの 2 体構成を基本とする。
- 配置は伺か風: 下端揃えでタスクバーの上に立つ。**既定配置はメインが画面右端・サブがその左隣**（デフォルトシェルは main 256×384 / sub 96×144 でメイン大・サブ小）。
- **キャラはそれぞれ独立してドラッグで X 軸方向にのみ移動できる**（§4.3.4）。Y は作業領域下端（タスクバー上端）で固定。移動範囲はステージ内（＝ステージを置いているモニタの作業領域内）。**キャラをドラッグで別モニタへ移すことはできない**（ステージごと移す = 表示モニタの選択は §4.1.6）。
- **シェル/ゴーストはサブを省略可能**。サブ無しゴーストでは:
  - 画面にメインのみ表示
  - 掛け合いパターンはパターン1（main単独）相当に縮退
  - 撫で/つつきは main のみ
  - 設定 UI の「サブの声」等は無効化または非表示
- データスキーマ（shell.json）と辞書スキーマは「サブが存在しないゴースト」を表現可能にする（Phase 2）。

#### 4.1.2 キャラ画像表示（全 pose プリロード）
- 全 pose の `<img>` を data URL でプリロードし、`visible` クラス切替で表現。
- 切替時のチラつきはほぼゼロを目標。

#### 4.1.3 吹き出し描画 ★
- **吹き出しはキャラクターの左横に表示**(伺か風)。上端をキャラの顔の高さ（キャラ上端 + 高さの 12%）に合わせ、しっぽはキャラ側を向く。main/sub 両表示で重なる場合は main を上・sub を下へ退避。
- キャラが画面左端付近で左横に収まらない場合は**右横に反転表示**（しっぽも反転）。
- **タイプライター描画**（1文字ずつ表示）。
- **描画速度はユーザー設定で可変**（速い / 普通 / 遅い / 一気に表示）。
- main → sub の順に逐次表示、重ならない。
- **掛け合いパターン3/4 では 3 つ目の吹き出しを独立表示**（v0.0.3 の「同じ吹き出しに追記」方式は廃止）。
- 新発話で interrupt（古い音声・描画を打ち切る）。
- 表示継続時間はセリフ総文字数に比例。
- 全ターンの描画+発話完了後に一括消去。

#### 4.1.4 口パク（振幅駆動のみ）★
- TTS 有効時のみ動作。再生振幅（AnalyserNode RMS）でリアルタイム駆動。
- **TTS 無効時の口パクは無し**（v0.0.3 のタイマー近似を廃止）。
- pose 画像の隣に `<name>_talk.png` があれば開口フレームとして使用。無いシェルは口パクなし。

#### 4.1.5 表示スケール ★
- 設定 UI で 0.5〜2.0 の範囲で可変。
- スケールはキャラ画像のみに適用（ウインドウはステージ方式 §4.1.6 で全幅固定のため連動しない）。拡縮の基準点はキャラの足元左（bottom left）。ステージ高さは上限 2.0 でもデフォルトシェルのキャラの頭が切れないよう確保する（§4.1.6）。
- **要件: 吹き出しのテキスト・フォントサイズはスケールの影響を受けず、視認性を維持する**（v0.0.3 で課題化された問題）。
- 実装方針（Phase 2 で設計）: キャラ画像と吹き出しのレイヤーを分けて scale を別管理、または逆補正。

#### 4.1.6 ステージ（ウインドウ）とキャラ位置の永続化
- ウインドウは**モニタ作業領域の全幅 × 高さ 1024 の透明ステージ**として**作業領域下端に固定**する（＝キャラの足元が常にタスクバー上端に乗る）。高さはデフォルトシェルのキャラを表示スケール上限（§4.1.5、2.0）で拡大しても頭が切れず、その上のバルーン・入力欄まで収まる値。作業領域高さが足りなければその高さでキャップする。**ユーザーがウインドウをドラッグで動かす手段は無い**（表示モニタの切り替えのみ設定から可能。次項）。
- **表示モニタの選択（v0.4）★**: ユーザーは**設定パネルで、ステージを表示するモニタを選べる**。
  - **明示的に選択されたモニタが常に優先**される。選択が無い場合にかぎり、前回終了時の位置から推定する（`window_pos` キー。従来の挙動）。**1 秒間隔の監視は明示選択を上書きしない**。
  - 選択したモニタが見つからない場合は**主モニタへフォールバックする**が、**選択自体は保持する**。
  - **戻る保証の範囲**: OS が返すモニタ識別子は接続順で入れ替わりうるため、「同じ物理モニタに必ず戻る」ことは保証しない。**表示構成が選択時と同じであれば選んだモニタに戻る**。構成が変わっていた場合は主モニタに置き、ユーザーは選び直せる（誤ったモニタに固定されない）。
  - 選択は `monitor_pref` キーに永続化する（識別子の形式は Phase 2 設計。`window_pos`（前回位置）とは別の値）。
  - **DPI が異なるモニタへ移しても正しく表示される**（ステージ高さをそのモニタのスケールで再計算する）。
- モニタ構成・解像度・タスクバー高さ・DPI の変更は 1 秒間隔の監視で検知し、自動で再ドックする。
- **キャラごとの X 位置**（ステージ内 CSS px、視覚ボックス左端）を `char_pos` キーに永続化する。保存はドラッグ終了時（mouseup）に即時。起動時に復元し、ステージ幅に収まるよう clamp。保存が無いキャラは既定配置（§4.1.1）。**モニタを移して幅が変わった場合も新しいステージ幅に clamp する**（モニタごとに別々の X 位置は記憶しない。将来課題 §6.6）。

#### 4.1.7 タスクトレイ ★
- アイコン常駐、左クリックでウインドウ表示/非表示。
- 右クリックでメニュー（**セーフモード項目は除く**）:
  - 表示/非表示
  - モード切替（low / advanced）
  - 静音モード
  - 設定を開く
  - 終了
- メニューのチェック状態は設定変更時に同期。

#### 4.1.8 セーフモード（廃止）★
- v0.0.3 のセーフモード（不透明・枠ありで起動する保険機能）は廃止。
- ウインドウ生成は単一ラベル・単純構造に。

### 4.2 対話

#### 4.2.1 二モード制
- **low モード**: 辞書のみ。API キー不要・無料・オフライン。
- **advanced モード**: LLM 経由で動的生成。
- ユーザーは設定で手動切替可。
- 自動降格条件: API エラー連続 / コスト上限超過 → 一時 low に降格 → 一定時間後に復帰試行。
- **モード境界の再定義（2026-07-12、日常支援 §4.6 の採用に伴う）★**:
  - low = **決定論的・ローカル・即時・低コスト**（辞書会話、定型コマンド、リマインダー、ToDo、ポモドーロ、状況検知と定型通知、カレンダー表示 等）
  - advanced = **解釈・生成・要約・提案**（自由会話、曖昧な指示の解釈、タスク分解・優先順位提案、状況に応じた発話生成、長期記憶の参照 等）
  - **不変条件: LLM が利用不可（未設定・降格・障害）でも、生活支援機能（リマインダー・ToDo・タイマー・カレンダー表示）は常にローカルで動作する。** advanced はこれらの上に「解釈と提案」を上乗せする層であり、基盤機能の前提にしない。

#### 4.2.2 LLM プロバイダ（OpenAI 互換のみ）★
- **OpenAI 互換 API のみサポート**。
- 設定: モデル名 / `base_url`（任意） / API キー（keyring）。
- これにより以下が同じ仕組みで接続可:
  - OpenAI 公式
  - Grok（OpenAI 互換）
  - LM Studio / Ollama（ローカル LLM、OpenAI 互換エンドポイント）
  - その他 OpenAI 互換サーバ
- **Anthropic SDK 専用ルートは廃止**。

#### 4.2.2b キャラクターの人格記述（persona）★

- `ghosts/<id>/ghost.json` にゴースト作者が記述し、**advanced 経路の system prompt に載せる**。
  - `characters.main.persona` / `characters.sub.persona`: 各キャラの人格・口調・一人称。
  - `prompt.max_chars_per_line`: 1 発話あたりの目安文字数。**指示として載せるだけで強制はしない**。
  - `prompt.style_notes`: 掛け合い全体のトーン指示。
- **いずれも省略可**。省略時は役割だけの既定文（「メインキャラ。」等）にフォールバックする。
  第三者ゴーストが書いていなくても壊れない。
- 適用先は **advanced の 3 経路すべて**: チャット応答 / 独り言生成（§4.4.4）/ 定例会話の言い換え（§4.7.1）。
- **プロンプトには「設定文そのものを台詞で説明しない」旨の指示を併記する。**
  これが無いと LLM が人格記述を復唱する（「あたし、好奇心旺盛だから！」）。
- **ここに書かれたものを読むだけで、ugg が人格記述を生成することはない。**
  第三者ゴーストの辞書等から persona を機械生成して LLM に演じさせる導線は
  **§6.4 のレッドライン**で禁止している。
- 背景: v0.4.1 まで `GhostManifest` がこれらのフィールドを宣言しておらず、
  **serde が黙って捨てていた**。実測（2026-09-02、ローカル LLM・8 往復 ×2）では、
  persona 不在だと一人称の一致が main/sub とも 0/8 で、**2 人が区別のつかない同調役に潰れ、
  §4.2.4 の掛け合いが成立していなかった**。v0.5 §6.0 の項目 1 で配線。

#### 4.2.3 辞書スキーマ v3 ★
- v0.0.3 の schema v2 を整理して v3 を新規策定（**v2 からの自動マイグレーションは設けない**、作者に書き直しを求める）。
- 整理方針:
  - セクションを統合・最小化（recall_talk / update_talk 等の使い分けを見直し）
  - events キーの乱立を抑制（推奨命名・部位粒度を C-2 に合わせて簡素化）
  - 横断方針 §3.1 に対応する system 系 events を整理・追加
- スキーマ詳細は Phase 2 で策定。

#### 4.2.4 掛け合いパターン ★
- パターン1: main → sub
- パターン2: sub → main
- パターン3: main → sub → main（**3つ目の吹き出し**で表示）
- パターン4: sub → main → sub（**3つ目の吹き出し**で表示）
- **新パターン: 問いかけパターン**（極低確率発生、ユーザー応答を期待）
  - 例: 「最近どんなことに興味あるの？」「コーヒー派？紅茶派？」
  - ユーザー応答時の処理（user_profile への自動反映、follow-up 発話）は Phase 2 で設計。
  - 応答が来なかった場合のタイムアウト挙動も Phase 2 で設計。
- サブ無しゴーストではパターン2/3/4 は使えない（自動的にパターン1へ縮退）。
- advanced のみ可変、辞書系は常にパターン1。
- 番号が小さいほど高確率（重み付け）。

#### 4.2.5 長期記憶（user_profile）★
- ユーザーの情報を保存。LLM 呼び出しの system prompt に注入。
- 設定パネルで閲覧・追加・削除。
- オンボーディングで nickname / 興味 / 話し方 / 時事ネタ ON/OFF を聞き取り → 自動投入。
- **新機能: 会話からの自動抽出**（advanced のみ）
  - LLM 呼び出し時に「記憶すべきサマリ」を副産物として抽出
  - user_profile に自動保存
  - 抽出ロジック・トリガー条件は Phase 2 で設計
- **容量管理**: 件数/文字数の上限・古いものの自動破棄/要約を Phase 2 で設計。

#### 4.2.6 会話の自動要約（記憶に統合）★
- v0.0.3 の `context_summaries` テーブルは廃止。
- 過去会話の要約は §4.2.5 の user_profile 自動抽出に統合する。
- recall_talk のトリガーも user_profile から派生。

#### 4.2.7 コスト管理 ★
- LLM 呼び出しのコストを `api_usage` テーブルに記録。
- 月額上限 `monthly_limit_usd` を設定。
- **80% 到達時に警告**:
  - トースト + **ゴースト発話**（横断方針 §3.1）
  - 辞書 events に対応キーを追加（例: `cost_warning_80`）
- **上限超過時に自動降格**:
  - low モードへ降格
  - **ゴースト発話**で通知（黙って降格しない）
- 次月リセットで復帰。
  - 判定は **LLM 呼び出しの前**に行う単一のゲートとし、chat / 独り言補充 /
    定例会話の言い換えの 3 経路すべてが通る。降格タイマー（API エラー由来）で
    解除してはならない。
  - 告知済みかどうかは **当月タグを `app_settings` に永続化**して判定する
    （プロセス内フラグでは再起動で消え、月が替わっても戻らない）。
- ローカル LLM 利用時は記録のみ（料金は 0）。
- **当月の利用状況を設定画面（AI・拡張）に表示する**: 利用額 / 上限 / 比率。
  `get_cost_status` コマンドで取得する。
  - **料金表に無いモデルはコスト 0 で記録され、上限が発動しない。**
    ローカル LLM なら 0 が正しいので、`llm_base_url` がローカルを指していない
    場合のみ「料金を計算できないため上限は機能しない」と警告する。

#### 4.2.8 API キー管理
- keyring に保存（`service = "ugg"`, `user = provider 名` 等）。
- 設定パネルで登録（伏せ字表示）、「保存済み」状態を表示。
- 1 プロバイダ 1 キー。

### 4.3 ユーザー操作

#### 4.3.1 クリック種別の判別と入力導線 ★
- 最後のクリックから 250ms 待って確定:
  - 1 回 → **入力導線**（下記）
  - 2-3 回 → つつき反応
  - 4 回以上 → 連打反応
- mousedown 後の移動 4px 超でドラッグ扱い（クリック判別を抜けてキャラ移動 §4.3.4 へ）。
- **入力導線**: クリックされたキャラが「なにか用かな？」のような**入力促しの反応**（辞書 `input_prompt`、そのキャラ単独の短い発話。TTS 対象・chat_log 記録あり）を返し、**チャット入力欄をそのキャラのバルーンの上側に表示**する。
  - 促しの吹き出しは通常の表示時間で消さず、**入力欄が閉じるまで保持**する。
  - 入力欄が開いている状態での 1 クリック・Esc は入力欄と促し吹き出しを閉じる。送信時・新しい発話でも促しは置き換わる。
  - キャラ以外（吹き出し・透明部分）のクリックは main の導線として扱う。**ただしパネル・バッジ・入力欄などの UI 要素上のクリックは導線・つつきの対象外**（その UI の操作を優先する）。辞書に `input_prompt` が無いゴーストでは促し無しで入力欄だけ開く。
  - 入力欄の配置はバルーンと同じ幾何に従う（キャラ左横基準、画面左端付近では右横へ反転、キャラのドラッグに追従）。

#### 4.3.2 つつき部位判定（縦のみ）★
- 縦 3 区分: head / chest / body（**横判定は廃止**）。
- shell.json で `poke_regions.head_max` / `chest_max` を指定（横の `left_max` / `right_min` は廃止）。
- 辞書 events 探索順: `poke_<t>_<v>` → `poke_<t>`。

#### 4.3.3 撫で（ホバー往復判定）
- ボタン無しでキャラ上を往復するホバージェスチャを検知。
- 判定指標の合わせ技: 方向反転回数 ≥2 / 累積移動量 / 局所性 / 最低継続時間 / cooldown。
- 部位判定は §4.3.2 と同じ（縦のみ）。
- **パネル (設定・読み上げ・チャットログ・確認・オンボーディング) 表示中は無効**。
  パネル操作でカーソルが背後のキャラ上を往復して誤発話するため。

#### 4.3.4 ドラッグでキャラ移動（キャラ単位・X 軸のみ）★
- mousedown したキャラ（部位判定と同じヒットテスト）だけを動かす。**main / sub は独立して移動**。
- 移動は **X 軸方向のみ**。Y はステージ下端（タスクバー上端）に固定（伺かと同仕様）。
- mousedown 後 4px 超でドラッグ開始。移動範囲はステージ（モニタ作業領域）内に clamp。
- ドラッグ終了（mouseup）で位置を即時保存（§4.1.6）。
- 吹き出し表示中はキャラに追従する。
- キャラ以外（吹き出し・透明部）のドラッグでは何も動かさない。`data-tauri-drag-region` は使わない。

#### 4.3.5 右クリック → バルーンメニュー ★
- 独立したコンテキストメニュー UI は廃止し、**メニューはメインキャラのバルーン内に表示**する（伺か風）。
- **メインを右クリック**: メインが前口上（辞書 `menu_prompt.main`、例「なにか用かな？」。TTS 対象・chat_log 記録）を発話し、**続けて同じバルーン内に**メニュー項目を表示する。
- **サブを右クリック**: サブが誘導セリフ（辞書 `menu_prompt.sub`、例「用事ならメインに頼んでくれ」）を自分の吹き出しで発話した後、メイン右クリックと同じ挙動に遷移する（サブの吹き出しは表示したまま）。
- 項目（実装準拠）: モード切替（low ⇔ advanced）/ 静音モード切替 / ポモドーロタイマー（§4.4.5、専用パネルを開く）/ テキスト読み上げ / 設定を開く / ウインドウを隠す / 終了。ゴースト/シェル切替は設定パネルから行う。
- 閉じる: 項目実行・Esc・メニュー外クリック。新しい発話（自発発話等）でも置き換わる。メニュー表示中の左クリックは「閉じる」専用（入力導線 §4.3.1 やつつきには流さない）。
- キャラ以外の右クリックは何もしない（WebView 既定メニューの抑止のみ）。
- 辞書に `menu_prompt` が無いゴーストでは、セリフ無しでメニューのみ表示（サブ右クリックは直接メインのメニューへ）。

### 4.4 存在感系イベント

#### 4.4.1 起動挨拶
- 初回 = `events.first_boot`（オンボーディング兼）。
- 2 回目以降 = `events.boot`（時間帯条件 / 日付条件で分岐）。
- 静音モードでも起動挨拶は鳴らす。

#### 4.4.2 終了挨拶
- トレイ「終了」時に `events.quit` を再生してから exit。
- 強制終了では当然鳴らない。

#### 4.4.3 放置反応
- 60 秒間隔チェック、最終操作から 30 分で 1 回 idle 発火。
- 静音中・busy 中は持ち越し。
- ユーザー操作でリセット。

#### 4.4.4 ランダムトーク（独り言）★
- 一定間隔でキャラが独り言を発話。
- **既定間隔: 10 分**（v0.0.3 の既定 0=無効から変更）。
- 0 設定で無効化可能。
- advanced モードでは LLM 生成 + キャッシュ補充。
  - 発話のたびに LLM を呼ばず、**まとめて複数ストックし、キャッシュが尽きたら補充**する（LLM 呼び出し頻度を独り言の発話頻度より低く保つ）。ストックは**再起動をまたいで保持**する（起動のたびに補充が走らないこと）。
  - 補充時、時事ネタ（§4.4.6）が有効なら**その材料を一緒に渡して織り込む**（有効でなければ独り言のみ。追加の LLM 呼び出しはしない）。
  - **ストックした文にも生成時刻を持たせ、発話時に鮮度を判定する**（時事ネタを含む文の失効は §4.4.6）。
  - コスト管理は advanced 会話と同じ扱い（月額上限・自動降格に従う）。降格中・LLM 障害時は low と同じ辞書経路にフォールバックする（本節の low 側の挙動と同じ）。
  - **履歴クリア（§4.5.5）の対象**に含める。
- low モードでは辞書 `random_talk` から選択。
- 静音条件下では発火しない。

#### 4.4.5 ポモドーロ ★
- 集中(work) → 休憩(break) をラウンド数だけ繰り返す。
- 既定 25 分 / 5 分 / 4 回（設定変更可）。
- 集中中は静音扱い（ランダムトーク・放置反応を止める）。一時停止中も静音扱いを維持。
- 辞書 events: `focus_start` / `focus_end` / `break_end` / `pomodoro_done`。
- **focus_end / pomodoro_done では「ねぎらいの台詞」を充実**させる（辞書側で台詞バリエーション拡充）。
- バッジ表示（画面上部中央、`.solid`）。進行状況（フェーズ・残り時間・ラウンド）を常時表示。一時停止中はその旨を示す。
- **専用 GUI パネル（`.solid`、アプリ内オーバーレイ。独立ウインドウは作らない）から操作する**:
  - **開始**: idle 時にタイマー開始。
  - **停止（一時停止 / 再開）**: 進行中のカウントダウンを一時停止し、再度押すと同じ残り時間から再開する（**新設**。従来の「レジューム無し」から変更）。
  - **中断**: タイマーを破棄して idle に戻す（従来の stop 相当）。
  - **閉じる**: パネルを閉じる。タイマーが動作中なら継続し、バッジで表示する。
  - **時間設定**: 集中/休憩/ラウンド数をパネルで編集。値は既定設定（`pomodoro_work_min` / `pomodoro_break_min` / `pomodoro_rounds`）と共有し保存される（設定パネルと同一の値）。進行中は編集不可（次の開始時に反映）。
- **右クリックメニューは「ポモドーロタイマー」1 項目**でこのパネルを開く（従来の「開始」「停止」直接項目は廃止）。トレイからの制御は現状維持。

#### 4.4.6 時事ネタ雑談
- RSS（既定 Google ニュース検索）から興味分野の見出しを取得。
- **advanced モードの独り言生成のついで**に織り込む（追加 LLM コストなし。§4.4.4 のキャッシュ補充に相乗りする）。
- **賞味期限は 1 週間**。時事ネタは鮮度が価値なので、次の 2 点で担保する:
  - **織り込み時**: 取得から 7 日を超えた見出しは材料に使わない。
  - **発話時**: 独り言のストックは補充から時間が空いて発話されうるため（§4.4.4）、**発話の時点で見出しが取得から 7 日を超えていたらその文を使わず、辞書の独り言に差し替える**。古いネタを口に出さないことを優先する。
- 暗い見出し（事故・災害等）をフィルタ。
- low モードでは時事ネタ無し。
- 取得間隔は 30 分以上にクランプ。
- 興味分野は `interest_topics` テーブル（user_profile との統合は Phase 2 検討）。
- **既定オフ**・オンボーディングで明示同意必須。

#### 4.4.7 更新通知
- `update_feed_url` の JSON を起動時に取得。
- 現バージョンより新しければ辞書 `update_talk` で**一度だけ**ゴーストが通知。
- 既定オフ（フィード URL 未設定なら無効）。

#### 4.4.8 静音モード
- `quiet_mode` 設定 ON で自発的な発話を停止。
- ユーザー操作への応答は通常通り。
- 起動挨拶・終了挨拶は静音下でも鳴る。
- トレイ・右クリックメニューから切替。

#### 4.4.9 フルスクリーンアプリ自動静音 ★
- `auto_quiet_fullscreen` 設定 ON で、フォアグラウンドウインドウがモニタ全面なら自動静音扱い。
- ゲーム・プレゼン・動画視聴中は黙る。
- Win32 API で検知、デスクトップシェル（Progman/WorkerW）は除外。
- **既定 OFF**（v0.0.3 の既定 ON から変更、ユーザーが明示的に ON）。

### 4.5 音声・補助

#### 4.5.1 TTS ★
- **2 エンジン体制**:
  - **voicevox_core**（既定、必須）: 公式プリビルド C API を libloading で実行時ロード。CPU合成・無サーバ。
  - **Irodori-TTS**（オプション、上級）: サイドカー同梱、GPU必須、不安定許容。
- **共通動作**:
  - 「ユーザーが別途サーバー/アプリを起動する必要はない」を両方とも満たす。
  - 失敗時は声なしで会話継続（アプリは落ちない）。
  - 全発話経路（応答・独り言・つつき・撫で・挨拶・時事ネタ・リマインダー）に乗る。
- **voicevox_core 詳細**:
  - 資産（dll / onnxruntime / Open JTalk 辞書 / .vvm）は **初回 DL** で取得
  - 規約同意必須、GitHub PAT で API レート制限緩和（任意）
  - クレジット表示「VOICEVOX:話者名」を画面下端中央に常時表示（VVM 規約準拠）
  - 事前 init（boot 時・設定変更時）で初回発話のラグを解消
- **Irodori-TTS 詳細**:
  - Python + PyTorch + CUDA + モデルをサイドカー同梱方式で配布
  - **初回 DL 方式**（軽量インストーラ → 設定で有効化時に 5〜10GB DL）
  - GPU 検出失敗時は voicevox_core にフォールバック + ユーザーに通知
  - **参照音声クローン方式**（声質の一貫性を確保）
    - 参照音声がある場合: 保存済み参照音声でクローン合成
    - 参照音声が無い場合: キャプション（VoiceDesign）から参照音声を生成 → 保存 → 以降はクローン合成へ切替
    - 参照音声の供給源は**自前生成のみ**（外部音声の取り込みは行わない＝著作権リスク回避）
    - 参照音声の再生成（キャプション変更で作り直し）・削除 UX は Phase 2 で設計
  - **漢字→ひらがな前処理**: Irodori-TTS は漢字の発話精度が不安定なため、合成前にテキストをひらがなに変換する前処理を入れる
    - 変換手段の候補: voicevox_core が同梱する Open JTalk 辞書の流用 / 形態素解析ベース（Phase 2 で選定）
    - 変換漏れ・誤読は許容（完全な読み付与は目指さない）
    - voicevox_core エンジン側ではこの前処理は不要（内部で読み解析を行うため）
  - **絵文字アノテーションの保護**: Irodori-TTS V3 は入力テキスト中の特定絵文字（45 種、upstream `EMOJI_ANNOTATIONS.md` 準拠）で感情・スタイル・効果音を制御できる。前処理はこれらの絵文字を除去せず、位置を保ったまま合成テキストに残す
    - 対応絵文字は upstream の一覧をホワイトリストとして保持（対応外の絵文字は従来通り前処理で落ちる）
    - 同一絵文字の連続（強調）も保持する
    - voicevox_core エンジン側では絵文字は解釈されないため保護しない（従来通り読み飛ばし）
  - **詳細実装は Phase 2 で**: Python ランタイム配布方式 / モデル配布 / サイドカープロセス管理 / GPU 検出 / 参照音声管理（生成・保存・再生成・削除） / **漢字→ひらがな前処理の実装方式** / 設定UI
- 設定:
  - エンジン選択（VOICEVOX / Irodori-TTS）
  - 話者選択（メイン / サブ）
  - 話速・音量
  - Irodori-TTS のキャプション入力（参照音声の初回生成・再生成に使用）
  - Irodori-TTS の参照音声管理（生成・再生成・削除）
  - 規約同意・GitHub PAT（voicevox_core 用）
- 共通の再生制御:
  - 逐次キュー（main → sub が重ならない）
  - 新発話で interrupt
  - WebView2 自動再生ポリシー対策（`--autoplay-policy=no-user-gesture-required` + ウォッチドッグ）

#### 4.5.2 STT（廃止）★

- 将来必要になれば §6 将来課題から検討。

#### 4.5.3 ツール（時刻・リマインダー・クリップボード）
- `tools_enabled` トグルで 3 つまとめてオンオフ（個別切替なし）。
- advanced モード前提。
- **改訂予告（v0.2）**: リマインダーは §4.6.1 で本格化し、`tools_enabled`・advanced から独立した常時ローカル機能へ移行する（§4.2.1 不変条件）。本節のリマインダー記述は移行完了までの現行仕様。
- **時刻注入**: 「今何時?」「今日何曜日?」に LLM が答えるための system prompt 補強。
- **リマインダー**: 「N 分後に教えて」→ タイマー登録 → 時間で発話（**静音中も鳴る**）。
- **クリップボード補助**: 入力欄の📋ボタン押下時のみ読み取り、「翻訳して」「要約して」「説明して」等に応える。**📋 ボタンは `tools_enabled = false` のとき非表示**。
- 既定オフ。

#### 4.5.4 自動起動
- OS ログイン時の自動起動（`tauri-plugin-autostart`）。
- 既定 OFF、ユーザーが設定で ON。

#### 4.5.5 データエクスポート / 履歴クリア
- **エクスポート**: 会話ログ・記憶（任意）・コスト履歴を JSON でダウンロードフォルダに書き出し。
- **履歴クリア**: 会話ログ・独り言キャッシュを削除。記憶を含めるかはオプション。
- 設定パネルから手動実行。

#### 4.5.6 ゴースト・シェル切替 ★
- **ゴースト切替時のシェル追従（v0.5.1）**: ゴーストを切り替えたとき、そのゴーストの `ghost.json` が `default_shell` を宣言していればシェルもそこへ追従する。
  - **同じ操作でユーザーがシェルも明示的に変えた場合は、ユーザーの選択を優先する**（設定画面はゴーストとシェルを同時に保存するため）。
  - 宣言が無い / 実体のシェルが存在しない場合は追従しない（切替先が無いと起動できなくなるため）。
  - 背景: v0.4.1 まで `default_shell` は出荷されているのに読まれておらず、DnD で入れたゴーストが自前シェルを連れてこなかった。
- 設定パネルで複数のゴースト・シェルから選択切替。
- **ホットリロード（ファイル編集の即時反映）は廃止**。作者は再起動して確認する。
- **検討: ドラッグ&ドロップ展開**
  - ゴースト/シェルの zip ファイルやフォルダをアプリにドロップ
  - 自動的に `ghosts/<id>/` or `shells/<id>/` に展開
  - 「再起動して使えるようにする」を明示提示
  - 実装可否・対応形式は Phase 2 で決定（zip 中身検証・上書き確認 UX 含む）

#### 4.5.7 チャットログパネル
- 簡易ログパネル（開閉式、`.solid`）。
- `get_chat_log(limit)` で新しい順 N 件取得。
- 設定パネルから開閉。

#### 4.5.8 テキスト読み上げツール（詳細: docs/text-reader-spec.md、台本形式: docs/script-reader-spec.md）
- 右クリックメニュー「テキスト読み上げ」で専用パネルを開く。パネル**表示中のみ**、
  `.txt` ファイルの DnD を受理してメインキャラの声で読み上げる（複数 DnD は先頭 1 件）。
- 入力: `.txt` のみ、1MB 上限、UTF-8 (BOM 有無) / Shift_JIS 自動判定。
- 長文対策: 文境界優先・最大 120 トークンのチャンク分割（`reader_load_text` コマンド）。
  Irodori 絵文字アノテーションはどの分割経路でも分断しない。
- 合成はチャンクごとに既存 `synthesize_voice`（= 前処理・絵文字保護・フォールバックが適用）。
  再生は先読み 1 のパイプライン、失敗チャンクはスキップして件数表示。
- 読み上げ中は自発発話を抑制（`set_reading_active` コマンド → 静音判定に追加）。
  リマインダーの静音特例は従来通り。停止ボタン / パネルクローズで即停止。
- 追加コマンド: `reader_load_text(path) -> Vec<ReadingChunk>` / `set_reading_active(active)`。
  `synthesize_voice` に `caption: Option<String>` を追加（Irodori 実モデル経路のみ使用）。
- **台本形式対応**: `.md` 台本（`speakers` / `lines` ブロック必須 + `defaults` 任意）も
  受理する。話者 ID を ugg の slot（main / sub）へマッピングし、行ごとに話者を切り替える。
  行ごとの `speed`（再生側 playbackRate に合成）、`caption`（声質・演技指示。Irodori 実モデル
  時のみ有効、無効環境ではパネルに注記を表示して読み上げ）、`pause_after`（行間の間）を制御。
  不正な台本はロード時に全行検証して fail-fast（部分再生しない）。詳細は docs/script-reader-spec.md 参照。

### 4.6 日常支援（v0.2 実装済み）★

2026-07-12 の新機能評価（評価軸と経緯は §6 冒頭）で採用した Tier S 機能群。**「ユーザーの生活状況を軽く把握し、必要なときだけキャラクターとして声をかける」**方向へ ugg を拡張する。**実装設計（DB・コマンド・モジュール・マイルストーン）は [docs/daily-support-design.md](daily-support-design.md) を正とする**（Phase 2 成果物、reviewer 反証済み）。全機能に共通する原則:

- **AI 非依存**: 基盤部分は low（ローカル・決定論）で動作する（§4.2.1 不変条件）。advanced は解釈・提案の上乗せ。
- **キャラクターが配達する**: 通知・催促はリスト UI ではなくゴースト発話が主経路（§3.1）。**通知・催促・進捗確認はサブが主体**、応答・受付はメイン（サブ無しゴーストではメイン兼務、§4.1.1 の縮退規則に従う）。
- **邪魔をしない**: すべての自発的通知は発話ガバナンス（§4.6.3）に従う。

#### 4.6.1 統合リマインダー ★
- 現行の相対時刻（§4.5.3「N 分後」）に加えて対応する:
  - **絶対時刻**（「18時に洗濯物」）
  - **日付・相対日**（「明日の朝ゴミ出し」）
  - **曜日指定と繰り返し**（毎日 / 毎週X曜）
  - **スヌーズ**（発火時に「あとで」を選べる。既定 10 分、Phase 2 で確定）
  - **完了 / 未完了の管理**と**通知履歴**
- 「朝 / 昼 / 夕方 / 夜」の既定時刻マッピングを持つ（設定変更可）。low の決定論パーサが解釈する語彙・書式の確定は Phase 2。
- **`tools_enabled`・advanced から独立し、常時ローカル動作**（§4.2.1 不変条件）。既存の「静音中も鳴る」特例は維持。
- 通知はゴースト発話（サブ主体）を主経路とし、発話不能時のフォールバックとして
  **アプリ内トースト**（§3.1 の二段構え）。
  - **OS 通知（Windows トースト）は現状の実装範囲外**。フォールバックはアプリ内の帯であり、
    ウインドウが見えていなければ届かない。OS 通知の採否は §6.6 の将来課題とする。
  - したがって **ウインドウが不可視の間は「未達」として保留する**。到達扱いにすると、
    トレイに隠している間に期限が来た単発リマインダーが画面に何も出ないまま完了扱いで消える。
    保留は 10 秒ごとに再試行され、2 件以上溜まったら「『X』ほか N-1 件」に集約して 1 発話にする
    （起動時の取りこぼし回収と同じ扱い）。
  - 可視性は**到達判定**であってガバナンスではないため、`can_deliver` には段を足さない。
- advanced 上乗せ: 曖昧表現の解釈（「夕方になったら薬局」）、会話中の予定からの登録提案、通知文の生成、未完了の再通知判断。
- 登録導線はチャット入力欄の自然文（現行踏襲）。一覧・完了・削除・スヌーズの管理 UI は `.solid` パネル方式（ポモドーロパネル §4.4.5 と同型）を想定、配置は Phase 2。
- データスキーマ（既存 `reminders` テーブルの拡張 or 新テーブル）・コマンド契約は Phase 2。

#### 4.6.2 ToDo・日課管理 ★
- **期限が厳密でない作業**を管理する（厳密な時刻を持つものはリマインダー §4.6.1 の領分）。
- low:
  - 追加・完了・削除
  - 分類は **今日 / 今週 / いつか** の 3 区分のみ
  - **繰り返しタスク（日課）**: 完了しても翌日（翌週）に復活する
  - 優先度は **高 / 普通 の 2 段階のみ**
  - 未完了件数の表示（表示位置・形式は Phase 2）
  - 起動時・終了前の確認（発話ガバナンス §4.6.3 に従う）
- **キャラクター関与が本体**（一覧 UI は従属）:
  - 朝: 件数の告知（「今日は 3 件あるよ」）
  - 長時間未完了: **責めない**催促（サブ主体、頻度はガバナンス管理）
  - 完了時: 労いの反応
  - 複数日滞留: 再整理の提案
  - 対応する辞書 events キーを新設（命名・種類は Phase 2）
- advanced 上乗せ: 会話からの ToDo 抽出提案、タスク分割、優先順位・「今から何をすべきか」の提案、実行可能な量への絞り込み。
- **非採用（過剰 PM 化の防止）**: サブタスク階層・プロジェクト・タグ・工数管理。

#### 4.6.3 状況対応型自発発話と発話ガバナンス ★
- 現行の時間間隔ベースの自発発話（§4.4.3 放置反応・§4.4.4 独り言）に、**ユーザーの状況に反応する発話カテゴリ**を追加する（既存の置換ではない）。
- low の判定材料（**すべてローカルで完結**。ウインドウ内容・キー入力・スクリーン内容は見ない）:
  - 現在時刻 / PC 連続利用時間 / アイドル時間（既存基盤）
  - フルスクリーンアプリの有無（既存 §4.4.9）
  - バッテリー残量 / 音量・ミュート状態
  - ポモドーロ状態（既存）/ リマインダー・ToDo の状態（§4.6.1 / §4.6.2）
- 発話カテゴリの例: 休憩促し（連続利用）・深夜利用の声かけ・バッテリー低下・未完了フォロー。**提案 #10「PC 利用時間・休憩支援」は独立機能とせず本カテゴリに統合**。医療的判断・診断はしない。
- **発話ガバナンス（本機能の前提条件であり、後付けにしない）**:
  - **カテゴリごとのオン / オフ**（新カテゴリの既定は控えめ = 原則 OFF。既定値の確定は Phase 2）
  - **全体の最低発話間隔**
  - **夜間静音（時間帯指定）**
  - 既存の抑制系と統合: フルスクリーン自動静音（§4.4.9）・静音モード（§4.4.8）・ポモドーロ集中・読み上げ中
  - **フィードバック**: 「いまのは邪魔」をワンアクションで伝えられ、該当カテゴリの頻度が自動で下がる
- advanced 上乗せ: 直前の会話・最近の作業傾向の考慮、発話必要性の判断、同内容の繰り返し回避、キャラ別の言い回し生成。**ただし発話可否の最終ゲートは常に low 側のガバナンスが握る**（LLM 判断でガバナンスを越えて喋らせない）。

#### 4.6.4 カレンダー参照（読み取り専用）★
- **ICS（ファイル / URL）の読み込みのみ**。書き込み・双方向同期・OAuth 認証は非採用（将来課題 §6.6）。
- low:
  - ICS 取得とローカルキャッシュ（オフライン時はキャッシュを表示）
  - 今日・明日の予定表示
  - **開始 N 分前のゴースト通知**（既定 15 分、変更可）と終日予定の通知
- プライバシー（§3.3 準拠): URL はユーザーが明示設定・**既定オフ**・外部へ送るのは ICS 取得リクエストのみ。
- advanced 上乗せ: 「今日の予定は？」「次の予定まで何分？」への応答。空き時間の抽出・ToDo の予定割当提案は将来（§6.2 以降）。
- Tier A「朝・夜の定例会話」（§4.7.1）の主要材料になる前提で設計する。

### 4.7 定例会話と天気・生活情報（v0.3 スコープ・**実装済み** 2026-07-24）★

2026-07-18 のスコープ選定（ユーザー裁定）で Tier A（§6.2）から採用した第 2 弾。**「1 日の始まりと終わりに、キャラクターがその日の情報をまとめて話しかけてくる」同居感の完成形**。Tier S（§4.6）のデータ（予定・ToDo・未完了）と本節の天気を材料にする。実装設計（API 選定・DB・モジュール・マイルストーン）は **Phase 2 設計書（regular-talk-design.md として新設予定）**を正とする。§4.6 の横断原則（AI 非依存 / キャラクターが配達する / 邪魔をしない = 発話ガバナンス §4.6.3 準拠）は本節にもそのまま適用する。

#### 4.7.1 朝・夜の定例会話 ★
- **朝と夜の 1 日 2 枠**、それぞれ独立に有効/無効・時刻・有効曜日をユーザー設定できる（既定: **両方オフ**のオプトイン。有効化時の既定時刻は朝 8:00 / 夜 21:00、曜日は毎日）。
- **発火規則**: 「設定時刻きっかり」ではなく、**設定時刻を過ぎて最初にユーザーが PC を使っているとき**に 1 回配達する（朝 8:00 に PC が点いていない日常を許容する）。「使っている」の基準は **OS 全体の入力アイドル**（§4.6.3 の連続利用検知と同系統）が閾値未満であることとし、**連続利用中でも設定時刻経過後の最初の判定で発火する**（アイドル→アクティブの遷移待ちではない。閾値は Phase 2）。ただし**設定時刻から一定時間で当日分は失効**する（既定 6 時間・確定値は Phase 2 設計書。終日 PC を触らず夜に開いた日に朝の定例が夜間へずれ込んで配達される「夜の『おはよう』」と、朝・夜の連続配達を避ける）。1 枠 1 日 1 回。日付が変わったら未配達分は消化（翌朝に昨日の朝の分を言わない）。
- **中身（low = 定型フォーマット。材料の集約はローカルで完結）**:
  - 朝: あいさつ + 今日の予定（カレンダー §4.6.4）+ 今日の ToDo・日課の件数（§4.6.2）+ 未完了リマインダー（§4.6.1、**直近の数件に絞る** — 全件読み上げをしない。絞り方は Phase 2）+ 今日の天気（§4.7.2、有効時のみ）
  - 夜: ねぎらい + 今日の完了実績（ToDo 完了数）+ 未完了の持ち越し + 明日の予定 + 明日の天気（有効時のみ）
  - 材料が空の項目は黙って省く（空リストの読み上げをしない）。全部空でも短いあいさつは成立させる。
- **§4.6.2「朝の件数告知」との統合**: 定例会話（朝）が有効な間は、朝の ToDo 件数告知を定例会話に**吸収**し単独では発火させない（二重告知の禁止）。吸収時の 1 日 1 回管理は定例会話側で行い、**定例会話が当日配達されなかった日は件数告知も出ない**（許容する）。定例会話（朝）が無効なら従来どおり。
- **ガバナンス**: **朝・夜それぞれ独立の発話カテゴリ**として追加する（どちらも Ambient。段 3 のカテゴリ OFF が各枠のトグルに対応する）。ハード静音・夜間静音に従い、抑制中は**同日内で再試行**する。**夜間静音が優先**のため、枠の設定時刻を夜間静音帯内に置くとその枠は配達されない — 設定 UI はこの重なりを検知して警告する。🔕 フィードバックは各枠を対象とし、**3 回で当該枠のトグルを OFF にする**（1 日 1〜2 回の定例のため、Situation* の間隔バックオフ（§4.6.3）は適用しない）。
- advanced 上乗せ: 同じ材料を会話形式の言い回しに整形する（**材料の選定と発話可否は常に low が確定**し、LLM は言い回しのみ。§4.6.3 の原則）。
- 辞書 events キーを新設（朝/夜の導入・締め。命名は Phase 2）。サブ主体の原則（§4.6 冒頭）に従う。

#### 4.7.2 天気・生活情報 ★

「生活情報」は将来の傘だが、**本 v の実体は天気のみ**（それ以外を本節に足す場合は spec 改訂を伴う）。

- **キー不要・無料の公開気象 API** から予報を取得する（サービス選定は Phase 2。API キーをユーザーに要求しない）。**選定 API の利用規約に従い出典表示を行う**（§4.5.1 の VOICEVOX クレジットと同型の義務）。規約・可用性の条件を満たす API が確保できない場合は、本機能を無効のまま出荷してよい（任意の API キー方式へのフォールバックは将来判断）。
- **地域は手動設定・既定オフ**（§3.3 準拠・**設定行為をもって同意とみなす**）。地名検索から緯度経度を設定できる UI を持つ。外部へ送るのは気象 API への座標・地名クエリのみで、**送信する座標は市区町村粒度（目安: 小数 1 桁 ≒ 約 11km）に丸める**。
- low:
  - 予報の取得とローカルキャッシュ（定期 + 定例会話の直前。オフライン時はキャッシュを使い、**取得から一定時間を超えた古いキャッシュは使わず天気項目を省く** — 閾値は Phase 2、既定 6 時間目安）
  - 定例会話（§4.7.1）への材料提供: 今日/明日の天気・気温・降水確率
  - **降雨の一言**: 当日に降雨が見込まれる朝に一言知らせる状況発話カテゴリ（§4.6.3 に追加、既定オフ）。カレンダーに外出予定（当日の時刻付き予定）がある日は言い回しを強める。**朝の定例会話が有効な間は定例会話（天気項目）に吸収**し単独では発火させない（§4.6.2 の吸収と同型・二重告知の禁止）
- **本 v の非採用**（将来課題 §6.6）: 気象警報・注意報の取得、気温差アラート、週間予報の読み上げ、複数地点。
- advanced 上乗せ: 「今日の天気は？」への応答（キャッシュを会話材料に注入）。

## 5. 配布

- **形式**: NSIS インストーラ（`currentUser` モード、日本語ロケール）。
- **初回起動時 DL** が必要なもの:
  - voicevox_core 資産（c_api / onnxruntime / dict / models 合計数百MB）
  - Irodori-TTS（オプション、Python+PyTorch+CUDA+モデル 数GB）
- **インストーラサイズ目標**: 5〜10 MB（資産は全部初回DL）
- **インストール先**:
  - 実行ファイル: `%LOCALAPPDATA%\ugg\`
  - データ: `%APPDATA%\ugg\`（DB、TTS 資産、ログ）
    - ログは `ugg.log`（追記、2MB で `ugg.log.1` へ 1 世代退避）。パニックと、これまで `eprintln!` で stderr にしか出していなかった診断を残す。**リリース版はコンソールが無く、以前は 1 行も残らなかった。**
  - keyring: OS 標準（Windows Credential Manager）
- **更新**: 自動更新は無し、`update_talk` 経由のゴースト案内のみ（手動 DL & 再インストール）。

## 6. 将来課題とロードマップ（2026-07-12 再構成）

新機能提案の評価に基づく優先順位付きロードマップ。**評価軸はユーザーにとっての有用性**（利用頻度 / 代替不可能性 = OS・スマホ・既存アプリに対する限界価値 / キャラクター相乗 = キャラが配達することで価値が増すか / 負効用リスク）であり、**実装難度は評価軸にしない**。方向性: 汎用 AI アシスタント化ではなく「生活状況を軽く把握し、必要なときだけキャラクターとして声をかける常駐アシスタント」。

### 6.0 現在のスコープ: v0.5「宣言どおりに動く」（2026-09-02 確定）★

**方向性は「契約と実装を一致させる」**。新機能はゼロ。

契約（spec / 出荷資産 / architecture）は宣言されているのに実装が繋がっていない箇所が
**12 件**見つかった。既知の 3 件（keyring の store feature 未指定・`persona` の serde 未宣言・
口パクの呼び出し元ゼロ）と同じ型で、いずれも**「それらしい名前のテスト」や「成功を返す UI」が
発覚を遅らせている**という共通構造を持つ。3 件では偶然でも、12 件は構造である。

| # | 項目 | 位置づけ |
|---|---|---|
| 1 | **`persona` / `prompt` の配線** | `ghosts/*/ghost.json` は `characters.*.persona` / `prompt.style_notes` / `prompt.max_chars_per_line` を出荷しているのに `GhostManifest` がフィールドを宣言しておらず **serde が黙って捨てている**。`advanced.rs` はキャラ説明をハードコード。**advanced の LLM はキャラの人格を名前以上に何も知らない**＝差別化の片翼が機能していない。チャット / 独り言 / 定例会話整形の 3 経路に注入する |
| 2 | **月額上限を本当に効かせる** | §4.2.7 と実装の乖離。降格は `DEGRADE_HOLD_SECS = 300` で失効し `recover_if_due` が**時計しか見ない**ため、上限超過は実質「5 分の一時停止」。`cost_limited_emitted` が立ちっぱなしで再降格も再告知も起きない。**§4.2.7 は「次月リセットで復帰。」と既に定めており、これは仕様判断の保留ではなく未修正のバグ**（v0.4.1 で見送った際の理由「spec に記述が無い」は誤り）。3 経路を LLM 呼び出しの**前**に同一ゲートへ通し、告知済み年月を永続化し、既定辞書に `cost_warning_80` / `cost_limit_exceeded` を追加し、当月使用額を表示する |
| 3 | **記憶の閲覧・追加・削除 UI** | §4.2.5 の ★ 要件。`get_profile` / `add_profile` / `delete_profile` は実装済みで invoke_handler にも登録されているが、**フロントからの呼び出しが 0 件**。origin（auto / onboarding / manual）を表示し「会話から自動で覚えたもの」が分かるようにする |
| 4 | **配達の可視性判定** | §4.6.1 が約束する「Windows トースト」のフォールバックは実体が**アプリ内の 6 秒帯**で、OS 通知プラグインは無い。`app.emit` は非表示でも Ok を返すため `DeliveryOutcome::Toast` が到達扱いになり、**トレイに隠している間に期限が来た単発リマインダーが無言で完了扱いになる**。不可視なら `Deferred` を返す（`Deferred` と 60 秒再試行は既に配線済み）。判定は `governance::can_deliver` に段を足さず `deliver.rs` の到達判定側に置く（二重ゲート禁止の維持）。OS トーストの採否は §6.6 へ送る |
| 5 | **再発を止める土台** | ログ（**§5 配布**が `%APPDATA%\ugg\` の中身として明記済み。現状は出力先が無く、リリース版では 1 行も残らない）と契約テスト 2 本。① 出荷資産のキー集合と Deserialize 構造体の突合（**これがあれば項目 1 は出荷時点で落ちていた**）② Rust が引く辞書キー ⊆ 既定辞書（同じく `cost_warning_80` の欠落が落ちていた）。②は手書きリストにせず列挙をコンパイラに担保させる形でのみ入れる — 手書きリストの契約テストは偽の安心を新しく作るだけ |

**着手順は 1 → 2 → 3 → 4 → 5。** ただし項目 1 の着手前に、persona を手で system prompt に
入れて advanced で 20 往復試す（1 時間）。良くならない、または LLM が persona 文をなぞって
自己申告し始めるなら、問題は配線ではなくプロンプト設計であり、スコープを組み直す。
あわせて `ghost.json` の persona 文と既定辞書の low 台詞の口調を突合する（割れていると
low と advanced が別人になる）。

**v0.5 に入れないもの**: `recall`（契約は spec §4.2.6 / architecture §6.2 / DB スキーマ /

### 6.4 Tier C — 後期（識別性を薄める / リスクが価値を上回る）

| 項目 | 要点 |
|---|---|
| 画面 OCR・画面理解 | PowerToys 等で代替可能。採用する場合は範囲選択・送信前プレビュー・クラウド送信明示・自動マスクを必須条件とする |
| ファイル検索・ランチャー | 前面に出すと「キャラクターアプリ」から「ランチャー」に寄りすぎる。補助機能に留める |
| ゴースト拡張基盤の高度化 | 権限マニフェスト・署名/ハッシュ検証・対応バージョン明示。第三者ゴースト流通が現実になってから。**外部ゴーストへの任意コード実行は許さない** |
| スマートホーム連携 | 構想のみ |
| **伺かゴースト（SHIORI 辞書）の変換** | **非目標（2026-08-31 裁定）。** 実装しない。技術的に不可能だからではなく（里々は宣言的で構造がほぼ 1:1 に対応する）、**得られるものと失うものが釣り合わないため**。① ugg の events 約 40 キーのうち伺かから供給源があるのは約 20 で、それは汎用マスコットの側。`focus_*` / `pomodoro_done` / `todo_*` / `reminder_*` / `situation_*` / `calendar_upcoming` / `regular_*` / `weather_*` と `system_messages` / `input_match` / `fallback` / `recall` / `monologue` は**供給源が存在せず**、ugg の存在理由にあたる側が結局手書きになる。② 辞書の `Line` は 1 応答 = 最大 2 発話だが、伺かのトークは話者が 4〜12 回入れ替わる脚本で、**その往復のリズム自体がキャラの個性**。スキーマの表現力差なので実装では改善しない。③ ゴーストは作者が書いた文章そのもので、条件分岐を潰す変換は「作者が設計したいつ何を言うか」を壊す。**著作権法 50 条により私的複製（30 条）は著作者人格権に及ばず**、同一性保持権の論点は手元利用でも消えない。界隈の許諾も作者ごとに真逆で機械判定できない。**例外は「原作者本人が自分のゴーストを移す」場合のみ**（他人のゴーストを変換する道具としては作らない） |
| **他人のキャラの人格記述の自動生成** | **レッドライン（2026-08-31）。** 第三者ゴーストの辞書から `persona` / `style_notes` を機械生成して LLM に演じさせる導線は作らない。原作者が一度も書いていない台詞を、そのキャラの名前で、原作者の訂正手段なしに生成し続ける装置になるため。**§4.2 の persona 配線を行う場合も、この線を先に確定させてから着手する** |

### 6.5 縮小・凍結（現行機能で優先度を下げる）

| 項目 | 方針 |
|---|---|
| 高品質 TTS（Irodori）の追加拡張 | 新音声モデル・演技機能の追加は凍結。バグ修正・安定化のみ |
| 台本読み上げの高度化 | 安定化を優先。大規模な編集機能・音声制作機能は後回し |
| ニュース機能の拡大 | 現状維持。本人に直接関係する情報（天気・予定・ToDo）を優先する |
| 汎用 Web 調査 | advanced 会話から明示的に要求された場合だけ起動する補助に留める |
| **伺か資産の変換ツール（`crates/nar2ugg/`）** | **凍結（2026-08-31 裁定）。シェル変換・ゴースト変換とも行わない。** scaffold（CLI・モジュール境界・出力契約は確定、変換ロジックは `todo!()`）のまま停止し、実装を進めない。ゴースト変換の不採用理由は §6.4。シェル変換は権利・技術の両面で成立するが、**ugg 本体の完成度を優先する判断**により着手しない。crate は削除せず、README 冒頭に凍結中である旨を明記して残す |
