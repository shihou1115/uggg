# ugg v0.5.5 — 環境ぜんぶが更新の対象になる

**リリース日**: 2026-09-14
**タグ**: `v0.5.5`
**テーマ**: v0.5.4 が作った更新経路を、実行環境を構成するもの全部へ広げる。**新機能ゼロ。**

## なぜこの回だったか

当初 v0.5.5 は「Irodori-TTS を v3 → v4.1-Small へ差し替える」だった。
**反証レビュー（別 Opus）が前提を崩した**ので、v0.5.4 と同じ形で分割した（差し替えは v0.5.6）。

1. **更新判定は固定 URL 4 本しか見ていなかった。** `outdated_pins` は `current_pins()` としか
   突き合わせないので、`transformers<5` のような名前付き要件の版を変えても `outdated` は空。
   **transformers 4→5 を届ける手段が 1 本も無かった。** `installed.json` の `resolved`
   （実際に入った版）は記録しているのに、判定に一度も使っていなかった。
   v0.5.4 は「モデルが対象外」と書いたが、**対象外なのはモデルだけではなかった。**
2. **モデル ID は毎起動で上書きされる `sidecar.py` にあった。** `install_sidecar_script` が
   無条件にコピーするので、ID を変えた瞬間コードだけ新しくなって重みが無い。`decide_fallback` が
   ほぼ全部を VOICEVOX へ流すので、**「届かない」ではなく「静かに壊れる」**。
3. **import ゲートは依存の版ずれを原理的に検出できない。** `transformers.initialization` の
   import は `PretrainedTextBackbone.__init__` の try/except の中にある。

**土台が無いまま差し替えれば、既存ユーザーには届かないうえに黙って壊れる。** 順序はここで決まった。

## 入れたもの（4 項目）

| | 内容 |
|---|---|
| 1 | **落ちた理由が残る（2 経路とも）** — サイドカーの stderr を捨てずに `ugg.log` へ（`[irodori:py]`）。合成失敗の理由も、発話テキストを伏字にしたうえで毎回ログへ |
| 2 | **孤児サイドカーの掃除** — 強制終了で残ったサイドカーを次の起動で止める。台帳 `sidecars.json` を追加し、**pid もポートも撃たず、`/health` の応答の形で自分のものと確かめてから**止める |
| 3 | **更新の対象を広げる** — 名前付き pip 要件の版差と、モデルの repo / revision。モデルの正本を Rust 側へ移し、revision ごとに置き場所を分けて**旧モデルを上書きしない** |
| 4 | **更新中の発話を止める** — 更新の実行中は新しいサイドカーを立てず、VOICEVOX で話す |

**見送り 1 件**: スコープで掲げた「成否の条件を『import できる』から『1 回合成できる』へ」は、
依存の major 移行を伴う v0.5.6 で入れる（今回は要件・モデルの版を変えていないので、
入れ直しの実害が出る経路が無い）。

### 実機検証の直前に 1 件 — 記録に欄が無いものを「古い」と扱っていた

項目 3 をそのまま入れると、**v0.5.4 から上げただけのユーザーの記録には `requirements` /
`models` の欄が無い**ため全部が更新対象になり、**torch を含む数 GB の再取得**が走る。
固定 URL の 3 本は「記録が無い＝ pin 前が入っている」と実機で確かめてあるが、
**要件とモデルは欄が無いだけで中身が古い証拠にならない**。記録にある名前だけを突き合わせ、
基準値を書き足して永続化する形にした。**代償が非対称なら、証拠が無い側へ倒す**（v0.5.4 の
python 判定と同じ原則）。

## 実機検証（E-8）が出した欠陥 3 件

**3 件とも自動テストでは鳴らなかった。**

### 1. 古い `ready.json` を信じて、死んだポートへ投げていた

`try_read_port` が pid を見ずにポートだけを返していた。起動前の削除が効かない状況で、
新しい子が書くより先に**前回の子の記録**を読み、前回セッションで止めた孤児のポートへ
起動時の挨拶を投げて失敗した。**起動した子の pid と一致する記録だけ**を受け入れる。

### 2. 通知の 5 分レート制限が、理由のログまで消していた

項目 1 で足した理由のログを `notify()` の中にだけ置いていたため、1 回通知した後の失敗の理由が
どこにも残らなかった（実機では更新中の「進行中です」がログから完全に消えた）。
理由はレート制限より**前に**毎回ログへ。**開発方針 7 の掃討で、ヘルス監視にも同じ形を見つけて
一緒に直した。**

### 3. 孤児掃除が、確かめる前に台帳を空にしていた

先に台帳を空にしてから 1 件ずつ確かめる作りだったため、**掃除の途中でアプリが落ちると、
記録が 1 件も確かめられないまま全部消える**。実機では dev が起動直後に落ち、ダミーを含む
2 件が着信 0 件のまま台帳から消えた。本物の孤児なら GPU を掴んだまま二度と止められない。
**確かめ終えた記録から 1 件ずつ**消す形に改め、掃討で同じ形を 2 つ見つけて一緒に直した
（停止処理が**止まるのを見届ける前に**記録を消す / 台帳の読み→書き戻しに**排他が無い**）。

## 開発方針 7 を足した

**「直したら、同じ形を全部探してから『直した』と書く」**（2026-09-11、ユーザー指示でルール化）。
1 リリース（v0.5.4 + v0.5.5 着手）で「1 箇所直して同じ形を残す」が 4 回起きたため。
手順は「形に名前を付ける → grep で全数当たる → 対になる関数のテスト観点を移植する →
コミットに掃討の結果を書く」。上の欠陥 2・3 はいずれもこの掃討で隣の同型を捕まえている。

## v0.5.6 へ引き継ぐ

正本は spec §6.0「v0.5.6 へ引き継ぐ調査結果」。要点:

- **モデルの差し替え先の候補を `Aratako/Irodori-TTS-v4.1-Small-MF`（bf16）にした。**
  上流が 2026-09-12 に公開した MeanFlow 蒸留版で、4 ステップ・CFG を蒸留に焼き込み済み。
  ユーザーが聴いて bf16 で「十分許容範囲」と裁定した
- **高速化は v0.5.6 で行う**（ユーザー裁定）。この機材での実測では、効くのはステップ数だけで
  bf16 は速くならない。MF は v3 現行の約 3.5〜4 倍速
- caption の有効化の検証 / 透かし（SilentCipher）の裁定 / 倫理条項の提示 / 「1 回合成できる」を成否の条件へ

## 検証手順に足した注意

どれも今回実際に踏んだもの。

- **Claude デスクトップ内のツールは `%APPDATA%` の MSIX 複製を読む。** そのツールから起動した
  dev も複製側へ書く。判定は対象プロセス自身の出力で行う
- **ユーザーの資産を動かさずに失敗経路へ入れる。** 参照音声を別プロセスが排他で開いて握ると、
  ファイルに一切書き込まずに 500 経路を通せる
- **台帳を手で書くとき PowerShell 5.1 の `ConvertFrom-Json` を通さない**（配列を包んで壊し、
  Rust 側が台帳を空とみなす＝検査が無効になる）
- **dev を止めたら台帳とサイドカーの生死を見る**（起動時の挨拶がサイドカーを立てている）
- `scripts/dev-ready.ps1 -CleanOrphans` が、取りこぼした孤児を「孤児なし」と報告していた。
  停止の失敗を出し、最後にポート 5273 が空いたかを直接確かめる形にした（日本語の出力が化けて
  いたので UTF-8 BOM も付けた）
