# ugg v0.5.1 — 棚卸しの残り 7 件

**リリース日**: 2026-09-05
**タグ**: `v0.5.1`
**テーマ**: v0.5 で洗い出した契約⇔実装の乖離 12 件のうち、v0.5.0 で扱わなかった 7 件をすべて閉じる。

## なぜこの回だったか

v0.5.0 は乖離 12 件のうち被害の大きい 5 件だけを直し、残り 7 件を明示的に持ち越した。
持ち越しの理由はそれぞれ妥当だったが（新規設計が要る / 記述の裁定が先 / 順序に依存がある）、
**「宣言どおりに動く」を掲げた回の直後に、宣言どおりに動かない箇所を 7 件残したままにする**
のは筋が悪い。棚卸しの残高をゼロにする回として切った。

7 件のうち `recall` と問いかけパターンは配線ではなく新規実装で、パッチ版が通常運ぶ範囲を
超える。番号は 0.6.0 のほうが実態に近いが、v0.5 の宿題を閉じる回であることを版番号で
示すほうが履歴として読みやすいと判断し 0.5.1 とした。

## 直したもの

### 1. WebView2 の自動再生ポリシー（spec §4.5.1）

ユーザー操作を伴わない発話（起動挨拶・ランダムトーク・リマインダー）で `AudioContext` が
`suspended` のままだと、`start()` は例外も投げず Promise も解決するため、**正常に喋った
ように見えて音だけ出ない**。`speaker.ts` は decode/play の失敗も `console.warn` で握り潰す
ので、症状は「たまに無音」としてしか現れない。

`ensureAudioCtx` で `suspended` なら `resume()` を試みるようにした（待たない。待つと発話が
遅れるうえ、失敗時に無音なのは変わらない）。

**ここは当初の実装が誤っており、リリース前監査で是正した。** 詳細は下の「監査で見つけて
直したもの」①。要約すると、`additionalBrowserArgs` は wry の既定引数を**置換**するため、
自動再生ポリシー自体は元から効いていた。

### 2. `ghost.json` の `default_shell`（spec §4.5.6）

v0.4.1 から出荷されているのに `GhostManifest` が宣言しておらず、serde が黙って捨てていた
（v0.5.0 で入れた契約テスト①が検出した項目）。DnD で入れたゴーストが自前のシェルを連れて
こず、ユーザーが手でシェルも選び直す必要があった。

v0.5.0 では「読むと挙動が変わるため仕様判断が要る」として意図的に無視へ分類していた。
**ユーザー裁定で「読む（ゴースト切替でシェルも追従）」に決定**したので実装した。

- 同じ操作でユーザーがシェルも明示的に変えた場合は**ユーザーの選択を優先**する
  （設定画面は両方を同時に保存するため、宣言で上書きすると手動選択が握り潰される）
- 宣言が無い / 実体のシェルが無い場合は追従しない（切替先が無いと起動できなくなる）

### 3. `export_data` を 3 → 9 テーブルへ（spec §4.5.5）

`chat_log` / `api_usage` / `user_profile` しか出しておらず、**リマインダー・ToDo・興味分野・
設定が持ち出せなかった**。

再生成できるキャッシュ 3 つ（`calendar_cache` / `topics_cache` / `monologue_cache`）は除外し、
除いたことを payload の `omitted_caches` に明記する。schema を `ugg-export-v1` → `v2` へ。

**これを 4 より先に直したのは順序の問題。** 出せないまま DB の保全機能を入れると、
「退避したのに肝心のデータが手元に残らない」事故になる。

### 4. DB 破損の検知・保全（spec §4.5.5）

ugg には DB の整合性を検査する経路が 1 つも無く、**壊れても誰も気づけない**状態だった。
発端は、実機の `companion.db` について M14 の頃に `integrity_check` が破損を報告した記録。

**ただし本リリースの実機確認（2026-09-05）では `quick_check` / `integrity_check` とも `ok` を返し、
現時点の実機 DB は健全だった**（WAL あり・なしの両方で確認）。長く前提にしていた記録のほうが
古くなっていたので、訂正としてここに残す。検知経路が無かったこと自体は事実で、機能の必要性は
変わらない。

設計判断: **破損していても DB は作り直さない。** 作り直すとリマインダー・ToDo・記憶・設定が
一緒に消える。起動も止めない（起動できないより、壊れたまま動くほうがデータを取り出せる）。
やるのは検知と非破壊の保全だけで、復旧方針はユーザーが決める。

- `Db::open` で `PRAGMA quick_check` を 1 回
- 破損時: ① 原本のタイムスタンプ付きコピー（**`-wal` / `-shm` も同じ規則で運ぶ**）
  ② `VACUUM INTO` による救出コピー（元 DB を書き換えない。読み出せた分だけ。失敗しても続行）
- **保全は破損 1 件につき 1 回だけ。** 既に退避があれば作り直さずそのパスを指す
- `get_db_health` を追加し、設定 →「システム」→「データ管理」に検知内容と退避先を表示
- **正常時は何も表示せず、コピーも作らない**

「1 回だけ」と WAL の同梱はどちらも監査で見つかった欠陥の是正。下の ②③。

### 5. 口パク — 一度も動いていなかった（spec §4.1.4）

spec は「TTS 有効時のみ、再生振幅（`AnalyserNode` RMS）でリアルタイム駆動」「v0.0.3 の
タイマー近似を廃止」と定めているが、実装は:

- `mouth.ts` が **120ms 間隔のタイマー近似そのもの**（spec が明文で廃止したもの）
- しかも `startFlap` / `stopFlap` の**呼び出し元がゼロ**
- 既定シェルに `_talk.png` が 8 枚あるのに boot payload に載っていない

3 つが重なって、**口パクは一度も動いたことがなかった**。

- `manifest.rs`: pose 画像の隣の `<stem>_talk.<ext>` を**自動検出**して `talk_poses` として
  送る（spec が「pose 画像の隣にあれば」と定めている＝自動検出が仕様。`shell.json` には
  書かせない）。`poses` と分けたのは、`poses` のキーが advanced の LLM に渡る pose 語彙
  そのものだから — 混ぜると LLM が `normal_talk` を選ぶ
- `character.ts`: 開口フレームの `<img>` も**静的に**作る（動的 `createElement` は WebView2 の
  透過レイヤーで描画されない既知問題）
- `mouth.ts`: タイマーを捨てて `AnalyserNode` の RMS 駆動へ全面書き換え。解析器は信号を
  素通しするので音は変わらない
- `speaker.ts`: **本発話のみ**結線（設定画面のプレビューはキャラが喋っているわけではない）。
  終了時と**中断時**の両方で口を閉じる（`stop()` は `onended` を確実には発火しない）。
  **音量 0 のときは駆動しない**（監査の指摘 ④）

### 6. 問いかけパターン（spec §4.2.4）

spec が採用機能として列挙し、architecture は `banter.rs` の責務を「掛け合いパターン制御
(1-4 + question_curiosity)」と**実装済みの体で**書いていたが、`question_curiosity` の文字列は
コード・辞書・フロントのどこにも 0 件だった。

**記述そのものが矛盾していた** — spec は「掛け合いパターンの 5 番目」、architecture は
「辞書の events キー + `probability: 0.05`」で、実装が変わるレベルで食い違う。CLAUDE.md が
spec を要件の正本としているので **spec に従い、architecture 側を訂正した。**

- 構造はパターン 1（main → sub）と同じで、**内容がユーザーへの問いかけで終わる**点だけが違う。
  ターン数を増やさないので `assemble_advanced` は 1 と共通のまま
- 発生確率 5%（architecture が指定していた値を採用）。残り 95% は従来の重み (50/25/15/10) を保つ
- サブ無しゴーストでも出せる（main が尋ねるだけなので 2/3/4 の制約が当たらない）
- プロンプトに「質問は 1 つに留める」を明記（尋問にしない歯止め）

### 7. `recall`（記憶想起） — 契約 4 箇所に対し実装ゼロ

契約は spec §4.2.6 / architecture §6.2 / DB スキーマ（`source_keywords` に「recall トリガー用」
とコメント）/ 出荷辞書（`{summary}` 入りの recall 行）の **4 箇所に揃っている**のに、実装が
1 行も無かった。`#[allow(dead_code)]` がコンパイラ警告まで消していた。

**死んでいた本当の理由は `pick_recall` の不在ではない。** `source_keywords` を作る手段が
リポジトリに 1 つも無かった（`insert_profile` の全 5 呼び出しが `None` を渡していた）。
仮に `pick_recall` があっても、照合する材料が常に空だった。

- `extract_keywords`: 記憶本文から漢字・カタカナ・英数の連なりを拾う。**形態素解析器は
  入れない**（辞書数十 MB を配布物に足す価値が無い）。2 文字以上・最大 8 語・重複除去。
  **1 文字語は拾わない**（「時」「好」がトリガーになると誤爆する）
- **キーワードはユーザーが入力した語からのみ作る**（監査の指摘 ④）
- `pick_recall`: キーワード一致で recall セクションから選び `{summary}` を記憶本文で埋める。
  `low::reply` が `pick_reply` より**先に**評価する
- **low モードで効く**のが要点。記憶は advanced が貯めるが、想起は無料・オフラインの既定
  モードでも起きる（spec §4.2.1 の二モード）

## リリース前監査で見つけて直したもの

**監査は多視点レビュー（7 観点）で回したが、検証段が利用制限で全滅したため、
指摘 38 件は自分で 1 件ずつ実コードに当たって判定した。** 以下は確定したもの。
いずれもタグ前に修正済み。

### ① `additionalBrowserArgs` が wry の既定引数を丸ごと消していた（自作の回帰）

`--autoplay-policy=no-user-gesture-required` だけを書いていたが、
`wry::webview2` は `additional_browser_args.unwrap_or_else(|| 既定を組み立てる)` なので、
**値を設定すると既定ブロックごと飛ぶ**。既定は
`--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection` に、
`WebViewAttributes::autoplay` が既定 `true`（Tauri は上書きしない）のため
`--autoplay-policy=no-user-gesture-required` を足したもの。

つまり **自動再生ポリシーは v0.5.0 以前から効いており、この変更で得たものは無く、
既定の抑止だけを失っていた。** 純粋な回帰である。既定分も併記する形に修正し、
spec §4.5.1 と architecture §7.0（新設）に置換挙動を明記した。

皮肉なことに、実装時に「一般的なスニペットをそのまま入れてしまった」として
`--disable-features=...` を**自分で外した**のがこの回帰の直接の原因だった。
範囲外の追加だと判断したが、実際にはそれが既定であり、外したことが変更だった。

### ② 破損 DB では起動のたびに退避が 2 本ずつ無限に増えていた

`check_integrity_and_preserve` に「既に退避があるか」の判定が無く、`Db::open` のたびに
原本コピーと救出コピーを新規作成していた。**実機の `companion.db` は既に破損している**ので、
このユーザーは 100% 踏む。596KB の DB に対し毎起動 1MB 超が積み上がる。

「破損 1 件につき 1 回」に変更した。先に作られた世代のほうが原本に近いので、古いものを残す。

### ③ 原本の退避が WAL を含まず、中身の大半を落としていた

`std::fs::copy(path, &backup)` は `companion.db` しか運ばない。実機では
**`companion.db-wal` が 4.0MB、本体が 596KB** で、まだチェックポイントされていない
書き込みのほうが多い。「今の状態を保全する」と名乗りながら、直近のデータが丸ごと
抜けたコピーを作っていた。`-wal` / `-shm` も同じ規則で運ぶようにした
（救出コピーは開いている接続を通すので元から WAL を反映していた）。

### ④ recall がアプリ自身の定型文で発火していた

オンボーディングは「ユーザーの呼び名は「◯◯」」「話し方の希望: ◯◯」「興味のあること: ◯◯」
という**アプリが組み立てた文**をそのままキーワード抽出にかけていた。結果、
**「ユーザー」「希望」「興味」** がトリガー語として保存される。`pick_recall` は
`pick_reply` より先に評価されるため、これらの語を含む入力では**low モードの通常応答が
毎回奪われ**、出荷辞書の recall は 1 行しかないので同じ台詞を繰り返す。
`{summary}` には DB のレコードがそのまま出る。

キーワードの抽出元をユーザー入力値だけに変更した。

### ⑤ 音量 0 でも口が動いていた

`AnalyserNode` を `GainNode` の**前**に挿しているため、音量 0（スライダの下限）でも
RMS はしきい値を超え、無音のまま口だけ動く。解析器の位置自体は正しい（後ろに置くと
音量を下げただけで口が動かなくなる）ので、音量 0 のときだけ駆動しない形にした。

### ⑥ テスト 2 本が名前どおりのことを検証していなかった

**本リリースのテーマそのものが自分のテストに出ていた。**

- `open_never_recreates_the_database`: 破損 DB を一度も作らずに「作り直さない」を名乗って
  いた。実際に破損させる経路を追加（ヘッダを避けて後続ページを潰す）。
- `extract_keywords_is_bounded_and_deduped`: 上限の検査に**区切りの無い 1 本のカタカナ列**を
  使っていたため run が 1 個しか生まれず、`truncate(MAX_KEYWORDS)` を消しても通る空振りだった。

**②③⑥ の修正はすべて変異テストで有効性を確認した。** うち「保全は 1 回だけ」のテストは
最初に書いたものが変異を素通りした（タイムスタンプが秒単位で、同一秒内の再オープンが
同じファイル名を上書きするため件数が増えない）。既存世代を先に置く形に書き直して、
ガードを外すと落ちることを確認した。

### ⑦ 要件の正本が、出荷した機能を「入れないもの」と宣言したままだった

spec §6.0「現在のスコープ」が v0.5 のままで、**v0.5.1 で出荷した 4 件
（`recall` / 問いかけ / 口パク / DB 退避）を非スコープとして列挙**していた。
v0.5.1 のスコープに差し替えた。あわせて `architecture.md` に v2.1 の改訂履歴が
欠落していたのを補記し、`get_db_health` がコマンド契約表に無かったのを追加した
（どちらも「宣言の片方だけ書いて繋げない」という、この回が閉じている型そのもの）。

## 既知の制限

- **v0.5.1 以前に保存された記憶は想起されない。** `source_keywords` が `None` のため
  照合材料が無い。誤爆しないことはテストで固定してあるが、遡って埋める処理は入れていない
  （記憶本文は上書きせず、次に手で入れ直すか、advanced が新しく覚えるのを待つ形）
- 口パクは開口フレーム（`<pose>_talk.<ext>`）を持つシェルでのみ動く。既定シェルは 8 pose
  すべてに同梱している
- 出荷辞書の recall は 1 行のみ。想起が続けて起きると同じ台詞になる
- `export_data` は `app_settings` を丸ごと含むため、カレンダーの ICS URL も平文で出る。
  書き出し先はユーザー自身のダウンロードフォルダだが、共有するときは中身を確認すること
