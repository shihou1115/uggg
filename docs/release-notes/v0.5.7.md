# ugg v0.5.7 — v4.1 へ乗り換える

**リリース日**: 2026-09-28
**タグ**: `v0.5.7`
**テーマ**: 高品質モード（Irodori-TTS）の合成を v3 から `Aratako/Irodori-TTS-v4.1-Small`（**bf16**）へ乗り換え、v0.5.6 の
更新の土台で既存の環境へ届ける。依存の major 移行（transformers 5.17.0 / huggingface_hub 1.33.0 / 上流 `89f9d8fb`）を伴う。
**新しい設定は 1 つ**（合成のステップ数 8 / 16 / 40、既定 16。v4.1 にだけ効く）。

## なぜこの回だったか

v0.5.4〜v0.5.6 の 3 回は、どれも spike で前提が崩れてモデルの乗り換えを先送りし、更新の経路を作り直してきた。
この回で乗り換える。当初の乗り換え先 MF（蒸留版）は、spike でユーザーが聴き比べて**高い音が劣化する**と判断し不採用
（帯域でも 8 kHz 以上が v3 より 4〜13 dB 低く、bf16 と fp32 で差が無い）。v4.1-Anime は学習データの出所が不明で不採用。

## 入れたもの（11 項目）

| | 内容 |
|---|---|
| 1 | **依存と上流の版を上げる** — spike で確かめた版に固定（transformers 5.17.0 / huggingface_hub 1.33.0 / tokenizers 0.23.2 / pydub 0.25.1 / 上流 `89f9d8fb`）。導入済みの環境で「ランタイムをダウンロード」を押すと、全段の入れ直しではなく更新の経路へ回す |
| 2 | **合成モデルを v4.1-Small（bf16）へ** — コーデックの revision も固定。v4.1 のトークナイザをモデルの隣に置き、欠けていれば「更新あり」に数える（「未導入」にはしない） |
| 3 | **参照音声の生成も v4.1 にまとめる** — 生成と合成が同じモデルなら、読み込みは 1 回 |
| 4 | **合成のステップ数の設定** — 8（速さ優先）/ 16（標準）/ 40（品質優先）。v3 の間は効かない |
| 5 | **透かしを効かせる** — 重みを更新の最初の段で取得。サイドカーの起動ごとに効いているかを 1 行残す（v0.5.6 までは一度も効いていなかった） |
| 6 | **ゲートと全戻しを乗り換えに合わせる** — 確かめの合成で参照音声の生成も試す。参照音声が無い環境でも確かめられる。VRAM 不足は全部戻さず**保留**（パッケージは入れ替え、声は旧モデルのまま。次の更新は確かめだけ） |
| 7 | **更新があることと、使えない理由を伝える** — 更新の告知（起動 30 秒後と 24 時間ごと・組ごとに 1 回）と、更新中 / モデルが無い / GPU が無い / VRAM 不足をキャラが言い分ける |
| 8 | **伝えること** — 更新と導入の確認に、取得量・声の質感が変わること・古いモデルを消すこと・倫理条項。空き容量が足りなければ何も変えずに止める。取得中の進捗を「取得中 … / …（N%）」に |
| 9 | **静かに失敗していたものを画面に出す** — エクスポートで読めなかったもの、カレンダーの取得の失敗（取得元ごとに 1 回） |
| 10 | **旧モデルの片付け** — 合成と生成の両方を確かめて記録を書いたあとにだけ、使われなくなったモデル（約 4 GB）と変換結果を消す |
| 11 | **接続切れのログを抑える** — サイドカーの `_call_connection_lost` のトレースバックだけを落とす |

受け入れ条件を 1 回で確かめる試験の経路（`sidecar.py --acceptance`: seed 固定の caption・絵文字・透かしの読み取り）も用意した。

## 実機検証（E-11）が出した不具合 — 全件タグ前に修正

**どれも自動テストでは鳴らなかった。**

1. **途中で止まった更新の後始末が、pip の一時退避を「入っている版」と読んだ**（`2e09255`）— 検証中に dev が作り直され、
   更新が pip の transformers の入れ替えの途中で止まった。次の更新の冒頭の後始末は、pip が残した `~ransformers-4.57.6.dist-info`
   を入っている版と数え、transformers を戻さずに hub と tokenizers だけを旧版へ戻して、**それまで喋れていた v3 を動かなくした**
2. **取得中の進捗の変換が、一度も効いていなかった**（`24133de`）— サイドカーの `snapshot_download` は、hub 1.33 ではファイルごとの
   行を出さず全体をまとめた 2 本だけを出す。変換はファイルごとの形しか読まず、実機では生の棒グラフが並んでいた
3. **初めての長さの文ごとに約 700 ms かかっていた**（`37d2ee5`）— 上流 `89f9d8fb` が注意機構の cuDNN を最優先に固定しており、
   cuDNN は入力の形が変わるたびに実行計画を組み立てる。毎回長さの違う台詞では、ほぼ毎回この時間を払っていた
   （torch.profiler で特定）。サイドカーで cuDNN を外し、初回も 457〜495 ms（修正前 1115〜1290 ms）
4. **取説の「caption は反映されません」が古いままだった** — v4.1 では反映される（効きは弱い）

あわせて、更新の告知を出さなかった理由を残すログ（`960ecbb`）と、A1 の出力先をデスクトップの実体から引く手順の修正を入れた。

## リリース前監査（release-audit）が出したもの — 全件タグ前に修正（`a9a9364`）

1. **VRAM 不足の保留のあとの再試行が、空き容量で断られる**（取得済みなのに 6 GB を求めた）
2. 最新なのに「ランタイムをダウンロード」で「更新があります」と確認する
3. 保留を「更新に失敗しました」と赤字で表示する
4. 参照音声の wav が消えていると、「モデルが無い（更新で直る）」と事実でない案内をする
5. 旧モデルの片付けで、記録の値が空や `..` なら `model\` や `irodori\` ごと消しうる
6. 更新が始まったこと・終わったことが `ugg.log` に残らない（E-11 の中断を site-packages の日時からしか見つけられなかった）

見送った 3 点と理由はコミット `a9a9364` に記録した。

## 既知の制限・次の回へ

- **ローカル AI（LM Studio など）が同じ GPU で文章を考えている間は、高品質モードの 1 文に数秒〜十数秒かかることがある**
  （2 つのプロセスの GPU の取り合い。v3 でも同じ状況で 3〜5 秒）。取説の FAQ に書いた
- caption（台本の演技指示）と絵文字は v4.1 で反映されるが、効きは弱い（ユーザーの聴感で誤差のレベル）
- 段階 3（保留）と、修正後の取得中の進捗の見え方は実機で見ていない
- ICS の URL がカレンダーの取得失敗のログに残る（spec §6.0 の「裁定に含めていないもの」）
