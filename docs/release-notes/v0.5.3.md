# ugg v0.5.3 — つないでも動く

**リリース日**: 2026-09-10
**タグ**: `v0.5.3`
**テーマ**: 第三者レビュー（Codex）の指摘 14 件を全件解消。**新機能ゼロ。**

## なぜこの回だったか

v0.5 は「宣言どおりに動く」（契約と実装の一致）、v0.5.1 はその残り 7 件、v0.5.2 は
その過程で自分が作った 13 件目の修正だった。棚卸しの残高はゼロになったはずだった。

そこへ第三者レビュー（Codex、2026-09-06）が 14 件を出してきた。**こちらで 1 件ずつ
実コードに当てて確認し、全件が妥当と判定した**（誤りも誇張も無かった）。

**残っていたのは単独の機能ではなく、つなぎ目だった。**

- 旧版からの更新（アセットを上書きするとき）
- 保存したあとの再保存（設定パネルが古い値を送り返す）
- 連続する通知（後の通知が前の通知を消す）
- 非同期処理の途中での中断（合成後は世代を見るが、デコード後は見ていない）

**14 件のうち 1 件も、こちらの単機能テストでは捕まらなかった。** 実機確認も機能ごとに
1 回ずつ通す形で、操作列としては流していなかった。Codex の総評「残る弱点は、機能の
有無より『処理をつないだ結果』の検証にある」は当たっていた。

### こちらの判断が誤っていた 2 件

**14 件のうち 2 件は、v0.5.1 でこちらが誤って棄却・誤って説明したものだった。**

**#3（保存後の再保存）** は v0.5.1 のリリースノートに「棄却できたものの例」として
明記していた。根拠は「`save_settings` は追従後の値で `settings-changed` を emit し、
パネルは開いていれば再適用する」。emit と listener までは確認したが、
**その `applySettingsToForm` が実際にその select を更新するかを見ていなかった。**

**#7（問いかけ）** も同型。v0.5.1 のノートに「advanced では次のターンで LLM が会話
として自然に受ける」と書いたが、`load_recent_history` が常に空を返す以上、受けられない。

どちらも「宣言と実装の一致」を掲げた回で、**検証を一段浅く済ませて結論だけ書いた**。
file:line まで辿ってから書く、という手順自体は持っていたのに適用しなかった。

## 直したもの（9 項目）

### 1. 復旧導線を本当に使えるようにする

**破損時に案内している当の機能が、必要な場面でだけ失敗していた。**

- **`export_data` を部分救出へ。** 全テーブルの読み取りが `?` で、1 つ失敗すると JSON を
  一切出さなかった。`manual.md` の「まず JSON エクスポートで手元に控えてください」は
  v0.5.1 でこちらが書いた案内で、その export が壊れた DB では止まっていた。
  取得できたデータと、取得できなかった対象（`failed_tables`）を両方出す。
- **整合性検査を pragma より前へ。** `journal_mode=WAL` が検査より前にあり `?` で伝播
  するため、**ヘッダやスキーマページの破損では保全にも起動継続にも到達しなかった。**
  spec §4.5.5 の「起動も止めない」は無条件では成立していなかった。
  副次的に、**原本を退避する前にアプリが原本へ書き込む**こともなくなった。
- **退避・救出コピーの妥当性を見る。** `find_preserved` は名前だけで採用しており、
  v0.5.1 が残した 0 バイトの `salvaged-*.db` を「救出済み」と誤認して二度と再試行しなかった。

**v0.5.2 で追加したテストはページ 3 以降しか壊しておらず、ヘッダ破損を一度も通していなかった。**
今回はヘッダを壊すテストを足した。

### 2. 更新でデータを失わない

- **アセット導入を非破壊に。** 上書き承認後に `remove_dir_all` してから展開していたため、
  禁止拡張子・zip 破損・容量不足で失敗すると**使えていた旧版まで失われた**。悪意ある入力を
  必要としない、通常の更新操作の問題。
  別ディレクトリで展開・検証してから差し替え、旧版は待避してから入れ替える。
  **戻せなかった場合は待避先を消さず、場所をログに残す**（自動で消すと、まさに守ろうと
  したデータを失う）。
- **manifest の選択規則を 1 箇所へ。** 事前確認が「最初に一致」・展開が「最も浅い」で、
  複数 manifest を含む zip では**確認ダイアログに出した id と実際の中身が食い違いえた**。
- **PowerShell のパス引用を修正。** アポストロフィを含むパスで `-LiteralPath` が壊れていた。

> 実装中に、待避先を最初 staging の中に置いて**自分で穴を作っていた**。差し替え失敗 →
> 復元も失敗、というときに直後の掃除が旧版を巻き添えで消す経路ができていた。
> 待避先を staging の外へ出して解消した。

### 3. 保存したあとの再保存で巻き戻らない

- **`applySettingsToForm` にゴースト・シェルの select を含める。** 値合わせが
  `fillAssetSelect`（一覧を埋める）にしかなく、保存済みの値をフォームへ戻す側は
  select に触れていなかった。ゴースト切替は再起動案内のためパネルを閉じないので、
  **「保存 → もう一度保存」で `default_shell` の追従が黙って取り消される。**
- **カレンダーソース更新を 1 トランザクションに。** `set_setting` 成功後に
  `clear_calendar` が失敗すると、DB は新しいソース構成・キャッシュは旧 index・
  メモリと UI は旧構成、という三者バラバラが残っていた。
  `Db::clear_calendar` 単体は残していない（分けて呼べる限り同じ穴が空くため）。

### 4. 通知を後続の発話で消さない（spec §4.1.3 改訂）

通知は「一度出したら配達済みの記録が残り、二度と出ない」。消されると
**記録だけが残って永久に届かない。** 実際に起きていたのは 2 つ:

- 同じ周期で 2 件のカレンダー通知が配達されると、後の 1 件が前を消す
- 80% コスト警告を emit した直後にチャット応答が返ると、応答が警告を消す

規則を 2 つ入れた（ユーザー裁定）:

1. **通知は割り込まない。** キューに入れ、描画中なら空くのを待って 1 件ずつ出す。
2. **通知は割り込まれても捨てない。** 描画中に他の発話が来たらキューの先頭へ戻す。
   割り込み自体は許す（ユーザーの入力への応答を待たせないため）。

対象は通知だけ。状況発話・独り言・定例会話（Ambient）は消えても記録が残らず、また
出るので含めない — 含めるとユーザーの操作を待たせるだけになる。

### 5. 課金の保護を異常時にも効かせる（spec §4.2.7 改訂）

`cost_exceeded` は集計に失敗すると `false` を返して LLM 呼び出しを通していた
（意図的な fail-open）。単独なら仕様判断だが、**v0.5.2 で「破損 DB でも起動を続ける」
ようにしたことで `sum_cost_since` の失敗が現実の経路になり**、「上限を設定しているのに
無制限に課金される」組み合わせが生まれていた。

上限が有限＝ユーザーが「ここまで」と言っている以上、守れないなら使わない（fail-closed、
ユーザー裁定）。**黙って low に落ちないよう、上限超過とは別の告知**を出す（辞書
`cost_unknown`）。ユーザーが取るべき行動が違うため、文言を分けている。

この告知済みフラグだけは**永続化しない**（プロセスごとに 1 回）。記録先の `app_settings`
自体が同時に失敗しうる状況で、月単位の予算ではなく「いま壊れているか」の話だから。

### 6. 問いかけを会話として閉じる（spec §4.2.4 改訂）

`load_recent_history` が `Ok(Vec::new())` 固定で、**advanced は毎ターン、その場の入力
だけで応答していた。** キャラが尋ねてユーザーが「それがいい」と答えても、その「それ」が
LLM に渡らない。

- 直近 **8 往復**を上限に注入（ユーザー裁定）
- **合計 1200 文字**の上限も設け、超えたら古い方から落とす
- 切り出しの起点は「最初に残すユーザー発言の 1 つ前」= **問いかけ本体**
- 掛け合いの連続発話は `<名前>: <台詞>` でまとめて 1 応答
- **チャット経路のみ**（独り言補充には渡さない。§4.4.4「独り言は応答ではない」を維持）

### 7. 記憶とログの後始末（spec §4.2.6 / §5 改訂）

- **自動記憶のトリガー語を LLM 要約文から採らない。** v0.5.1 で塞いだのはオンボーディングの
  定型文だけで、自動抽出は要約文に `keywords_of` をかけていた。要約文に「ユーザー」等が
  出れば同じ誤爆が起きる（`pick_recall` は `pick_reply` より先なので low の応答を奪う）。
  ユーザー入力から拾った語のうち記憶本文にも現れるものだけを採り、**言い換えられて一致
  しなければトリガーを作らない**（誤爆は毎回邪魔になるが、不発は静かなだけ）。
- **診断ログに会話本文を残さない。** JSON パース失敗時に応答本文を `%APPDATA%\ugg\ugg.log`
  へ書いていた。**ログは履歴クリアの対象外**なので、消す手段が無いまま溜まり続ける。

### 8. 非同期の中断を跨いで確認する

`playBase64Wav` は合成後には世代を確認するが、`decodeAudioData` の待機後に確認していな
かった。デコード中に停止すると `currentSource` がまだ無いので停止対象も無く、
**停止したあとに再生と口パクが始まっていた。**

台本読み上げ側は同じ位置で `token.cancelled` を見ており、チャット発話側だけが抜けていた。

### 9. 操作列で固定するテストを常設する

今回の 14 件は単機能テストでは 1 件も捕まらなかったので、4 つの操作列を常設側に置いた
（v0.5 の契約テスト 2 本と同じ位置づけ）。

| # | 操作列 | 場所 |
|---|---|---|
| 1 | 旧版からの更新 | `assets.rs::install_tests::install_then_update_then_failed_update_leaves_a_usable_ghost` |
| 2 | 保存してからの再保存 | `src/__tests__/resave-does-not-revert.test.ts` |
| 3 | 連続通知 | `src/__tests__/consecutive-notices.test.ts` |
| 4 | 非同期処理途中の停止 | `src/__tests__/stop-during-async.test.ts` |

**フロントにテストの仕組みが無かったので Vitest + happy-dom を導入した。**
test-plan.md §2.2 は Phase 3 から Vitest を書いていたが、v0.5.2 まで実体が無かった。
DOM はダミーを手書きせず `index.html` の body を読み込む（フロントは静的配置された要素を
`getElementById` で掴む設計なので、手書きだと id がずれてもテストだけ通る）。

> **ここでも一度、自分のテストが変異を素通りした。** 最初の通知テストは「表示が
> **始まった**」ことを記録しており、打ち切られた発話も表示済みとして数えていた。
> 「**最後まで表示された**」を観測する形に直して解決。v0.5.1 で踏んだ「テスト名が
> 主張を検証していない」と同じ形なので、書き方の要点として test-plan.md §3.2b に残した。

- **E-6b（`default_shell` の追従）は実機未検証のまま。** 項目 3 の 1 を直しても、
  検証にはゴースト・シェルが 2 組必要で、手元には `default` の 1 組しかない。
  デフォルトゴースト・シェルを刷新する v0.6 で自然に消化する

  1 行 / `export_data` は `app_settings` を丸ごと含む）はそのまま
- **履歴注入は advanced のプロンプトを長くする。** 直近 8 往復・1200 文字が上限だが、
  1 ターンあたりのトークンは v0.5.2 より増える
