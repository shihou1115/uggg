# ugg v0.5.6 — 速くして、乗り換えに備える

**リリース日**: 2026-09-24
**タグ**: `v0.5.6`
**テーマ**: 高品質モード（Irodori-TTS）を、モデルを変えずに約 4 倍速にする。あわせて、次の回（v0.5.7）の
モデルの乗り換えを既存ユーザーへ安全に届けるための土台（更新を 1 つのトランザクションにする・孤児と二重起動への
備え）を入れる。**新機能ゼロ・モデルと依存の版は変えない。**

## なぜこの回だったか

当初は「モデルを v3 → `Aratako/Irodori-TTS-v4.1-Small-MF` へ差し替えて速くする」一括案だった。
**反証レビュー（別 Opus）が「高速化は差し替え無しで届く」ことを spec 自身の実測から示した**（v3 の 8 ステップ + 参照音声の
事前変換は、同じ条件の MF とほぼ同じ速さ）ので、3 回目の分割をした（乗り換えは v0.5.7）。反証と検証は、乗り換えの前に
要る土台の欠落も見つけた:

1. **更新の途中失敗が、成功済みの退避（＝唯一の旧版）を戻さずに消す。** 名前付き要件には退避も復元も無かった
2. **読み先がビルドの定数だけで決まる。** 定数を変えた版を入れた瞬間から更新を終えるまで高品質モードが死に、キャラは
   「GPU 環境が整っていない」と事実でない説明をする
3. **合成を 1 回試す経路がどこにも無い。** 「import できる」では依存の版ずれを検出できない
4. **新版のインストーラは動いている ugg を強制終了する。** 直前に高品質音声を使っていれば、サイドカーが GPU を掴んだまま残る

## 入れたもの（6 項目）

| | 内容 |
|---|---|
| 1 | **速くする** — v3 のまま 8 ステップ（sway）+ 参照音声の事前変換。短い文で 200〜400 ms（v0.5.5 は 900 ms 前後）。声はユーザーが聴いて許容 |
| 2 | **落ちた理由が読める** — サイドカーの文字化け（cp932）の原因を確かめて直した。取得の進捗を行ごとに出し、出力も読み書きも CPU も 5 分無ければ止める。stderr にも発話の伏字 |
| 3 | **更新を 1 つのトランザクションにする** — 読み先を導入記録から決める（取得先と分ける）。固定の段取り（torch を先に CUDA の index から、ほかは torch を縛って 1 回で）。最後に 1 回合成して確かめ、だめなら全部戻して「更新が原因か、元からか」を切り分ける。版の控えは全配布。導入・更新の錠をプロセスをまたぐものに |
| 4 | **孤児と二重起動** — サイドカーの台帳に持ち主（ugg の pid と開始時刻）を持たせ、ほかの ugg が使っているものは止めない。台帳の錠もプロセスをまたぐ。**サイドカーと zip の展開を ugg と一緒に終わらせる**（Job Object。強制終了でも残らない）。実モデルの ON/OFF がサイドカーの稼働中も次の発話から効く |
| 5 | **終了のあいさつを揃える** — トレイと右クリックメニューの「終了」を 1 本に。見えていれば終了前の確認かあいさつ、隠していればすぐ終了（ユーザー裁定: 隠していても聞こえていたあいさつは無くなってよい） |
| 6 | **告知は届いたと確かめてから済みにする** — 見えていない間は出さずに保留し、1 回だけの告知（コスト・更新）は届いたときだけ済みにする。spec §3.1 の二段トーストは取り下げ |

## 実機検証（E-10）が出した不具合

**どれも自動テストでは鳴らなかった。**

1. **実環境のテストが、最後に起動した ugg の `sidecar.py` で走っていた** — 実環境の `sidecar.py` は v0.5.5 のもの（`--synth-once` を
   知らない）で、1 回合成のゲートのテストは環境と関係なく必ず不合格になるところだった
2. **終了のあいさつを待つ間に独り言が流れ、あいさつを置き換えた** — 待つ間は自発発話を止めるようにした（トレイの経路にも
   以前からあった）

## リリース前監査（release-audit）が出した 4 件 — 全件タグ前に修正

1. **隠している間、告知の保留が `ugg.log` へ毎分 2 行ずつ増えた**（項目 6 が作った後退）。同じ告知の保留は見えるまで 1 回だけ書く
2. **合成の側の錠の「試してすぐ放す」に重なると、更新が「もう 1 つの ugg が更新しています」と事実と違う理由で断られた**。
   0.5 秒だけ取り直す
3. **全戻しに失敗して残った退避と控えを、初回導入が片付けなかった** — 次の更新の入口が、入れたばかりのものを古い退避で
   書き戻す。初回導入が成功したら片付ける
4. architecture の資産表の欠け（`update-constraints.txt`）

見送った懸念 5 点と理由は spec §6.0 に記録した。
