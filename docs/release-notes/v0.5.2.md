# ugg v0.5.2 — 破損 DB で起動できなかった

**リリース日**: 2026-09-05
**タグ**: `v0.5.2`
**テーマ**: v0.5.1 の実機確認で見つかった 2 件の修正。**新機能ゼロ。**

## なぜこの回だったか

v0.5.1 のリリース直後、手動チェックの E-5b（DB 破損の検知・保全）を実機で通したところ、
**破損した DB ではアプリが起動しないことが分かった。**

v0.5.1 は spec §4.5.5・architecture・manual・リリースノートの 4 箇所で

> 破損していても DB は作り直さない。起動も止めない
> （起動できないより、壊れたまま動くほうがデータを取り出せる）

と宣言していた。整合性検査は実際に非致命に作ってあった。**その直後の 1 行がアプリを
殺していた。**

**これは v0.5 / v0.5.1 が閉じるはずだった「宣言はあるのに実装が伴っていない」型そのもので、
今回はそれを私が新しく作っていた。** 12 件の棚卸しを終えた次のリリースで、同じ構造の
13 件目を出荷したことになる。

## 直したもの

### 1. 破損 DB で起動できなかった（spec §4.5.5）

隔離環境（実 APPDATA の複製、破損させた DB）にインストール版 v0.5.1 を当てた結果:

```
[db] 整合性検査に失敗しました: *** in database main ***
[db] 原本を退避しました: ...\companion.corrupt-20260905-100757.db
[db] 救出コピーの作成に失敗 (読み出せない範囲がある): database disk image is malformed
[panic] Failed to setup app: error encountered during setup hook: write db_schema_version=1
```

経路:

- `main.rs:71` — `AppState::initialize(app.handle())?`（setup フック内）
- `state.rs` — `Db::open()` の**直後**の `db.migrate()?`
- `db.rs` — `INSERT OR REPLACE ... db_schema_version=1` が破損 DB で失敗

破損 DB では `db_schema_version` の書き込み自体が失敗するため、**整合性検査を非致命に
作っても、次の行を致命扱いにしていれば意味がない。**

修正は、**健全な DB でのマイグレーション失敗は従来どおり致命**のまま（見逃すと以後の
全機能が壊れる）、**破損が検知されている場合だけ続行**する形にした。

```rust
if let Err(err) = db.migrate() {
    if db.integrity().ok {
        return Err(err);
    }
    ulog!("[db] 破損 DB のためマイグレーションを中断して続行します: {err:#}");
}
```

### 2. 失敗した救出コピーの残骸が、再試行を永久に止めていた

同じ実機確認で、隔離ディレクトリに **0 バイトの `companion.salvaged-*.db`** が残っていた。
`VACUUM INTO` は失敗したのにファイルだけが残る。

v0.5.1 で入れた「保全は破損 1 件につき 1 回」のガードは `find_preserved` で既存の
退避を探すので、**次回起動でこの空ファイルを拾って「救出済み」と判断し、二度と救出を
試みない。** ディスクを食い潰す穴を塞いだガードが、今度は失敗を成功として固定していた。

失敗時に作りかけのファイルを削除するようにした。

## 検証

- `cargo test` **349 → 351 passed** / warning 0 / `tsc --noEmit` green
- 追加したテスト 2 本:
  - `corrupt_db_opens_but_migrate_fails_which_startup_must_tolerate` —
    「open は成功し、integrity は false、**migrate は失敗する**」という
    `AppState::initialize` が続行判定に使っている前提そのものを固定する
  - `failed_salvage_leaves_no_empty_file` — 救出に失敗しても残骸を残さないこと
- **後者は変異テストで有効性を確認した**（`remove_file` を外すと FAILED になる）
- **隔離環境で修正後のビルドを実際に破損 DB へ当て、起動することを確認**（下記）

### 破損 DB での実機確認（この回の主眼）

隔離した APPDATA に実 DB のスナップショットを複製し、破損させて確認した。

| 確認 | 結果 |
|---|---|
| 破損検知 | `[db] 整合性検査に失敗しました` |
| 原本の退避（`-wal` / `-shm` 込み） | 626,688 バイト＝原本と一致、サイドカーも同伴 |
| **マイグレーション失敗を飲み込んで続行** | `[db] 破損 DB のためマイグレーションを中断して続行します` |
| **アプリが起動する（v0.5.1 との差）** | **ALIVE 30 秒 / `MainWindowTitle='ugg'`** |
| 救出失敗時の 0 バイト残骸 | **残らない**（v0.5.1 では残っていた） |
| 再起動で退避が増えない | `[db] 退避済みのため作り直しません` / ファイル数 3 のまま |
| 再起動で救出が再試行される | される（残骸を消したので「救出済み」と誤認しない） |
| 原本が作り直されない | `companion.db` は 626,688 バイトのまま |

**参考**: TTS を有効にした状態の常駐メモリは約 2.3GB だった（voicevox_core がモデルを
読み込むため）。これまでのリリース確認は TTS 無効で行っており、実測はこれが初めて。
v0.5.2 が変えた挙動ではない。
