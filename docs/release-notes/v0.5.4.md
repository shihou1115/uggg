# ugg v0.5.4 — 更新が届く

**リリース日**: 2026-09-11
**タグ**: `v0.5.4`
**テーマ**: Irodori-TTS ランタイムの更新経路を作る。**新機能ゼロ。**

## なぜこの回だったか

当初 v0.5.4 は「Irodori-TTS を v3 → v4.1-Small へ差し替える」で確定していた。
**着手前に置いた spike が、前提を 2 つとも崩した。**

1. **`assets_ready` はパッケージの「存在」しか見ていない。** `torch` / `fastapi` /
   `irodori_tts` のディレクトリがあれば「導入済み」で、**どの版が入っているかを問わない**。
   したがって 2026-08-15（`df2c82f`）に `refs/heads/main` から固定 SHA へ上げた pin は、
   **すでに導入した環境に一度も届いていなかった**。実機の `irodori_tts` は 2026-06-28
   導入のままで、`direct_url.json` が pin 前の `refs/heads/main.zip` を記録していた。
2. **v4.1-Small は transformers 5 を要求する。** `text_encoder_type: "pretrained"` →
   `PretrainedTextBackbone` が `transformers.initialization`（v5 専用）を無条件 import する。
   実機は 4.57.6。連鎖して huggingface_hub 0.27 → 1.x も必要になる。

**土台が無いまま差し替えても、既存ユーザーには一生届かない。** 順序はここで決まった。
ユーザー裁定で分割し、モデル差し替えと依存の major 移行は v0.5.5 へ送った。

### 「版を固定して再現性を担保」は、すでに成立していなかった

反証レビュー（別 Opus）が独立に同じ穴へ到達し、加えて 4 件を持ち込んだ。うち 1 件:
**`huggingface_hub==0.27.0` と指定しているのに実機は 0.36.2**（`transformers` の
`huggingface-hub>=0.34.0` に押し上げられた）。

だから記録するのは「**指定した版**」ではなく「**実際に入った版**」でなければ意味がない。
`installed.json` が `pins` と `resolved` を両方持つのはこのため。

## 入れたもの（5 項目）

| | 内容 |
|---|---|
| 1 | **入っている版を記録する** — `%APPDATA%\ugg\irodori\installed.json`（`pins` = 要求した固定 URL、`resolved` = 実際に入った版）。全段成功後にだけ書く |
| 2 | **「使える」と「最新」を分ける** — `get_irodori_status` を追加。`irodori_assets_ready` の意味は変えない |
| 3 | **更新の実行経路** — 古くなった分だけを「退避 → 入れ直し → import の前後比較 → 悪化が無ければ退避を捨てる」 |
| 4 | **ユーザーに見える形にする** — 「導入済み (更新あり)」表示と「更新する」ボタン |
| 5 | **判定ロジックのテスト常設** — Rust 側 + フロントの操作列テスト |

### 項目 2 は、書いた仕様のほうが間違っていた

spec §6.0 の項目 2 は当初「`assets_ready` を存在から一致へ／**一致しないものを
『導入済み』と呼ばない**」と書いてあった。実装前に `settings.ts:546-553` を辿って気づいた:

フロントは `canUseReal = gpuOk && assetsOk` で判定し、false のとき
`tts_irodori_use_real_model` を**黙って false へ倒して `set_settings` で永続化する**。
古いが動いているランタイムを「未導入」に落とすと、**更新が届いていないだけのユーザーの
設定が勝手に消える**。

実装前に spec を v1.8.3 で訂正し、「**使える**」と「**最新**」を別の信号に分けた。
`assets_ready` の意味は変えていない。

### 項目 3 で、`python` だけは対象から外した

`ensure_python_embeddable` は `python.exe` があれば skip する。つまり **Python 本体の
pin を上げても既存環境には届かない** — 今回の主題とまったく同じ問題が 1 段下にもあった。

ただし**稼働中のインタプリタを安全に差し替える方法は無い**。黙って他の 3 パッケージだけ
入れ替えて「最新」と記録すると、記録そのものが嘘になる。そこで **`python` は入れ直しの
対象にせず、何が要るかを返して止まる**ことにした。同じ理由で、成功後は**入れ直せた分だけ**
記録を書き換える。

## 実機検証（E-7）が出したバグ 3 件

**3 件とも、405 本の自動テストでは 1 件も鳴らなかった。** いずれもフォールバック経路・
中間状態・層の境目にある。

### 1. 記録が無い環境で、更新がちょうど 1 つも動かなかった

記録が無いときの対象を `current_pins()` から丸ごと組み立てていたため、**入れ直せない
`python` が必ず混ざり**、`update_irodori_runtime` の冒頭のガードで Err になっていた。
ユーザーには

> Python 本体の版が変わっています。`%APPDATA%\ugg\irodori\python` を削除してから、
> もう一度導入してください

という**事実でない案内**（数 GB の再取得要求）が出る。Python の版は変わっていない。

**原因は「記録が無い」ことと「版が違う」ことの混同。** `ensure_python_embeddable` が
skip する以上この 2 つは別物で、版は `python.exe --version` で**実物に聞ける**。
判定を実物へ移し、聞けなかったときは「古い」と言わない側へ倒した — 記録の欠落は更新ボタンが
出るだけだが、python の誤判定は全削除・再導入の要求になる。**代償が非対称なら、証拠が
無い側へ倒す。**

**この機能が対象にしている環境（v0.5.4 より前に導入した環境）が、ちょうど 1 つも
更新できない状態だった。**

### 2. 検証ゲートが厳しすぎて、既存環境では必ず巻き戻っていた

入れ直しの成否を「`irodori_tts` / `dacvae` / `silentcipher` が**全部 import できること**」で
判定していた。ところが実機の `silentcipher` は `pydub` が無く、**一度も import できたことが
無い**。upstream の `irodori_tts/watermark.py` は `ImportError` を握って「透かし無しで続行」
する設計で、合成はそれで成立している。

つまりゲートはシステムが保証していないことを要求しており、**pip が成功しても必ず
ロールバックし、更新が誰にも一度も成功しない**状態だった。

項目 3 が約束しているのは「**失敗しても、それまで動いていた環境を壊さない**」であって
「壊れていた環境を直す」ではない。判定を**入れ直し前後の差分**に改め、悪化したものだけを
失敗とみなすことにした。

あわせて、import 失敗の理由を握り潰していたのも直した。実機の失敗が
`python 異常終了 (code Some(1))` としか分からず、原因（`No module named 'pydub'`）に
辿り着くのに余計な一往復を要した。

### 3. 記録の書き込みが、テストから到達できない層にあった

`installed.json` の書き込みが `commands::tts` にあったため、「**パッケージは入れ直せたのに
`up_to_date` が false のまま**」＝ユーザーから見て更新が成立していない状態を、自動でも
実機ハーネスでも検出できなかった。記録は更新の一部なので `irodori_download` へ移した。

## 検証

- `cargo test` **382 → 405 passed** / 1 ignored（E-7 の実機ハーネス）
- `cargo check --all-targets` warning 0 / `npx tsc --noEmit` green
- フロント操作列テスト **9 → 14 passed**（項目 4 の 5 ケースを追加）
- **E-7 実機 PASS**（開発機、2026-09-11）
  - 記録が無い環境で 3 本を入れ直し、`direct_url.json` が**固定 SHA を指すようになる**
  - `installed.json` が 4 pin 揃って書かれ、`up_to_date: true` へ反転
  - **失敗時の復元も実地で確認**（1 回目の失敗で `.update-backup` は残らず、
    `direct_url.json` は旧 URL へ戻り、記録も書かれなかった）
  - **更新後も実モデルで合成できる**（参照音声の生成とプレビューで声が鳴る）

新規テストはすべて**変異テストで FAILED を確認してから復元**した（合計 16 種）。

### 変異 1 種を最初は素通りした

項目 4 の「同意を取らずに入れ直す」変異が通ってしまった。`vi.waitFor` に**否定**を
渡しており、1 回目の判定で通っていた。**「起きないこと」は待っても観測できない。**
同じ待ち方で肯定側が観測できることを同じテストで示す形に改めた。
v0.5.1・v0.5.3 と同型で **3 度目**。

## v0.5.5 へ引き継ぐ（「入れているのに使えていない」）

| | 内容 |
|---|---|
| caption | v3 本体が `use_caption_condition: false` なのに、契約表と script-reader-spec は使えると宣言。v4.1-Small は `true` なので差し替えで閉じる |
| SilentCipher の透かし | `pydub` を入れていないため import に失敗し、**出力音声に一度も透かしが入っていない**。`pydub` を足すか pin ごと外すかを裁定する |
| サイドカーの stderr | `[hf-download]` 以外を**すべて捨てる**ため、異常終了の理由がユーザーにもログにも残らない |
| 実モデルの ON/OFF | `ensure_sidecar_running` が `mock` を見ずに既存ポートを返すため、**サイドカーが生きている間は切り替わらない** |

モデル差し替え（v3 → v4.1-Small）+ transformers 4→5 + huggingface_hub 0.27→1.x も v0.5.5。
**v4.1-Anime は不採用**（学習データの出所が不明で、base 自身の倫理条項との関係を検証できない）。

## 検証手順に足した注意

どちらも今回実際に踏んだもの。

- **ビープ音は合成の成功ではない。** `mock = !tts_irodori_use_real_model` のモック経路で、
  実モデルを一度も通っていない。
- **設定を変えたらアプリを再起動する。** しないと前のモードのサイドカーが再利用される。
- **TTS の失敗は、まず VRAM を疑う。** 今回 1 回目の失敗は他アプリが GPU を占有して
  空き 461 MiB だったため。アプリ側には「HTTP 通信に失敗しました」としか出ない。

## 契約の変更

- コマンド 2 つ追加: `get_irodori_status` / `update_irodori_runtime`
- **設定フィールド・イベント・DB スキーマの変更なし**
- 新しいファイル: `%APPDATA%\ugg\irodori\installed.json`（`schema: 1`）
