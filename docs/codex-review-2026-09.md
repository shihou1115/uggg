# Codex レビュー（2026-09-06）の妥当性判定

> **この文書は v0.5.3 のリリースノートへ消化したら削除する**（CLAUDE.md 開発方針 6）。
> 判定の結論と「自分の判断ミス 2 件」は `docs/release-notes/v0.5.3.md` へ転記し、
> 本ファイルは次回の `tidy-docs` で刈る。原本はタグ v0.5.3 以前の履歴に残る。

**対象**: HEAD `0c0453d`（v0.5.2 タグ以降の差分は文書のみ）
**レビュー元**: Codex。ファイル・設定の変更なしで実施したと申告あり
**判定方法**: 指摘 14 件すべてを、こちらで実コードに当てて確認した
（前回 2026-08 のレビューと同じ手順。第三者の主張は根拠を自分で見るまで採らない）

## 結論: 14 件すべて妥当

誤りも誇張も見つからなかった。severity の見立ても概ね妥当で、
「未実装であること自体を脆弱性として数えない」「`cargo test` は実行しておらず
351 件成功を再確認した意味ではない」といった自己申告も正確だった。

| # | 指摘 | 判定 | 確認した根拠 |

## こちらの判断が誤っていた 2 件

**#3 は v0.5.1 のリリースノートで「棄却できたものの例」として明記していた。**
根拠は「`save_settings` は追従後の値で `settings-changed` を emit し、パネルは開いて
いれば再適用する」だった。emit と listener までは確認したが、
**`applySettingsToForm` が実際にその select を更新するかを見ていなかった。**
一歩手前で止めて結論を書いた形で、指摘は再採用が正しい。

**#7 も同型。** v0.5.1 のノートに「advanced では次のターンで LLM が会話として
自然に受ける」と書いたが、履歴が空である以上受けられない。問いかけパターンは
出しっぱなしで会話として閉じない状態で出荷していた。

どちらも「宣言と実装の一致」を掲げた回で、**検証を一段浅く済ませて結論だけ書いた**
のが原因。file:line まで辿ってから書く、という手順自体は持っていたのに適用しなかった。

## v0.5.1 / v0.5.2 との噛み合わせで重くなるもの

Codex は個別に挙げているが、直近で入れた機能と組み合わさると効きが変わる。

- **#6 は復旧導線そのものが壊れている。** `manual.md` の「まず JSON エクスポートで
  手元に控えてください」という案内は v0.5.1 でこちらが書いた。その export が、
  破損時に最初の読めないテーブルで止まる。**案内した先が、必要な場面でだけ失敗する。**
- **① は v0.5.2 の修正範囲の限界。** spec §4.5.5 の「起動も止めない」は無条件では
  成立していない。**v0.5.2 で追加したテストはページ 3 以降しか壊しておらず、
  ヘッダ破損を一度も通していない。**
- **#5 は ① と #2 に繋がる。** v0.5.2 で「壊れた DB でも動き続ける」ようにしたため
  `sum_cost_since` の失敗が現実的になり、fail-open すると上限があるのに無制限に
  課金される。単独なら仕様判断だが、この組み合わせでは放置しにくい。
- **③ は v0.5.1 の修正の穴。** オンボーディングの定型文は塞いだが、自動抽出経路は
  同じ誤爆が残っている。

## Codex の総評について

> 残る弱点は、機能の有無より「処理をつないだ結果」の検証にある

当たっている。確定 14 件のうち単独機能のバグは少なく、**更新経路・保存後の再保存・
連続通知・非同期の中断**という「つなぎ目」に集中している。こちらの検証も単機能ごとの
実機確認が中心で、操作列としては通していなかった。
